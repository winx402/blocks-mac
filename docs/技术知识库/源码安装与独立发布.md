# 源码安装与独立发布

现行方向：MIT 开源；不计划 App Store。本文描述入口与安全边界，实际可用状态以
项目管理库的最新验收记录和 GitHub Releases 为准。没有正式 Release 时，安装脚本
会拒绝安装，不会拿未签名源码产物充当官方发行包。

## 贡献者：Blocks 源码版

需要 Apple Silicon Mac、完整 Xcode 26+ 及其支持的构建主机系统。发行包的 macOS 14+
最低版本不代表 Xcode 可以运行在 macOS 14。无需 Apple 开发证书或 provisioning profile。

在检出目录执行：

```sh
./script/dev.sh doctor
./script/dev.sh run
./script/dev.sh test
./script/dev.sh update
```

`run` 编译主 App、CLI 和 Helper，固定安装到
`~/Applications/Blocks.app`，成功后启动。`build` 是仅构建、不安装的附加入口。
`update` 只允许干净工作树的快进拉取，不自动 stash、覆盖修改或重置分支。

Blocks 源码版保持 `app.blocks.dev`、原有独立 Application Support/Keychain/IPC 命名空间。
私有 `peers.json` 登记当前四个可执行文件的身份与 CDHash；重新编译应通过统一入口安装，
不要只替换其中一个二进制。开发 CLI 导出的是 `blocks-dev` 包装入口，调用固定安装内的已登记 CLI。
正式版不会信任开发版清单，开发版也不会接入官方 Sparkle 更新。

替换前需正常退出 Blocks（包括旧路径的 Blocks Dev）与其内置 Helper。脚本不杀进程；安装互斥、身份或权限不满足时会停止。
旧路径 `~/Applications/BlocksDev/Local/Blocks Dev.app` 会作为一次性迁移源；安装成功后旧包进入恢复目录，失败时还原旧包及 peer 登记。存在两份源安装或其他 Bundle ID 占用目标路径时停止，不猜测覆盖对象。

### 固定本机签名，避免每次编译重授权

可在 `~/.config/blocks/development-signing.json` 配置公钥身份信息（文件权限 0600，目录归当前用户且不可被其他用户写入）：

```json
{"schemaVersion":1,"mode":"certificate","identity":"填写 security find-identity -v -p codesigning 列出的40位证书指纹","teamIdentifier":"填写证书的10位Team ID"}
```

私钥仍留在系统钥匙串，不写入配置或仓库。统一安装入口使用该证书重签主 App、内置 Helper/CLI/Broker 及嵌套代码，并保留各组件权限边界。升级前比较旧新 designated requirement，已使用证书签名的安装不允许变回临时签名或改变身份。固定证书丢失时明确失败，不自动切换其他证书。

缺少配置时保留无需证书的 ad-hoc 构建路径，`doctor` 会提示重编译的授权限制。首次从临时签名迁移到固定证书可能需要一次重新授权；后续同身份升级应保留授权，但系统策略或用户撤销仍可能要求确认，不能承诺永不弹窗。不修改 TCC 数据库、不关闭 Gatekeeper、不用明文密钥替代钥匙串。

## 普通用户：官方包

只有通过 Developer ID 签名、公证和 stapling 的 DMG 才是官方安装包。安装不需要 Xcode。
可以从 GitHub Releases 下载后拖入应用程序，或使用 `./script/install.sh`。
脚本会核验版本、架构、固定签名身份、Gatekeeper 和完整性校验；SHA-256 不替代身份验证。
已有用户目录安装会原地更新；不会为绕过系统目录权限另造重复安装。

### 旧 Debug / 独立 Helper 迁移

此路径必须在真实迁移验收后才能标为完成。目前不自动把未知 Debug 包改签或删除。

1. 记录旧 App 和 Helper 的实际位置、Bundle ID、Team ID、数据目录与配对状态，不能只按显示名称猜测。
2. 正常退出旧进程；存在写入或退出失败时停止迁移，不 force quit。关闭相关登录启动项，防止旧包重新启动。
3. 备份旧 App、Helper 和退出后的完整应用数据目录（包括数据库附属文件）。备份放在归档目录，
   不再作为可启动的第二份 App 留在 Applications 中。钥匙串和配对项保留，不清空、不导出私钥。
4. 确认官方包使用兼容的 Bundle ID、Team ID、Keychain group 后安装；不把 `app.blocks.dev` 数据并入正式版。
5. 验证历史、收藏、设置、凭据重启读取、Helper 配对和单实例，再启用新包的登录/CLI 集成。
   任一项失败保留备份和诊断，不能通过清库或重新配对来假装迁移成功。

已知旧开发入口可能位于 `~/Applications/BlocksDev/Debug/Blocks.app`；不得因它不在常规
Applications 根目录就忽略它。各用户路径和数据位置需现场核实，本文不是自动删除指令。

## 维护者：本机发布

首次配置包括：固定的 `install-release-policy.json`（见同目录 schema）、忽略跟踪的
`apps/Blocks/Config/ReleaseIdentity.local.xcconfig`、两份独立 Developer ID profile，
以及本机公证 profile。将 `script/release/release.local.example.json` 的非秘密配置填入
`~/.config/blocks/release.json` 并设置为 `0600`。其中仅存公证 profile 名称、公开证书指纹、
公钥和本机路径，不存密码、API 私钥或 Sparkle 私钥。

Sparkle 使用独立钥匙串 account `app.blocks.app.sparkle`；私钥不进入 GitHub CI。
公钥随官方 App 编译，不能发布后随意更换而中断信任链。

为版本提交 `release-notes/<版本号>.md`，从干净检出运行：

```sh
./script/release.sh prepare 0.1.0-beta.1
./script/release.sh publish 0.1.0-beta.1
```

`prepare` 锁定已提交的源码到临时独立 worktree，核验身份/profile/公证配置后构建、打包、
公证并创建草稿。默认 build number 高于已验证 appcast 与本机状态记录；缺少远端证据时不猜测。
`publish` 复验草稿实际字节、签名和 tag 后公开，再更新对应频道的 appcast。
已公开但 feed 更新失败时可重试 `publish`；不会重新覆盖发行包。中断发生在外部操作和本地
记账之间时必须先核对状态，不手工删锁后盲目重发。

安装包托管于 GitHub Releases；GitHub Pages 仅托管 stable/beta 的静态 appcast，现有官网不迁移。
所有包默认稳定频道，Beta 由用户主动选择；无合适的更高版本时不会自动降级。
首次 Beta、下一版本真实升级和现有发布门禁全部通过后，才具备正式交付条件。
