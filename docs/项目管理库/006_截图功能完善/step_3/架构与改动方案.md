# Step 3 架构与改动方案

状态：implementation-in-progress
最后审阅：2026-07-17
来源级别：implementation architecture plan

## 1. 当前代码事实与必要差异

- 当前截图主路径由 `ScreenshotStore`、`ScreenCaptureKitAdapter`、`ScreenshotSessionGate`、统一编辑器和 `ScreenshotFinalOutputCoordinator` 组成；长截图应复用会话门禁、编辑器和最终 sink，不复制第二套编辑/历史/OCR 实现。
- 所有交互截图在进入编辑器前均不得写原图剪贴板；普通截图和长截图共用显式终态，只有完成写剪贴板/历史，保存只写文件。
- 当前编辑器 `Save As` 只写文件且不是 presenter 终态；Step 3 需要把“保存成功并提交”建模为长截图终态，保存面板取消或写入失败不能提交其他 sink。
- Step 3 实施前的权限快照只有屏幕录制和 Accessibility；本阶段正在新增 Input Monitoring 诊断、请求、设置跳转和刷新状态。代码存在不等于最终安装版 TCC 行为已验证，Accessibility 也不承担滚动控制。
- 当前 `ScreenshotImageCompositor.compose` 会创建整幅 RGBA bitmap。长图不能无条件积累全部解码帧并在主线程一次合成，必须先通过原型确定有效上限、工作集和拼接实现。

## 2. 模块边界

- `BlocksScreenshotCore`：新增纯 Swift/Core Graphics 的滚动会话契约、帧描述、纵向位移候选、重叠评分、固定头部候选、尺寸预算和状态 reducer；禁止依赖 AppKit、ScreenCaptureKit、TCC、数据库或 pasteboard。
- `BlocksApp/Features/Screenshot/Capture`：由 `ScrollingScreenshotCaptureCoordinator` 编排输入、按需取帧、HUD 和终态，由 `ScrollingScreenshotSessionCoordinator` 串行处理匹配、条带和 final stitch；窗口可见性、编辑上下文、会话支持、捕获支持和 Vision 提示分别下沉到独立文件，避免重新形成单体协调器。
- `BlocksApp/Features/Permissions`：为 `PermissionDiagnosticKind`、`PermissionStateSnapshot`、requester、系统设置动作和 assist UI 增加 Input Monitoring 独立状态。
- `BlocksApp/Features/Screenshot/Editor`：复用统一编辑器；扩展 presenter/output outcome，使长截图可区分 `.completed`、`.saved`、`.cancelled`，并关闭长截图的编辑期直接复制路径。
- `BlocksApp/Features/Screenshot/Output`：新增长截图 commit gate，接收唯一不可变 final revision，再调用文件、pasteboard、history/OCR sink；禁止中间帧或 stitch preview 进入现有 final coordinator。
- `BlocksCore` / `ActionRegistry` / Broker / CLI：新增 status/finish/cancel 的类型化契约与 handler；不实现 start、resume、图像传输或输出文件参数。

## 3. 会话状态机与并发边界

运行快照使用唯一状态集合：

`idle -> selecting -> capturing -> possibleEnd -> finalizing -> editing -> idle`

并包含 `capturing/possibleEnd -> recovering -> capturing|paused` 和 `paused -> capturing` 支路。取消、完成、保存和失败由独立 terminal gate 裁决，不再伪造一个与运行快照并行的第二套 `committed/cancelled` 状态机。

约束：

- `ScreenshotSessionGate` 继续作为普通截图、长截图和交互式 Action 的最外层互斥；长截图内部由单一 coordinator actor 串行化帧采集、匹配、状态转换和 finish/cancel。
- UI、滚动 event tap、ScreenCaptureKit 回调、倒计时和 CLI Action 只发送意图，不直接修改拼接缓冲或执行 sink。
- 每个会话有不可复用的 `sessionID` 和 generation。所有异步回调携带 generation；取消、完成或新会话开始后，旧回调无权发布帧、状态或输出。
- finish/cancel 使用 first-terminal-wins。`paused` 不接受 finish；`ready` 也不能被 CLI finish 绕过 Start。
- 拼接完成进入编辑器不是底层会话终态。`ScreenshotCapture` 必须携带长截图 `sessionID`，由编辑器完成、保存成功、丢弃、重截或失败结果显式结束底层会话；终态确认后才释放外层 gate，禁止遗留 `editing` 会话阻塞下一次捕获。

## 4. Input Monitoring 与捕获源

- Input Monitoring 是 Start 前硬门禁。实施候选使用 Quartz 的 listen-event preflight/request 能力和只读 scroll-wheel event tap；最终 API、系统设置 deep link、签名与重启行为必须在目标 macOS 和最终安装版上复核后落代码。
- 全局输入监视只把有效纵向滚轮、Page Up/Page Down、方向键、Space/Shift+Space 的物理 keyCode 和滚动条拖动转换为采样请求；不读取字符正文、不保存原始事件序列，也不向目标 App 注入事件。正负滚轮值和自然滚动设置仅用于低敏诊断，不直接决定方向或暂停。
- 滚轮和滚动条拖动只有在指针位于选区内时触发采样；Page Up/Page Down、方向键和 Space/Shift+Space 依据键盘意图直接触发，不要求鼠标停留在选区内。
- 用户仍在目标 App 中完成滚动；Blocks 不调用 Accessibility、AppleScript 或合成滚轮事件。
- frame source 复用 ScreenCaptureKit，只捕获已冻结的单显示器区域，并排除 Blocks 自身 overlay/HUD/editor 窗口。`SCStream` 只接收完整 surface，并在容量为 4 的 frame bridge 中保留请求后的有限有序帧；禁止把 30fps 回调无界堆成待处理队列。
- 首个完整帧立即建立锚点；后续采样由有效纵向输入驱动。帧源最高 30fps、`queueDepth = 6`，消费端使用 post-demand bounded FIFO：捕获端最多排 8 个 demand，frame bridge 只交付对应请求之后的新帧。滚动输入先立即请求运动帧，约 `80 ms` 再补运动帧，停止输入约 `180 ms` 后请求稳定帧；到底倒计时每秒再请求新帧，以接住懒加载。输入本身不判定方向，方向只由画面匹配确认。

## 5. 拼接流水线

1. Start 后采集首帧，规范化到固定像素宽度、sRGB 和一致 alpha 语义，建立第一锚点。
2. 候选帧先生成 192px 宽、保留完整纵向采样的灰度描述，在 Core 中做全范围稀疏搜索、多区域相关性和致密纹理差复核；仅当快路径出现重叠不足或多解时，App 层才对降采样后的左、中、右 3 个区域执行 Apple Vision 有符号平移估计，Vision 不可用时使用独立的多区域致密亮度估计，形成非决定性的位移提示并重跑 Core 验证。
3. 重叠评分按横向最多 4 区、纵向最多 10 区形成局部块共识，固定侧栏、局部动画和光标只能淘汰局部块；有效区域不足、重复纹理多解或置信度不足仍 fail-closed。
4. 重叠候选必须同时通过最小有效重叠、默认 30% 重叠比例、最佳/次佳间隔、局部一致性和新增行检查；只有独立三区域提示全数一致且高置信时才允许安全的低重叠追加。历史滚动距离不能把视觉多解强制变成匹配。
5. 零新增帧不追加且不替换最后接受锚点。向上位移、重叠不足或多解进入自动 `recovering`，保留最后锚点并继续采样；返回锚点或出现可信向下重叠后自动恢复。连续 3 次仍无法恢复才进入 paused。无效帧、尺寸变化和异常横移继续直接暂停。
6. 长截图开始后根据选区中心和实际可见区域选择最前的外部目标窗口，恢复该 App 而不是激活 Blocks 主窗口。HUD 和取消确认均使用非激活 panel 路径，不得为了显示状态或确认而唤起设置页。
7. 只在首个可信 append 帧对中检测顶部/底部稳定带，确认后锁定高度，后续匹配不重新猜测边界。页头只保留首帧；页尾从首帧条带中暂缓，final stitch 时写到最底部一次。动态或低置信边缘区域不去重，而不是猜测删除。
8. 每次接受新行前计算下一结果尺寸与资源预算，先执行 90% 和硬上限检查，再提交 append manifest。
9. Finish 后根据已接受 manifest 生成单一最终图和编辑上下文；只有完整生成成功才进入 editor。

具体特征、阈值、连续帧数、底部判断和采样节奏均为待 fixture 产出项。`拼接原型报告.md` 是其唯一记录位置。

## 6. 临时数据、内存与硬上限

- 已接受帧和 append manifest 存放在本次会话的随机临时目录，仅用于控制内存工作集；目录不进入截图历史、剪贴板 repository、OCR 或项目文档。
- 内存中只保留当前锚点、候选帧、降采样特征和有限缓存，禁止随高度线性保留全部解码 `CGImage`。
- 最终实现可采用分条带/磁盘后备合成，但必须通过统一 renderer 生成编辑器可消费的不可变最终图。不能在未验证峰值内存前直接把 120 MP 当作默认可达能力。
- 产品绝对边界仍为边长 `<= 32768 px`、总像素 `<= 120 MP`；当前生产有效上限已保守收紧为边长 `<= 16384 px`、总像素 `<= 64 MP`。90% 预警按当前有效上限中最先到达者计算，后续只能依据完整资源证据调整。
- 每次 append 在分配前检查上限；达到上限后不接受会超限的新行。编码、编辑器 source context、保存和 OCR 对长图的资源行为都纳入原型与验收。
- 正常取消与终态立即删除会话目录；崩溃后不恢复 manifest，App 下次启动只按专用目录和命名规则清理 stale 数据。清理失败发布低敏诊断，不尝试打开部分结果。

## 7. 失败暂停与恢复

- coordinator 把帧匹配歧义、暂时 capture 失败、event tap 失效、显示器变化和资源压力映射为类型化 pause reason；日志只记录枚举、计数、尺寸和耗时。
- coordinator 将画面确认的向上位移、暂时重叠不足和多解映射为非阻塞 `recovering`。该状态不提交 append、不允许 Finish；三次稳定恢复尝试耗尽后才转为 paused，Resume 会重置三次恢复预算。
- 进入 paused 前先停止采样并封存最后一致 manifest。候选帧和未提交 append 丢弃，任何 sink 保持未调用。
- Resume 重新检查屏幕录制、Input Monitoring、目标显示器、固定区域像素尺寸和最后锚点，并采集验证帧。只有锚点重新建立成功才回到 capturing。
- final stitch 失败视为不可恢复失败：停止帧源、清理临时目录并结束本次捕获，不打开编辑器、不输出部分结果。当前版本不保留一个可能已部分分配的 final stitch 供原地重试。
- 进程退出或崩溃不保留恢复入口，这是明确产品边界，不实现 session journal 恢复。

## 8. 最终编辑与输出事务

- 成功 stitch 创建长截图 `ScreenshotCapture`，类型和 metadata 明确标记 scrolling，`editingContext` 只覆盖最终长图，不伪装为可扩展虚拟桌面冻结源。
- editor presenter 为长图注入输出策略：禁用直接 copy；Complete 返回 final image；Save 先原子写文件，成功后返回同一 final image 与目标 URL 作为提交终态。
- 滚动会话以 `(sessionID, finalRenderRevision)` 做 first-terminal-wins 门禁。完成终态调用 `ScreenshotFinalOutputCoordinator` 写 pasteboard/history；保存终态只确认文件成功并结束编辑会话，不调用最终 sink。
- 保存面板取消、写盘失败、编辑器取消或 stitch 失败都不得调用 final coordinator。保存成功后文件 sink 已完成，其他 sink 仍按 Step 2 独立状态回报。
- 历史记录使用最终长图的同一 capture ID 和规范化 payload；不得为中间帧创建多条 screenshot 记录，也不得逐帧 OCR。

## 9. Action / CLI

| Action | 处理位置 | 主要结果 | 主要错误 |
| --- | --- | --- | --- |
| `blocks.screenshot.scrolling.status` | App host 读取 coordinator snapshot | `idle` 或低敏会话 snapshot | `host_unavailable` |
| `blocks.screenshot.scrolling.finish` | App host 发送 finish intent | `finish_requested` 与新状态 | `stale_session`、`invalid_state`、`session_paused` |
| `blocks.screenshot.scrolling.cancel` | App host 发送带显式确认的 cancel intent | `cancelled` | `stale_session`、`already_terminal`、`confirmation_required` |

- status snapshot 固定返回 session ID、state、pixel dimensions、limit warning 和 permission 状态；后续若增加低敏 pause/capability 字段必须保持向后兼容。不返回图片、区域坐标、窗口标题、App 名或临时路径。
- finish 只改变 GUI 已启动会话的状态，不能返回图片或跳过 editor。cancel 等待 coordinator 完成清理后才返回成功。
- `ScreenshotActionHost` 的现有 capture request 与长截图控制请求都受同一外层活动会话身份约束，但 status/cancel 必须能访问当前长截图，不能被“已有 active request”提前拒绝。

## 10. 实施顺序与门禁

1. 先实现 `拼接原型报告.md` 的 pure fixture harness，产出重叠、头部、到底、采样、内存和有效上限阈值。
2. 落 Core 契约、状态 reducer、尺寸预算和 fixture 回归，不接真实 TCC 或 sink。
3. 接入 Input Monitoring 诊断、单屏固定区域、frame source、HUD 与失败暂停恢复。
4. 接入 disk-backed staging、final stitch、统一编辑器长图策略和延迟 commit gate。
5. 接入 status/finish/cancel Action、CLI 契约与竞争测试。
6. 完成自动化、同签名 App/CLI/Broker、最终安装版 TCC、真实网页/文档录屏、资源上限和崩溃清理证据后，才可把阶段状态改为 complete。开发构建脚本必须把稳定签名参数同时应用到 App、Broker 和 CLI，禁止界面显示 Broker 已启用但 ad-hoc CLI 被身份校验拒绝。
