# 架构与改动方案

状态：accepted-platform-evidence-pending
最后审阅：2026-07-19
来源级别：implementation architecture

## 1. 目标

本文回写 Step 1 已确认的最终实现架构，只覆盖当前 Phase 1 的采集、编辑、输出和交互式 CLI/Action 接入。本文区分三类内容：

- 已确认：进入实现的唯一架构口径。
- 待平台实测：需要在 1A/1C 中用本机和打包运行态再次核验的系统事实。
- 非目标：本阶段不实现，也不顺带迁移。

## 2. 已确认架构

### 2.1 独立 `BlocksScreenshotCore`

Phase 1 的截图核心能力收敛为独立 `BlocksScreenshotCore`，由 GUI、CLI 和 Action 共用，不再把截图核心逻辑散落在 App presenter、Store 和临时 service 中。

`BlocksScreenshotCore` 负责：

- 截图请求模型、捕获规划和结果 metadata。
- `intent kind + displayScope` 契约解析、跨屏切片与合成。
- `ScreenshotSceneDocument`、`ScreenshotSceneSnapshot`、交互 draft、revision、撤销/重做和统一渲染/导出语义。
- 原图复制、最终图复制、PNG/JPEG 导出所依赖的非 UI 规则。

`BlocksScreenshotCore` 不负责：

- overlay、窗口、菜单栏、设置页、状态提示和权限引导。
- App 生命周期、冷启动激活、全局快捷键注册和 XPC 连接管理。

### 2.2 App adapters

App 层只保留截图 feature 的平台适配与界面协调，不重复实现核心规则。

App adapters 负责：

- 智能选择 overlay、区域调整、窗口/屏幕候选呈现和编辑器窗口。
- 屏幕录制权限、焦点、状态栏文案、设置入口和快捷键 UI。
- Pasteboard 写入、图片预览、窗口恢复和与现有 App shell 的路由衔接。
- 把 AppKit / SwiftUI / ScreenCaptureKit / NSPasteboard 细节封装给核心接口。

规则：

- App adapter 可以调用 `BlocksScreenshotCore`，但不能复制 capture planning、rendering、export 或 edit recipe 逻辑。
- 现有 screenshot page/result presenter 只允许作为替换对象，不继续演进为第二套路径。

### 2.3 通用 `BlocksActionBroker`

交互式 CLI/Action 不直接驱动截图 UI，而是统一进入通用 `BlocksActionBroker`。该 broker 不是 screenshot-only 组件，Phase 1 只是先让截图使用它。

确认口径：

- broker 采用 `LaunchAgent + XPC` 形态。
- broker 必须显式启用；不做静默安装或首次调用自动常驻。
- broker 接到交互式请求时负责定位或唤起 App；允许 App 冷启动后继续完成截图会话。
- CLI/Action 只负责提交请求、等待完成/取消/错误结果，不在命令侧实现选区层或编辑器。

### 2.4 `intent kind + displayScope` contract

所有截图请求都必须先解析成稳定的 intent contract，再进入实际捕获：

- `kind` 表达捕获意图：`smart`、`region`、`window`、`display`。
- `displayScope` 只在 `kind == display` 时使用，取值为当前显示器、全部显示器或指定 display ID；未提供时默认当前显示器。
- 捕获结果只返回实际 `region`、`window` 或 `display` kind，并附实际 `displayScope`；结果永不返回 `smart`。
- region/display 不允许直接依赖“全局一块图”假设；必须先解析到显示器范围，再按显示器切片捕获。
- 跨屏 region 由核心按显示器求交、分别捕获、统一合成；任一切片失败则整体失败。
- 实时 window 捕获采用 `SCContentFilter(desktopIndependentWindow:)`，选择结果只保存 window ID，完成选择后重新解析最新窗口；窗口周围可扩展的编辑上下文再按相关显示器抓取冻结 tile，并把干净窗口捕获置顶合成。

这意味着 GUI 智能选择、CLI 显式模式和 broker 请求最终都会汇聚到同一份 resolved contract，而不是各自维护一套 rect/display 推导。

### 2.5 输出终态与显式 copy

Phase 1 的交互式输出契约已经确认：

- 捕获成功和原屏统一编辑器出现时均为零输出，不写剪贴板，也不创建截图历史。
- 编辑器文档保持非破坏编辑；用户点击“完成”时才渲染最终扁平图，写入剪贴板一次、按当前设置写截图历史并关闭编辑器。
- “复制”显式写入当前渲染结果一次，但保持编辑器打开；“保存”只写文件，不改写剪贴板。
- 关闭、丢弃、重截和取消均不写剪贴板或截图历史；此前由用户主动复制的内容不回退。
- 默认格式是 PNG；JPEG 只作为显式导出选择。无编辑器 Action 保留既有显式 `copy` 参数语义。

### 2.6 Breaking replacement

Step 1 采用 breaking replacement，不做迁移层，也不维护新旧双逻辑：

- 旧三模式首页、旧截图结果预览窗、旧交互式 CLI 路径直接被新路径替换。
- 不保留“旧 capture chain 继续跑，只有新入口走新逻辑”的并行实现。
- 不引入兼容桥去长期维持旧状态机、旧 presenter 或旧入口模型。

需要保留的只有用户可见的能力目标和必要的测试样本，不是旧实现结构。

统一编辑器重构继续执行同一原则：

- `ScreenshotEditCommand` 被 scene snapshot + element 模型替换；拖动编辑通过 document interaction transaction 实时更新 draft，提交时只生成一次 revision。
- `ScreenshotEditorMode`、`ScreenshotEditorLayout` 及双 surface 分支被 `ScreenshotEditorToolbarState.compact/expanded` 替换；状态只表达同一原屏工具条内容，不影响窗口或画布语义。
- `ScreenshotEditorPresenter` 只管理一个覆盖冻结源范围的 `ScreenshotEditorHostPanel`；Store 必须只持有一个 `ScreenshotSceneDocument`。
- 交互编辑依赖冻结 `ScreenshotSourceContext` 扩展范围；缺少该上下文时终止本次截图且不写剪贴板，不允许降级到第二个窗口。
- 工具共用一份稳定 `toolOrder`，持久化 `quickToolIDs/hiddenToolIDs`，扩展区由其余可见工具推导；逐工具样式共享。v6 字段不迁移、不并行读取。
- 截图偏好 v7 同时保存 `retainsCaptureDefaults`、初始工具条状态和统一工具分区；旧版本不迁移。设置工具条始终修改基线；正式会话是否回写基线由该策略统一裁决。
- 正式选择层与设置页通过同一个 AppKit 捕获工具条组件渲染，设置变体只禁用把手拖动，参数映射和控件指标不得分叉。
- 共享捕获工具条把尺寸、延迟、冻结和水印建模为四个等宽具名字段；标签列按当前语言的最大标签宽度统一，值列固定为 96pt。冻结把原生 `NSSwitch` 放在完整可点击值槽内，延迟与水印使用不显示下拉箭头的安静值按钮打开原生 `NSMenu`。标签和值间距 4pt、字段间距 12pt 均由同一 metrics 计算，避免内容长度或本地化改变外层 frame。
- 编辑器输出优先使用与当前 scene revision 对齐的渲染缓存；缓存落后时输出命令等待异步结果，禁止在主线程重复渲染整张场景。
- 样式连续交互使用 begin/update/commit 事务，结束时只提交一次精确渲染和一次偏好持久化；工具选择和对象选择不得触发像素渲染。
- 编辑器关闭确认由单实例协调器以 attached sheet 附着到 `ScreenshotEditorHostPanel`，确认期间禁用画布和重复关闭请求。

### 2.7 编辑交互事务与控制柄

- `beginInteraction` 从 committed snapshot 建立 draft；`updateInteraction` 每帧规范化并更新 presented snapshot；`commitInteraction` 写入一次 undo；`cancelInteraction` 丢弃 draft。
- 新建对象、移动对象、矩形缩放、线端点调整、范围创建/移动/缩放均走该事务；不允许每个 mouseDragged 事件直接调用普通 mutate。
- canvas 绘制对象选框与控制柄，Store 用共享 geometry hit test 解析控制柄，避免视觉命中和实际编辑规则分叉。
- 模式切换前取消未完成手势，已提交 scene、选择、undo/redo 和 viewport 保留。

### 2.9 v19 圈选区 Chrome、工具分区、平铺水印与钉图边界

- 编辑器继续使用覆盖冻结源范围的单一全屏 Host。`ScreenshotEditorCropChromeLayout` 把源坐标中的当前 `cropRect` 投影到窗口坐标，并把状态条锚定在圈选区上方、属性行与主工具行组成的底栏锚定在圈选区下方；普通圈选仍使用完整画布，只有大图导致上下 Chrome 无法位于安全区时才缩小展示画布，输出像素与文档坐标不变。设置页不得复用运行态状态条。
- 编辑器工具栏不再提供移动手柄，也不持久化位置偏移；捕获阶段的参数工具栏仍是独立会话控件，不受该约束影响。
- 工具配置以 `ScreenshotPreferencesStore` 为唯一事实源。快捷、更多和隐藏三段由同一全局顺序与分区集合派生；AppKit 桥接层只负责指针会话、插入位置反馈和输出 `tool + destinationZone + beforeTool`，不得缓存第二份可提交配置。
- 拖动期间冻结桥接层展示快照，避免 SwiftUI 偏好回写打断 AppKit 指针会话；指针松开并解析出有效落点后才以一次原子操作更新归属和顺序，取消、无效载荷及原位投放都不持久化。
- `ScreenshotSceneSnapshot.outputAppearance` 是圆角输出的唯一文档状态；渲染和导出先完成裁剪，再统一应用圆角遮罩。PNG/剪贴板保留透明角，JPEG 在编码前合成白底，输出宽高不变。
- `ScreenshotWatermarkStyle` 是唯一运行时水印样式，只包含文字、颜色、字重、相对字号、密度、倾斜角度和透明度。`ScreenshotSceneDocument` 归一化为最多一个水印元素；渲染器在效果层之上、普通标注之下按最终裁剪宽度计算字号与间距，长截图只在拼接完成后平铺一次。画布命中和 AX 移动目标过滤水印，但状态条仍可选中它。
- `PinnedScreenshotManager` 持有多个临时钉图 Controller。Presenter 通过 `PinnedScreenshotPresentation` 显式传入最终像素图、裁剪区域逻辑点尺寸、统一输出像素比例、原截图屏幕 frame 和目标显示器安全区；100% 始终按逻辑点尺寸展示，显示缩放不修改复制或保存像素。普通截图把 Core 顶部原点的 crop 像素映射回 AppKit 全局坐标，初始 Panel 覆盖原截图位置；长截图以原捕获 frame 顶边为锚点。目标显示器按原 frame 最大相交面积选择，初始位置只做完整落入安全区所需的最小收敛，不再无条件居中。每个 Controller 管理无边框跨桌面浮动 Panel 和独立 OCR 结果卡，不再保留鼠标穿透、锁定状态或独立解锁窗口。`.pinned` 是明确编辑终态：Presenter 先显示钉图，再以 `writesPasteboard: false` 执行历史 sink；历史失败不回滚或阻止已显示的钉图。

## 3. 待平台实测

以下内容已确定要采用，但系统事实仍需在实施中重新核验，不能提前写成“已通过”：

- 多显示器、混合缩放、负坐标下的跨屏切片和合成结果。
- display-scoped window capture 在正式 App 运行态、不同窗口层级和冻结画面下的稳定性。
- `LaunchAgent + XPC` broker 的注册、显式启停、权限边界和 App 冷启动恢复。
- broker 在 App 未启动、App 已启动但无截图会话、截图会话取消/超时场景下的结果一致性。
- screenshot 自身 pasteboard 写入抑制，确保显式“复制”或“完成”的写入不被普通剪贴板监听重复收录。

这些项目是实现期 hard gate，不是开放性讨论项。

## 4. 非目标

本阶段明确不做：

- 截图历史、本地 OCR、OCR 搜索、翻译、总结或任何 Provider 图片外发。
- 双逻辑灰度、旧入口兼容桥、旧 presenter 迁移层。
- 为未来 AI、Hook 或其他 feature 预留新的截图专用 broker 分支。
- 重新设计剪贴板 schema、Provider 授权模型或 Phase 2 之后的数据持久化。
- GIF、视频、音频录制、滚动长截图和高级美化。

## 5. 当前实施状态

Phase 1 与 Step 2 已获得开发授权。当前工作树已完成统一编辑器、v10 类型化 preset、专业工具包、对象优先编辑和文字自动/定宽测量，Core/App hosted tests 与 P14/P15 已通过。当前仍需补专业工具条、A 工具包、对象优先编辑、三屏、混合 DPI、窗口层级和 Broker 的真实 UI 证据。
