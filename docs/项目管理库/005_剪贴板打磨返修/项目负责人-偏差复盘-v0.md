# 005_剪贴板打磨返修 项目负责人偏差复盘 v0

状态：recorded
日期：2026-07-07
角色：项目负责人

## 1. 结论

004 出现“需求理解和最终实现偏差”，主要不是用户表达不清，而是项目负责人在需求收敛、验收边界和角色协作上没有把真实 UI 体验类诉求守住。

004 的自动化、静态门禁和低敏验证证明了一部分架构与代码契约成立，但没有证明用户最关心的真实面板体验已经改好。项目负责人在最终接受时把真实 UI / hover / 详情编辑路径 / 本地化可见文案等风险保留为 P2 residual，实际这些恰好是本轮需求的核心体验目标，不应整体降级接受。

## 2. 主要偏差原因

### 2.1 把“覆盖需求”误判成“体验达标”

004 的覆盖矩阵确认了需求条目在 PRD、技术方案、开发记录和验证脚本中都有对应项，但这只能说明“有处理路径”，不能说明“真实界面达到了用户预期”。

例如：

- “显示内容”被转化成 preview/read model 契约后，没有强制拿真实面板截图逐条确认新旧数据展示。
- “条目密度提升”被转化成布局或静态检查后，没有和真实截图对比内容面积是否明显变大。
- “详情元数据重组”被转化成详情模型和窗口编辑能力后，没有验证用户看到的详情面板是否符合两列/长字段单列预期。

### 2.2 对真实 UI P2 residual 的分级错误

004 最终验收中已经写明以下内容未实测：

- 真实 App UI、真实鼠标 hover 手感。
- 真实窄宽度、长文本、长标签、长 App 名。
- 真实系统剪贴板。
- 真实 VoiceOver / accessibility inspector。

这些在工程风险上可以叫 P2，但从用户这次需求的性质看，面板显示、hover、右键菜单、详情编辑和隐私页文案就是主路径体验。项目负责人不应在没有真实 UI 证据的情况下接受“体验打磨完成”。

### 2.3 阶段拆解过于工程化，削弱了体验验收

004 拆成搜索、标签、面板交互、详情编辑、隐私页、收口等阶段后，工程边界变清楚了，但用户原始体验诉求被拆散到多个技术阶段中。每个阶段都能局部通过，最终却没有足够强的“用户路径回放”来确认整体体验。

典型问题：

- 收藏在模型上是内置标签，但用户交互上应该是一级动作；实现把模型事实暴露到了菜单层级。
- 详情编辑在能力上可编辑，但打开独立窗口与用户“在详情里编辑”的路径预期不一致。
- 隐私页功能完成了 App policy 管理，但可见文案没有以多语言可见结果作为验收。

### 2.4 对“低敏验证”的适用边界没有守住

低敏验证适合证明：

- 数据模型事务。
- 搜索索引契约。
- 禁止敏感输出。
- CLI 默认输出边界。
- 构建和静态扫描。

但它不适合替代：

- 内容预览是否好读。
- hover 安全区是否顺手。
- 右键菜单层级是否符合预期。
- 详情面板是否减少跳转。
- 本地化文案是否真实显示。

这次把低敏门禁的 PASS 当作足够强的项目接受证据，是验收方法和需求类型不匹配。

### 2.5 角色复审没有形成足够强的最终体验闸门

UI/交互、测试/质量、代码审查等角色多次指出真实 UI / VoiceOver / 截图证据不足，但项目负责人最终选择以 P2 residual 接受，没有把这些意见转化成“体验类需求必须真实截图验收”的硬门槛。

这说明协作流程里还缺一个规则：当项目标题和目标本身是“体验打磨”时，UI/交互复审和真实截图/录屏证据不能只是建议项，至少关键路径必须进入接受条件。

## 3. 后续纠偏原则

### 3.1 005 不能只复用 004 的自动化门禁

005 必须把真实界面证据作为验收输入。自动化门禁仍需要保留，但只能证明实现没有破坏底层契约，不能单独证明体验达标。

### 3.2 先用截图定义“用户看到的结果”

对每个返修点，PRD 或交互规格应先定义可见结果：

- 条目卡片里哪些区域显示正文，哪些区域显示来源、类型、标签和时间。
- 哪些旧数据允许显示字符数，哪些必须显示正文或更合适摘要。
- 收藏在右键菜单中的准确位置和名称。
- 详情编辑是否在当前详情面板内完成，保存/取消按钮如何出现且不跳布局。
- 元数据两列/单列规则对应哪些字段。

### 3.3 真实 UI 验收要前置

005 的阶段验收至少应包含：

- 真实 App 截图。
- 关键右键菜单截图。
- hover 展开/收起录屏或明确鼠标路径证据。
- 隐私页中英文/中文文案截图。
- 详情编辑前、中、后的截图。

如果某项无法真实验证，不能写成“完成”，只能明确保留为未验收项。

### 3.4 模型实现不能替代交互设计

收藏可以在底层继续作为内置标签，但用户入口需要按“收藏”动作设计。详情编辑可以复用已有详情 store，但用户路径需要在详情面板内完成。后续技术方案必须显式区分“底层模型事实”和“用户可见交互表达”。

### 3.5 项目负责人接受标准要调整

对体验打磨类项目，项目负责人最终接受前必须回答：

- 用户截图里指出的问题是否在新截图中消失。
- 用户原话里的动作路径是否能直接完成。
- 是否还有内部 key、英文文案、工程模型名暴露到 UI。
- 残余风险是否落在非核心路径，而不是用户核心诉求本身。

## 4. 对 005 的流程影响

005 当前应继续收集用户补充，不急于进入实现。用户补充完成后，项目负责人需要先做一轮“可见结果定义”，再派发产品经理和 UI/交互设计师。

005 的验收应改为“真实 UI 证据 + 自动化门禁”双轨：

- 真实 UI 证据负责证明用户体验达标。
- 自动化门禁负责证明数据、索引、事务、本地化资源、输出边界和构建没有回归。

只有两条轨道都满足对应范围，才可以接受。
