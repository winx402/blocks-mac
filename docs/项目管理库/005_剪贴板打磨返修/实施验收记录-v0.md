## 7.3 2026-07-21 排序刷新与双击粘贴竞态修复

### 已确认事实与根因

- 用户看到的 `BLOCKS_ORDER_B_20260720` 是此前验收产生的低敏排序测试文本；当前仓库和正式数据库检查均未发现残留记录。本轮不把该字符串或任何真实剪贴板正文写入日志、测试数据库或项目证据。
- 面板此前只依赖最长 0.7 秒轮询捕获外部复制，打开面板时可能先显示旧的第一条；Blocks 自己写入 pasteboard 后又在异步激活目标 App 之后才登记忽略，存在被轮询服务先捕获为新记录的窗口。
- 双击路由自身已能取消延迟单击，但粘贴命令可能在面板关闭、目标 App 激活和输入焦点恢复尚未稳定时发往错误窗口。

### 实现

- 展示浮动面板前同步执行一次 `pollPasteboard()`；外部新复制或重复内容可以在面板出现前进入既有 Repository/Store 严格排序链路。
- `ClipboardPasteboardWriter` 在成功写入或失败回滚发生的同一同步调用内，把对应 changeCount 登记到共享 `ClipboardPasteboardChangeSuppressor`，再开始窗口激活和焦点恢复；调用方删除事后重复抑制路径。
- 精确焦点恢复要求连续两次检测到同一可编辑焦点；发送前再经过一个主线程周期和 35ms 稳定窗口，并复核 PID/前台身份。`Cmd-V` 直接投递给已确认 PID；无法恢复精确输入框时仍只向稳定前台目标尽力发送一次，不自动重试。

## 7.6 2026-07-22 复制顺序和双击粘贴再定位

### 已确认事实

- 现场数据库的低敏元数据显示：两条不同记录的 `last_copied_at` 在约 1.17 秒内先后被更新，旧第二条确实在新复制后又发生了一次“提升”。因此这不是列表比较器或 SwiftUI 渲染次序问题。检查不读取、记录或输出正文。
- 可以更新 `last_copied_at` 的运行路径只有两类：同内容外部变更被重复捕获，或面板粘贴/纯文本复制成功后调用 `markCopied`。旧日志没有记录记录 ID 摘要和完整事务阶段，无法对已发生的两次提升做越过证据的归因。
- 代码审查确认两个结构性问题：卡片同时安装高优先级双击和并行单击，再由 140ms 自定义任务消歧，一次鼠标序列可跨越视图重绘和面板关闭；粘贴又在确认目标 App/输入焦点之前先覆盖系统剪贴板，焦点恢复失败后还会降级把 `Cmd-V` 发给任意前台控件。这与“面板关闭但输入框没收到内容”直接一致。

### 当前修复契约

- 卡片改用系统双击时间管理的 `ExclusiveGesture`：单击只会幂等打开详情，双击只会产生一个粘贴请求，删除 140ms 延迟任务、抑制时间窗和同记录详情反复切换。
- 粘贴事务先校验目标 App、Accessibility、前台稳定和精确可编辑焦点，确认后才以请求创建时的 `changeCount` 写入剪贴板。已捕获的精确焦点恢复失败时不再降级到任意控件；缺少有效目标时保持面板打开并报错。
- 有效目标已捕获时，面板只在事务期间临时隐藏：命令成功发送后才真正关闭；焦点恢复、激活、pasteboard lease 或事件创建任一步失败都会恢复原面板，避免“面板关闭但没有粘贴”变成无反馈终态。
- pasteboard writer 在真正写入前再次校验 `changeCount`，并一次抑制 clear/write/rollback 事务可能产生的全部连续 changeCount，不再只抑制最后一个值。只有当前代次、已发送粘贴命令且 write lease 仍有效的事务才能提升记录；目标丢失或事件失败不再伪装成“已复制到剪贴板”后提升旧记录。
- 新增不含正文的诊断链：交互 token、记录 ID 后 8 位、来源、阶段、事务代次和 changeCount。新安装版如再有顺序变化，可以直接区分“真实外部重复复制”和“Blocks 粘贴事务提升”，不再靠时间表象猜测。
- 新增覆盖互斥单/双击、写入前外部变更拒绝、多 changeCount 自写入抑制和旧事务不能提升的回归测试；P13-C 同步删除旧 140ms/详情 toggle 断言。本节不改变 005 项目阶段状态。
- 隔离 Application Support 数据库的安装版验收中，先复制 B、再复制 A，A 立即位于第一条并在等待 5.5 秒后仍保持第一；没有有效目标上下文的粘贴请求保持面板且没有产生事务。完整 `BlocksAppTests` 388 项执行，386 项通过、2 项按既有高内存条件跳过、0 failure；P13-C 通过。系统自动化无法代替 Carbon 全局热键产生真实硬件事件，因此该限制不写成“真实键盘双击粘贴已通过”。

## 7.7 2026-07-22 复制提交与面板粘贴事务重构

### 对 7.6 运行口径的纠正

- 7.6 把“只有 `Cmd-V` 已发送才提升记录”当成了安全约束，这与用户确认的“双击 → 复制 → 粘贴”语义冲突，也是目标 App 或焦点恢复失败时条目不会置顶的直接原因。本节废止该口径。
- 新口径为：双击先解析记录和 payload，写入系统 pasteboard 成功后立即更新该记录的 `lastCopiedAt` 并重排，然后才恢复目标 App/输入框并发送一次 `Cmd-V`。自动粘贴失败不得回退已完成的复制和置顶。

### 已确认根因

- 旧链路在自动粘贴命令成功后才调用 `markCopied`。无目标 App、Accessibility 拒绝、激活失败、焦点恢复失败或事件创建失败会同时跳过复制/置顶语义。
- `ClipboardHistoryPanelPresenter` 只保存一个全局布尔“临时隐藏”状态。旧任务取消后的 `defer` 可能恢复或关闭新一轮面板，这能直接导致连续第二/第三次操作失效或面板状态僵住。
- 搜索结果可以包含尚未载入 `ClipboardStore.records` 首页的记录，但旧双击和 payload 读取只查 `records`，因此部分界面上真实可见的条目实际无法粘贴。
- 旧 `markCopied` 在仅更新时间时仍重读图片 sidecar、标签并重建搜索文档/FTS；与时间更新无关的 I/O 失败会让置顶失败，同时增加连续操作的主线程负担。
- 时间精度不是已复现现象的原因：SQLite 保存的时间具有亚秒精度，原排序比较器也一致。但本轮仍增加全库严格单调时间，相同时钟输入按 1 微秒递增，消除快速连续操作的平局可能。

### 实现收敛

- `ClipboardAutoPasteCoordinator` 拆为 `copyToPasteboard` 和 `dispatchPaste`；前者产生 write lease，后者只处理目标激活、焦点恢复与一次 `Cmd-V`。
- `ClipboardPasteTransactionState` 明确跟踪 `copying → copied → activating → dispatching → completed/failed`；新请求取消旧请求，外部 pasteboard 变化使当前事务失效。
- 面板隐藏和完成回调都绑定 session UUID；过期回调会被记录并忽略，不能操作新面板。
- Store 按“已加载记录 → 当前搜索结果 → Repository”统一解析记录；时间提升只执行单条 SQL 和当前列表重排，不再读 payload 或重建 FTS。

## 7.8 2026-07-23 非激活面板与冻结目标模型

本节废止 7.7 中“面板激活 Blocks 后再激活目标 App、恢复 AX 第一响应者、按 PID 投递 `Cmd-V`”的派发设计；7.7 的“先复制并置顶，后尝试自动粘贴”仍然有效。

### 竞品交互结论

- [Paste](https://pasteapp.io/help/paste-directly-to-other-applications) 的直接粘贴以调用前的活动 App 为目标，失败时内容仍保留在系统剪贴板。
- [Maccy](https://github.com/p0deje/Maccy/blob/master/Maccy/FloatingPanel.swift) 使用非激活浮动面板，避免历史面板本身抢走目标 App。
- [CopyQ](https://github.com/hluk/copyq/blob/master/src/gui/mainwindow.cpp) 保存先前窗口上下文，不在条目动作发生后重新猜测目标。
- [Raycast](https://manual.raycast.com/clipboard-history) 将复制到系统剪贴板与是否成功派发粘贴视为两个阶段。

上述共同点用于确定 Blocks 的交互模型，不代表复制任一产品的完整实现。

### 已确认代码根因

- 旧面板在 `present`、`focus` 和失败恢复阶段调用 `NSApp.activate`，先把 Blocks 变成活动 App；随后自动粘贴再重新激活此前目标。连续操作中前台进程和 Key Window 因此反复切换。
- 旧自动粘贴在恢复目标 App 后遍历 AX 树、写 `AXFocused`，最后使用 `postToPid` 定向发送按键。浏览器/Electron 的 AX 节点可能在面板出现或页面更新后失效，导致“面板关闭但输入框没收到内容”。
- 旧 `hideForPaste/finishPaste` 维护独立的临时隐藏状态；旧事务的完成回调可以晚于新面板出现，造成第二次失效或第三次无响应。
- 条目置顶曾依赖自动粘贴成功。目标失效、Accessibility 拒绝或焦点恢复失败时，系统剪贴板和历史排序语义被错误地绑在粘贴结果上。
- 自写入只依赖 changeCount 推测时，监听器可能把 Blocks 写入再次当成外部复制；反过来，仅凭 pasteboard 中存在来源类型就忽略，也可能吞掉外部 App 原样保留该类型的真实复制。

### 当前唯一运行链路

```text
打开入口
  → 捕获调用 ID + 当前外部目标 PID/Bundle + 窗口/AX 诊断快照
  → 显示 nonactivatingPanel（普通面板目标冻结）
  → 双击 / Return / Cmd+数字
  → 解析记录与 payload
  → 写 pasteboard（携带 operation ID）
  → commitCopyEvent 去重、更新时间、立即置顶
  → 普通面板关闭；固定面板 resignKey
  → 确认冻结目标仍连续两次位于前台
  → 通过 session event tap 发送一次全局 Cmd-V
  → 成功；或保留复制/置顶结果并提示手动 Cmd-V
```

- 普通面板使用 `.nonactivatingPanel`。打开前生成 `ClipboardPanelInvocationContext`；搜索、筛选、详情和面板点击不覆盖目标。
- 固定面板只响应用户明确激活的、具有可见普通窗口的外部 App。Blocks、自身浮层、系统设置和无普通窗口进程不作为新目标。
- AX 只保留目标窗口、角色和可编辑语义作为诊断信息，不再遍历控件树或修改第一响应者。
- 普通面板在系统剪贴板写入和置顶成功后立即关闭，不等待 `Cmd-V` 结果；固定面板保持可见但放弃 Key 状态。
- 主路径只使用 `.cgSessionEventTap` 发送一次 `Cmd-V`，不激活目标、不使用 `postToPid`、不自动重试。
- `ClipboardPasteboardWriteOriginRegistry` 只确认本进程刚登记且 operation ID、record ID、签名、changeCount 全部匹配的写入。未知或被外部 App 重放的来源标记仍按真实外部复制捕获。
- 双击、Return 和 `Cmd+数字` 统一调用复制提交路径；成功写入后复用已有签名记录、以严格递增的 `lastCopiedAt` 置顶。按住 `Cmd` 时的快照继续保证连续数字映射稳定。

## 11. 2026-07-25 详情保存后历史面板失去交互

### 已确认根因

- 详情编辑发生在可成为 Key Window 的子 Panel。保存或取消结束后，Key 状态没有归还历史面板。

- 父面板收到详情子 Panel 之后的首次记录点击时，只恢复 Key 状态，并始终让原始鼠标事件继续进入 SwiftUI 条目控件。
- 删除旧的 `onFirstMouseRecordActivation` 手工选中旁路，单击、双击继续走既有唯一条目动作逻辑。
- 新增 `clipboard-detail-focus` 日志，区分“编辑结束主动恢复”和“首次记录点击兜底恢复”。
