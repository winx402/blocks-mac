# App 数据存储架构规范 v0

状态：implemented-v0
最后审阅：2026-07-05
来源级别：project architecture

本文定义积木工具后续 App 内数据存储的统一技术边界。剪贴板持久化是第一个落地场景，但本规范不只服务剪贴板；截图历史、provider 审计、hook draft、OCR/翻译历史等后续业务数据也应按本文分层进入对应 store。

## 架构结论

默认采用 `SQLite3 + Repository + sidecar blob files + Keychain + UserDefaults`。

- SQLite 负责结构化业务记录、索引、检索、迁移、策略裁剪和可审计删除。
- Repository 是业务唯一事实源；UI state 只保存视图态、选择态和临时交互态。
- 大图片、附件、截图原图、未来 OCR 输入图等大对象使用 sidecar 文件，SQLite 保存相对路径、hash、大小和生命周期。
- Keychain 只保存 secret、token、API key 等凭据；普通业务记录不得写入 Keychain。
- UserDefaults 只保存轻量偏好、布局、开关和用户配置项，不承载业务历史。
- JSON debug / fixture store 保留为验证、导入导出或低敏 fixture；不作为生产主存储路径。

## 数据分类

| 数据类型 | 默认存储 | 示例 | 规则 |
| --- | --- | --- | --- |
| 轻量偏好 | UserDefaults | 面板位置、快捷键、字体大小、默认语言 | 可丢失可重建；不放业务历史和敏感内容。 |
| 业务记录 | SQLite | 剪贴板条目、截图历史、provider audit、hook draft | 必须有 schema、迁移、删除和测试。 |
| 大对象 | Sidecar + SQLite 引用 | 图片 payload、截图原图、附件 blob | 文件名不含原文；删除记录时同步清理。 |
| 凭据 | Keychain | API key、provider token | 只短生命周期读取；不写日志、不写 DB。 |
| 临时 UI 状态 | 内存 | 当前选中、hover、临时输入框 | 不跨重启承诺。 |
| Debug/fixture | JSON 或临时目录 | helper watch、低敏 fixture | 不进入生产事实源；输出必须脱敏。 |

## 统一路径

首版主 App 单写，默认路径：

```text
~/Library/Application Support/Blocks/Data/
  Blocks.sqlite
  Blocks.sqlite-wal
  Blocks.sqlite-shm
  Blobs/
```

实现上通过 `StorageEnvironment` 计算路径，测试使用临时目录。未来 helper/App Group 生产化时，只允许通过 `StorageEnvironment` 切换到共享容器；不得在各模块硬编码路径。

## 基础设施

首版基础设施名称固定：

- `StorageEnvironment`：负责 app support、database URL、blob root、测试目录和未来 App Group 目录选择。
- `SQLiteConnection`：封装系统 `SQLite3` open/close/prepare/bind/step/finalize、transaction 和 pragma。
- `MigrationRunner` / `AppDatabase`：创建 schema、维护 `PRAGMA user_version`、保证迁移幂等。
- `BlobStore`：写入、读取、删除 sidecar；支持 orphan cleanup。
- Domain repository：每个业务域独立 repository，例如 `ClipboardRepository`。

首版不引入外部数据库依赖。当前本机已验证 Swift 可 `import SQLite3`，但每次改动仍需通过 Xcode build 复核 App target。

## SQLite 连接策略

每个连接初始化必须执行：

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;
```

- 写入必须走短事务。
- schema 迁移必须幂等，可重复执行。
- 复制、备份、清理数据库时要同时考虑 `sqlite`、`-wal`、`-shm` 和 `Blobs/`。
- v1 先主 App 单写；helper 多进程写入必须另立复测任务。

## Repository 规则

- Repository 返回业务模型或专用 read model，不把 SQL row 泄露到 UI。
- UI 不直接访问 SQLite、sidecar 或 Keychain。
- 新增业务能力时，先定义 repository API、schema、迁移和自动化验证，再接 UI。
- 删除必须是生命周期操作：主表、索引、关联表、sidecar 同步清理。
- 默认查询必须只返回 redacted summary；完整敏感 payload 只能由明确的用例方法读取。
- Action/CLI/agent 默认不得越过 repository 的确认和脱敏边界。
- 生产去重不能只依赖短 hash；短 hash 可展示和诊断，唯一性判断应使用完整 signature 或明确的 occurrence/upsert 规则。

## 安全边界

- 剪贴板、截图、OCR 图片、file URL、RTF、provider 原始响应都按敏感数据处理。
- `redacted index`、`full payload`、`secret` 三类数据必须分级；默认查询、日志、helper stdout、provider audit、agent/CLI 响应只能接触 redacted read model。
- `search_text` 如果包含正文、file path、URL、RTF 文本，也按 payload 等级处理；agent 默认搜索可以命中，但不能回显匹配原文。
- 日志、helper stdout、provider audit、测试报告和 agent 默认响应不得包含完整 payload、图片 base64、secret、Authorization header 或完整文件路径。
- Sidecar 文件名必须随机或内容无关，不含原文件名、URL、标题；只保存相对路径，读取时必须防 path traversal 和 symlink 越界。
- 删除和裁剪必须清理主表、payload 表、FTS、业务关联表和 sidecar；清空大量敏感数据后应执行 WAL checkpoint/truncate 或等价清理。
- 不启用 SQLCipher 不代表忽略安全：v1 以本机私有 Application Support、Keychain secret 隔离、显式删除、脱敏输出和外发确认降低风险；加密作为后续安全增强单独立项。
- 如果后续启用加密，key material 只能进 Keychain，不写入 DB、UserDefaults、仓库或日志。

## 首版落地顺序

1. 建立 SQLite / migration / blob 基础设施和自动化 smoke。
2. 剪贴板 repository 落地，覆盖 schema、插入、检索、删除、策略裁剪和 payload 生命周期。
3. AppState 从“生产事实源”降为视图态和用例编排，剪贴板写入/查询接入 repository。
4. 后续业务域按同一模式新增 repository，不再引入零散 JSON / UserDefaults 业务历史。

## v0 落地状态

- 已新增 `StorageEnvironment`、`SQLiteConnection`、`AppDatabase`、`MigrationRunner`、`BlobStore`。
- 已新增 `ClipboardCapturePolicy` 和 `ClipboardRepository`，覆盖完整签名去重、payload 持久化、FTS5 / LIKE fallback、Pinboard metadata、删除和策略裁剪。
- 已将 AppState 的启动加载、live capture、删除、固定、取消固定、移动 Pinboard、重命名和策略裁剪接入 repository；`@Published` 数组只作为视图缓存。
- 已新增 `p9a_clipboard_repository_storage_smoke.py` 和 `p9b_clipboard_appstate_repository_integration_checks.py`。

## 明确不做

- 不把 SwiftData/Core Data 作为当前生产事实源。
- 不把 JSON debug store 迁成生产主存储。
- 不在 v1 做云同步、跨设备同步、团队共享。
- 不在 v1 默认启用 SQLCipher。
- 不在 v1 让 helper 生产写入共享 store；App Group 和 signing 另行复测。
