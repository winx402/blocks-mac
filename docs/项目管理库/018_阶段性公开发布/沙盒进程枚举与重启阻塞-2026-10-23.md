同一个真实沙盒进程中得到：

- `proc_listallpids`、按 UID 和进程组的 `proc_listpids` 均返回 errno1。
- `sysctl(KERN_PROC_UID)`、`sysctl(KERN_PROC_ALL)` 的 sizing 与实际读取均成功。
- 实际返回长度与 `kinfo_proc` stride 对齐，ALL 列表包含其他 UID，不缩成当前 UID 范围。
- 两种列表均准确包含受控夹具一次；`proc_pidpath` 从沙盒读取其准确路径成功。

这证明候选 API 在当前系统／签名／沙盒下可执行，不证明生产 App 的完整重启或更新已经成功。
实现依据为 Apple 的 [sysctl 手册](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/sysctlbyname.3.html)：
`KERN_PROC_ALL` 返回进程表；进程表在 sizing 与读取之间增长时必须处理缓冲区不足。
不从这台 macOS27 的结果推定全部受支持系统都已通过。

## 修复边界

仅替换进程列表的枚举层：使用公开 `sysctl(KERN_PROC_ALL)`，仍扫描全进程而非只扫当前
Bundle/当前 UID。保留既有路径分类、认证排空、恢复凭据、进程生命周期与退出确认。

读取采用有上限的对齐缓冲区和有限次重新 sizing；拒绝权限错误、异常长度、PID 数据异常
以及缺失当前进程的列表。失败不转换为空列表，不跳过 Broker 安全检查，不用强退、
注销服务、放宽身份校验或关闭沙盒掩盖错误。失败诊断不输出全进程路径或用户数据。

## SwiftUI sheet 与退出的受控因果对照

只读审查确认生产默认 terminator 与菜单退出均为 `NSApp.terminate(nil)`；
已 arm 的 coordinator 分支返回 terminateNow，不重新排空。恢复按钮仍在 SwiftUI sheet 内，
调用后只改阶段，没有结束所属 sheet 的完成屏障。
[Apple 的 terminate 文档](https://developer.apple.com/documentation/appkit/nsapplication/terminate%28_%3A%29)
描述了文档控制器与 delegate 的退出流程，但没有承诺“任意 sheet 一定阻止退出”，因此先做
真实系统对照而非仅凭文档推测修改。

独立 Developer ID／Hardened Sandbox 的微型 SwiftUI App，不访问任何用户数据、文件或 IPC：

- **负向**：在 `.sheet` 内设置 scheduled，禁用交互关闭，再由 `Task { @MainActor in }`
  调用 terminate。18:03:29 日志显示 sheet_present=true、modalWindow=false，调用返回；
  delegate 与 willTerminate 未触发，PID65870仍存活。说明仅检查 modalWindow=nil 不足够。
  初版探针误禁了全部关闭按钮，菜单退出也无效；只对这个已核对路径、无数据测试进程发送
  SIGINT 清理，随后确认退出。**这不是生产 App 正常退出的通过证据。**
- **正向**：按钮设置 presented=false，仅在 `.sheet(onDismiss:)` 回调调用 terminate。
  18:05:28 依次记录 sheet_did_dismiss → delegate_should_terminate(now) → willTerminate，
  PID66136正常退出。
- **异步上下文控制**：onDismiss 中仍通过与负向相同的 `Task { @MainActor in }` 调用，
  18:09:18 同样出现 sheet_present=false → delegate允许 → willTerminate，PID66680正常退出。
  排除了“只是将 Task 改成同步调用”的混杂因素。

临时 App 的 Launch Services 注册定向注销；日常 beta22 未受探针进程清理影响。
