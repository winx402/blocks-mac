本轮最初读取 GitHub 开放 Issue #34–#37，随后纳入新出现的 #38–#42。实机系统为 macOS 26.6.2，当前安装实例是 `app.blocks.dev`、Developer ID 签名且带 Team ID；Issue 中的 macOS 27、“无 Team ID 自签名”和旧 TCC 记录是报告中的历史场景，不作为当前已复现事实。未读取 TCC 数据库，未执行权限重置。

## 无弹窗边界

旧式 file-based Keychain 不可靠支持单次查询的 no-UI 参数，因此使用同步 `SecKeychainGetUserInteractionAllowed` / `Set(false)` / 恢复。全部 Blocks 自有 `SecItem` 入口共用一把递归锁，其他凭据存储的操作不能与此临时作用域交错，且不改变其原有交互策略。不跨 `await`、IPC 或用户交互持锁。无法设置策略则不执行操作；恢复失败返回错误并记录非敏感状态码。

旧条目不改 ACL、不删、不替换。读取的“无此条目”和“无权读取/内容无效”分开处理；后者不能进入自动配对，也不能被当作成功断开。新建条目的窄 ACL 解决首次跨 App 授权；锁定钥匙串、旧签名 ACL 拒绝时安全失败并显示恢复指引。ad-hoc 新构建可完成新配对，但重新编译后的身份变化不能被承诺为永久授权。

参考：[Apple SecAccessCreate](https://developer.apple.com/documentation/security/secaccesscreate(_:_:_:))、[Chromium file-based Keychain no-UI 说明](https://chromium.googlesource.com/chromium/src/crypto/+/refs/heads/main/apple/scoped_keychain_user_interaction_allowed.cc)。

## Beta 2 发布门禁记录

首次 `prepare 0.1.0-beta.2` 正确被 Helper 版本门禁拒绝：请求 build 2，但最终 Info.plist 仍为 build 1。原因是 `xcodebuild -xcconfig Distribution.DirectBeta.xcconfig` 的固定版本值覆盖命令行请求；Beta 1 恰好与固定值一致，未暴露该缺陷。没有上传失败包或覆盖旧版本。需为当前发布生成显式覆盖配置，同时保留基线签名/沙盒/硬化策略，并验证主 App 与 Helper 的有效构建设置后重新构建。

修复为临时 0600 overlay：先包含原发布策略，再覆盖当前请求的版本、build、channel 和固定 HTTPS 更新源；不改源模板、不绕过审核。主 App/Helper 的 Beta 2/build 2 及 stable/build 3 实际 `xcodebuild -showBuildSettings` 校验通过；非法输入、原模板未改变、无版本路径、清理契约通过，release pipeline 自测及 P20 发行门禁通过。重新构建的最终产物仍须签名、公证、staple 和下载验证后才可发布。

## 本轮后续新增 Issue 方案

- #38：主授权操作复用现有引导面板，不再直接发 Helper 系统 prompt。显示真实 Bundle 名称以及“Blocks 与 Helper 是独立权限条目”。不代用户修改系统权限。
- #39：设置检查与采集冷启动采用有上界的渐进等待；冻结请求的外层超时包含启动预算，取消状态贯穿启动、等待和发送前。只在未运行时启动一次，不强制重启正在运行但无响应的进程；用户在检查期间退出也不会被拉起。钥匙串/身份/协议错误不走自动修复；监听 Helper 的启动与退出事件并在设置行生命周期中被动复查。主设置只引导到 Helper 的登录项开关，不自动开启登录项。
- #40：用既有冻结粘贴目标的 PID/windowID 查窗口几何，不读取输入正文。跨屏按面积选屏；丢失目标后指针→主屏回退。保留固定面板与屏幕底边锚定语义。
- #41：原文标题以文本行高布局，反馈控件热区向上覆盖，缩小编辑器间距，不让异步反馈推动输入框。
- #42：NSTextView 标记文本有独立的显示状态通道，隐藏占位但不提交未确认拼音；界面刷新不覆盖进行中的合成。
