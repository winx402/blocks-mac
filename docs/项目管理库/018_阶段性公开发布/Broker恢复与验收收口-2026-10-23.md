## 范围与现场

用户接受的优先级为 #69 → #59/#62 → 其他已补丁 Issue 的安装版验收。
不得以增加日志、重试按钮或测试通过代替原故障闭环；不强停旧 Broker、不绕过认证和排空、
不清空配对、不做全局 BTM/TCC 重置。当前分支为 `codex/broker-upgrade-recovery`，
基线 `b6cae1a`；既有 `AGENTS.md` 本机改动不属于本轮代码改动。

本轮能访问的是 UID501：官方 `/Applications/Blocks.app` build16，无运行中的 Blocks。
#69 原现场是 UID502、beta20 与存活数日的旧 Broker。前者不能证明后者已恢复；
已询问原现场所在 Mac／登录账户，不自动跨账户操作。
对原 UID 的两个特定服务路径作只读检查：GUI 域不存在，user 域返回权限不足；
后者是未知，不能将两者合并声称旧任务已不存在。没有跨账户停止服务。

已公开的最新 Beta 是 beta22。本轮补丁尚未成为新安装包，也未替换日常安装版。

## #69：不再把未知错误说成任务忙碌

- 生命周期连接失败、超时、明确缺失方法、身份验证失败、真实活动请求、恢复冲突、
  系统审批和未确认退出分别分类。只有活动请求证据才显示等待 CLI 任务。
- 保留现有可选 Bool/String RPC 形状，新 Broker 只返回固定版本化错误码。
  新客户端只解码精确 allowlist；旧 Broker 的本地化字符串、空值或未知版本均记作原因未知，
  不猜测 busy，不显示原始远端错误或路径。
- Broker 由其他 token 持有准备状态时，与真实业务请求忙碌分开；同 token 幂等，
  其他 token 不得恢复准入。
- UI／低敏日志保留准确分类，中英日文提示不要求用户凭空结束不存在的 CLI 任务。

**仍未解决的已部署二进制边界：**官方 beta20 没有独立管理 socket，其 lifecycle RPC 同样依赖
发生故障的新连接认证。公开 `SMAppService.unregister` 会终止正在运行的 Agent，
异步完成只是确认终止，不提供业务排空证明。当前 App 本地空闲、没有 CLI PID、
`launchctl print` 快照或禁止未来加载都不足以证明 Broker 全局准入关闭。

原现场下一步应先判明自身签名校验失败还是 peer 失败，保留旧进程／安装。
若可信认证可恢复，走认证 prepare → 关闭准入且空闲 → 注销 → 退出确认；
若所有可信通道均不可恢复，新代码不能追溯加入旧进程。在不放宽安全约束的前提下，
需要用户决定一次会话重建等恢复步骤，不能自动执行，也不能声称该步骤等于软件已经排空旧 Broker。
#69 继续开放，下一次真实升级及原机 CLI 读写／取消仍是验收门槛。

## #59/#62：可认证旧服务的迁移

本次新增的迁移仅适用于新源码版已能连接、身份匹配的 loaded legacy Broker：

1. 先排空当前 App 内入口，严格探测两个当前用户域；明确存在、明确缺失与未知分开。
2. 同用户、登记路径／CDHash 与系统签名 requirement 全部验证后，保存独立迁移 token、Broker 与
   发起 App 的 PID／内核启动时间及阶段，再向同一认证连接发送 prepare。
3. 远端确认全局关闭准入且空闲后，才能异步注销旧服务；双域消失、原进程退出及跨安装进程扫描空
   均确认后完成。开关意图和模块选择保留。
4. `preparing` 阶段的取消只向同一内核 lifetime 的认证实例恢复同 token。
   OS 注销调用前持久化 `unregisterStarted`，此后绝不恢复准入；只有原实例已结束且任务／进程均空时清理，
   或仍可信、同 lifetime、loaded 且 SM enabled 时，同 token 再次认证 prepare 后有界重试注销。
   这覆盖“阶段落盘后、OS 调用前”崩溃，不重新注册旧服务。
5. journal 使用稳定私有跨进程锁、原子发布和期望票据清理；启动仅在原 App owner 明确终结后，
   原子转移到当前 App，不能抢占仍活跃或不可确认的事务。内核 lifetime 的 same／ended／unknown
   三态区分无关 PID 复用与读取失败。断连保留 journal，下一次显式恢复重新认证，不无限复用坏连接。

加载但不可达、身份损坏、忙碌、未知域状态以及旧安装自身尚未具备新迁移代码的首次跳转，
都继续安全失败。当前补丁不证明这几个原报告场景已自动恢复，#59/#62 不关闭。
