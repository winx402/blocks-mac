## 2. ProviderStore / TranslationStore 边界

### ProviderStore

`ProviderStore` 承接 provider catalog、selected provider IDs、route resolution、provider audit、Keychain gate、OpenAI-compatible connection test 和 LLM mock adapter。职责仍偏宽，但都属于 Provider 域：route、secret gate、connection preview / test 和 audit 都共享同一 provider readiness / audit 语义，放在一个 store 内可接受。

边界判断：

- 合理：Provider audit 单事实源为 `ProviderStore.providerAuditEvents`。
- 合理：真实 secret 操作仍经 `ProviderKeychainService`，store 只保留脱敏结果。
- 可后续优化：ProviderStore 596 行，后续如果继续增加 provider 类型，应拆 use case 或 adapter protocol，避免它成为新的 AppState。

### TranslationStore

`TranslationStore` 承接 translation provider / engine selection、preview、mock result、runtime result、translation route 和 runtime gate。它没有直接持有 `ProviderStore`，而是通过闭包写 audit、通过闭包读取 secret，这是本阶段较稳妥的边界。

边界判断：

- 合理：`auditRecorder` 避免 TranslationStore 复制第二套 audit list。
- 合理：`readProviderSecret` 让 TranslationStore 只依赖“按 alias 取一次 secret material”的能力，不需要知道 Keychain service 细节。
- 合理：secret material 只在 ready runtime call 局部作用域内存在，未进入 `@Published` 或 stored property。
- 残余风险：`TranslationStore` 仍有 `providerRouteResolution`，ProviderStore 也有 `providerRouteResolution`，AppState facade 合并读取。此设计符合 Step 3 facade 迁移，但 Step 4 拆 Settings / Translation pane 时应继续收敛 route state 的显示归属。

## 3. AppState Facade

`AppState` 已从 Provider / Translation 业务事实源降级为 facade / coordinator：

- Provider / Translation 相关公开属性仍存在，但转发到 `providerStore` / `translationStore`。
- `providerStore.objectWillChange` 和 `translationStore.objectWillChange` 已绑定到 AppState，保护现有 View 观察链。
- AppState 保留 global `status` 投射、窗口 / 面板 presenter、快捷键、截图、权限、剪贴板 pasteboard 等跨 feature 协调，符合本阶段边界。

保留项可接受：

- `copyTranslationRuntimeOutputToClipboard()` 仍在 AppState，因为它触及 pasteboard，通过 AppState / service 协调比让 TranslationStore 直接访问 `NSPasteboard` 更符合边界。
- route / runtime facade 仍由 AppState 接收 View 层 base URL、model、alias 和 external gate，再转发到 TranslationStore，符合低风险迁移策略。

未发现 AppState 重新成为 Provider / Translation 事实源的问题。P10B 复跑确认 FR-3 的 16 个 forbidden `@Published` 名称均不在 AppState 直接声明。

## 4. Route / Runtime Readiness

`.llmBacked` 契约已从“route unsupported、runtime 可执行”的矛盾状态收敛为一致 gate：

- `ProviderRuntimeGate` 统一校验 base URL、model、alias、external transfer confirmation。
- `ProviderRouter` 对 `.openAICompatible` 和 `.llmBacked` 使用同类 missing configuration / missing secret / confirmation required / ready 语义。
- `TranslationStore.runTranslation()` 先做本地 gate；blocked cases 不读取 Keychain、不访问网络。
- `OpenAITranslationRuntimeService` 继续承担实际 OpenAI-compatible request 构造和 mock transport runner 覆盖。
- LLM-backed metadata 已调整为 `implemented: true`，避免 route ready 与 UI “not implemented” 冲突。

本复审复跑结果：

- P10A PASS：`.llmBacked` ready / missing configuration / missing secret / confirmation required 均覆盖；dedicated API 和 local CLI 仍 unsupported；external HTTP blocked；loopback HTTP ready。
- P5O PASS：local mock、unsupported、gate false、missing alias、missing base URL、missing model、invalid URL、external HTTP 均为 0 Keychain read / 0 network call；loopback HTTP mock case 为 1 / 1；输出不含 raw secret / raw body。

该契约可以支撑 Step 4 继续拆 Settings / Translation pane，但 Step 4 必须继续通过相同 runtime context 传入 base URL、model、alias 和 external gate，不得回退到无 context 的 `ProviderRouteRequest(profile:)`。

## 7. 可转入 Step 4 的残余风险

以下风险不阻断 Step 3 接受，应转入 Step 4 或后续阶段：

- `AppState` 仍保留 Screenshot、Permission、Shortcut、Settings shell、clipboard panel / paste 等跨 feature 协调入口。

- `providerRouteResolution` 分别存在于 ProviderStore 和 TranslationStore，AppState facade 做合并投射；Step 4 拆 Settings / Translation pane 时应明确 UI 使用哪个 route state。
- Clipboard `repositoryUnavailable` 产品化、redacted list + lazy payload 仍未解决。
- helper / App Group / CLI 完整 payload 读取仍是未来能力，不能写成已具备。
- 真实 provider 兼容性、真实 API key 生命周期、真实网络失败形态不是 Step 3 目标；启用真实 provider 前需要单独验收。
- `FloatingPanelSupport.swift` main actor isolation build warnings 不属于 Step 3 改动目标，但建议 UI / AppShell 阶段清理。
