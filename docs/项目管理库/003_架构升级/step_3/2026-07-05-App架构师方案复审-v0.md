## 1. 复审结论

Step 3 PRD 方向成立，可以在补齐必要修改后交给开发。方案聚焦 Provider / Translation 状态拆分和 `.llmBacked` route/runtime 契约统一，没有把 Step 3 误写成整个架构升级项目完成。

## 2. 已要求补强的点

- 明确 `.llmBacked` ready 的 runtime 输入，避免只检查 alias / confirmation 而漏掉 base URL / model readiness。
- 明确 `AICapabilityProfiles.swift` 中 LLM-backed translation metadata 与 route ready 的关系，避免 UI 继续显示 not implemented。
- 明确 AppState facade 必须把现有 View 的 `@AppStorage` base URL、model、alias 和 gate 传入 route / runtime context。
- 明确 `TranslationStore` 不强持有 `ProviderStore`，通过 audit recorder closure 或窄协议写入 provider audit，避免 store 间强耦合和 audit 双事实源。
- 明确 P10A 负责 route contract，runtime gate 继续由 P5O / P5P 覆盖。

上述要求已回写到 Step 3 PRD。

## 3. 主要风险

P0：无方案级阻断。

P1：

- `.llmBacked` route ready 与 runtime readiness 仍需通过 P10A、P5O 和 P5P 共同验证。
- LLM-backed profile metadata 若处理不当，会造成 route ready 与 UI not implemented 标签冲突。
- ProviderStore / TranslationStore 边界若执行不严，会形成 audit 双事实源或 store 间过度耦合。
- AppState status projection 需要在 async runtime、connection test 和 mock result 迁移后保持一致。

P2：

- `SettingsView` 仍是大型聚合体，但可留到 Step 4。
- 旧 `TranslationProviderProfile` 与新 `TranslationEngineProfile` 并存，后续需要收敛。
- 旧 P7 / P9 门禁退役说明需要写清楚，避免测试误判。

## 4. 开发顺序建议

1. 先写或更新 P10A、P5M、P5N，让 `.llmBacked` contract 失败可见。
2. 修改 `ProviderRouting.swift` 和必要的 `AICapabilityProfiles.swift` metadata。
3. 建立 `ProviderStore`，迁移 provider route、Keychain gate、connection test 和 audit。
4. 建立 `TranslationStore`，通过明确注入方式使用 route / audit / secret 能力。
5. 最后改 `AppState` facade 和 objectWillChange 绑定，控制 UI 改动面。
6. 补 P10B / P9B，再跑 PRD 列出的完整回归并记录开发结果。
