评审范围：`docs/项目管理库/003_架构升级/`、`docs/项目管理库/002_剪贴板持久化/数据存储架构规范-v0.md`、`docs/技术知识库/正式AppScaffold架构-v0.md` 与当前 `apps/Blocks/` 代码事实。

## 总体判断

目标分层 `AppShell / Features / Core / Platform Adapters` 成立，迁移顺序以 `Clipboard -> Provider/Translation -> Screenshot/Permissions/Shortcuts/Settings` 起步也成立，但当前方案需要先修订后再进入开发计划。

主要原因不是方向错误，而是方案还没有完全吸收当前代码事实：剪贴板生产 repository 已经落地，`AppState` 和 `SettingsView` 仍是最大聚合点，Provider route 与 Translation runtime 存在契约不一致，CLI/helper/App Group 仍是预留或受控 debug 边界，不能在架构升级中被默认视为已打通。

## 评审意见

### P1：先修订方案中的当前事实基线

建议回写到方案：是，回写到 `2. 当前事实`、`7. 优先迁移顺序`、`8. 迁移策略`。

当前 `数据存储架构规范-v0.md` 已标记 `implemented-v0`，代码中也已有 `StorageEnvironment`、`SQLiteConnection`、`AppDatabase`、`BlobStore`、`ClipboardCapturePolicy`、`ClipboardRepository`。`AppState` 已在启动加载、live capture、pin、move、rename、delete、clear、policy prune 等路径接入 repository。

方案仍把剪贴板描述成“已经有 repository 和 policy 基础，适合验证 feature store 模式”，这个方向对，但不够精确。第一阶段不是再证明 repository 路线，而是把已有 repository 从 `AppState` 的兼容接入中抽成明确的 `ClipboardStore / use case / read model` 边界，并守住现有行为不回归。

行动建议：

- 将“Clipboard 第一批迁移”的目标改为“围绕既有 `ClipboardRepository` 建立 feature store 和用例层”。
- 明确不重建 SQLite 基础设施，不重复发明第二套剪贴板存储。
- 把 `p9a_clipboard_repository_storage_smoke.py` 和 `p9b_clipboard_appstate_repository_integration_checks.py` 作为第一阶段基线门禁，而不是可选补充。

### P1：Provider route 与 Translation runtime 的契约必须先统一

建议回写到方案：是，回写到 `3. 问题判断`、`7.3 第二批迁移：Provider / Translation`、`9. 架构门禁`。

当前 `ProviderRouter.resolve()` 对 `.llmBacked` 返回 `unsupportedCapability`，但 `AppState.runTranslation()` 又把 `selectedTranslationEngine.base.executionMode == .llmBacked` 当作真实 OpenAI-compatible runtime 执行入口，读取 Keychain secret 并调用 `OpenAITranslationRuntimeService.translate()`。

这是架构升级中的关键契约风险：route 层说不支持，runtime 层实际执行。后续拆 `ProviderStore` 和 `TranslationStore` 前必须确定唯一语义，否则拆分后会把这个不一致扩散到两个 feature。

行动建议：

- 先决定 `.llmBacked` 是抽象 engine mode，还是可直接执行的 runtime mode。
- 如果 `.llmBacked` 需要落到 OpenAI-compatible runtime，应在 route request 中显式解析到具体 provider profile，并让 `ProviderRouter` 返回 ready / missingSecret / confirmationRequired，而不是 unsupported。
- 增加门禁：同一 engine/profile 在 route check 和 runtime gate 中的 readiness 结果不能互相矛盾。

### P1：`AppState` repository fallback 不能继续作为隐式生产路径

建议回写到方案：是，回写到 `5.1 AppShell`、`8. 迁移策略`、`9. 架构门禁`。

当前 `AppState.makeClipboardRepository()` 失败时返回 `nil`，live capture 写入失败时会回退到内存路径。这个 fallback 对早期开发友好，但在生产持久化已经落地后，会造成第二事实源：用户以为剪贴板已保存，实际只是内存态；重启后丢失。

行动建议：

- 第一阶段定义 repository 不可用时的产品行为：建议 fail closed，显示降级状态，不静默进入内存生产路径。
- 如果保留内存 fallback，只能标记为 debug/test 兼容路径，并要求 UI 明确提示“持久化不可用”。
- 架构门禁应禁止新增 feature 在 repository 失败时静默写入 UserDefaults、JSON debug store 或内存假生产事实源。

### P1：Clipboard 第一阶段必须先做行为保全清单

建议回写到方案：是，回写到 `7.2 第一批迁移：Clipboard`。具体文件列表和任务拆分可留到 Step 2 实施计划。

Clipboard 适合作为第一批迁移，但不是因为它最简单，而是因为它已经有生产 repository 和较多用户可见路径。拆 `ClipboardStore` 时必须把行为保全列成入口条件，否则容易只搬状态，丢掉面板、粘贴、筛选或 debug gate。

第一阶段开发建议：

- 新建 `ClipboardStore`，持有剪贴板 view state：records、filter、pinboards、pinned metadata、selected floating record、paste attempt、recorder runtime state。
- 新建 `ClipboardUseCases` 或等价薄用例层，承接 load、ingest live capture、filter/search、pin、move、rename、delete、clear unpinned、apply policy、copy plain text、paste/auto-paste。
- `AppState` 保留 facade 兼容现有 view 调用，但内部转发到 `ClipboardStore`；最终只保留打开面板、全局 status、权限失败后的跨域协调。
- 暂不大规模搬 SwiftUI 文件；先确保 `ClipboardHistoryView`、floating panel、Settings clipboard 区域仍可工作。
- 迁移完成前后必须跑 repository smoke、AppState integration、clipboard panel/product/paste 相关门禁和 App Debug build。

### P1：Settings 不能完全排到最后处理

建议回写到方案：是，回写到 `7.4 第三批迁移` 和 `8. 迁移策略`。

迁移顺序把 `Settings` 放在第三批是合理的，但 `SettingsView` 当前已经直接持有大量 `@AppStorage`：provider、clipboard policy、agent/CLI、translation runtime、shortcut、language 等，并直接调用 `AppState` 的 provider route、clipboard policy、secret gate 等动作。

如果 Provider/Translation 第二批迁移时不同时定义 settings 边界，新的 `ProviderStore` / `TranslationStore` 会继续被 `SettingsView` 以全局 `AppState` 方式间接驱动，拆分收益会被抵消。

行动建议：

- 方案中增加“Settings shell 早建，settings panes 随 feature 迁移”的规则。
- Clipboard 第一阶段至少拆出 clipboard settings pane 的依赖边界，允许它使用 `ClipboardStore` / preference adapter，而不是继续把 policy 用例写回 `AppState`。
- Provider/Translation 第二阶段同步拆 provider settings pane 和 translation settings pane；剩余视觉 shell 可留到第三批。

### P1：BlocksCore 的职责需要在方案中直接定案

建议回写到方案：是，回写到 `5.4 Repository`、`5.5 Platform Adapter`、`12. 待决策问题`。

方案把“`BlocksCore` 是否继续承载 production repository，还是 protocol 留 Core、实现放 App / Infrastructure”列为待决策，但当前实现已经把 `AppDatabase`、`SQLiteConnection`、`BlobStore`、`ClipboardRepository` 放进 `BlocksCore`，CLI 和 helper 也 import `BlocksCore`。

这不一定错。当前 Core 只依赖 Foundation / SQLite3 / CryptoKit 这类非 UI 依赖，仍符合共享核心方向。但方案必须把这个作为当前架构事实，而不是开放问题。

行动建议：

- 在 v1 方案中明确：首版接受 concrete repository 位于 `BlocksCore`，但 Core 禁止 import SwiftUI、AppKit、Security、URLSession 或任何 UI/localization 运行时。
- 如果后续要把实现挪到 Infrastructure，应单独立迁移任务，不应夹在 Clipboard feature store 拆分里。
- 增加 Core import 门禁，防止 provider runtime、Keychain 或 AppKit adapter 滑入 `BlocksCore`。

### P1：默认列表读取不应继续等同完整 payload 预载

建议回写到方案：是，回写到 `5.4 Repository`、`7.2 第一批迁移`、`9. 架构门禁`。

数据存储规范要求默认查询返回 redacted summary，完整敏感 payload 只能由明确用例读取。当前 `AppState.loadClipboardRepositoryState()` 加载最近记录后，会对每条 record 调 `readPayload()` 并放入 `clipboardPayloads`。这保住了现有 UI/paste 行为，但不符合长期分层目标，也会放大启动性能和敏感数据驻留面。

行动建议：

- Clipboard 第一阶段定义 `ClipboardListItemReadModel`：列表和搜索默认只带 redacted summary、类型、来源候选、时间、pin 状态和 preview 所需的低风险字段。
- 完整 payload 改为 lazy read：paste、hover detail、copy plain text、translation preview 等明确用户动作再读取。
- 先不要一次性改所有 UI；可以保留 facade，但新增门禁禁止新列表 API 默认批量读取完整 payload。

### P2：Repository 拆分可以留到实施计划，但接口边界要先写入方案

建议回写到方案：部分回写。原则回写到方案；具体文件拆分留 Step 2 实施计划。

`ClipboardRepository.swift` 当前约 790 行，已经同时包含 insert、query、payload 编解码、policy prune、pinboard、FTS、sidecar 删除。它作为 v0 可接受，但继续扩展会变成新的聚合点。

行动建议：

- 方案写明 repository 对外 API 要按 read/write/policy/payload 生命周期分组。
- 具体是否拆成 `ClipboardRepository+Query`、`ClipboardPayloadStore`、`ClipboardPolicyPruner` 等，留到 Step 2 实施计划，不作为 Step 1 阻塞项。

### P2：helper / App Group / CLI 只能作为未来边界，不能写成当前能力

建议回写到方案：是，回写到 `3. 问题判断`、`5.5 Platform Adapter`、`10. 不做事项`。

当前 App 和 helper entitlements 都没有 App Group；helper 仍是受控 debug / preflight / redacted watch 路径；CLI 目前只注册和执行 `blocks.screenshot.capture` dry-run。虽然目标架构写 `CLI / Helper -> Core / explicitly allowed adapters` 是正确方向，但方案应明确当前不做生产 helper 写库、不做 CLI 读取完整剪贴板、不做 App Group 共享容器。

行动建议：

- 在架构升级期保持 helper debug/预留状态；长期 background recorder 单独立项。
- CLI 迁移只允许基于 action schema 和 redacted repository read model 设计，不允许绕过确认读取 payload。
- App Group 只能通过 `StorageEnvironment` 切换，并且必须在 signing/provisioning 复测后进入实施。

### P2：验证门禁需要区分结构门禁和真实交互验收

建议回写到方案：部分回写。门禁分类回写方案；具体命令留 Step 2 实施计划。

方案已意识到静态门禁不足，但第一阶段需要更明确地把“结构门禁”和“实物门禁”拆开。

行动建议：

- 结构门禁：Core import、feature view 禁止直接 SQLite/Keychain/NSPasteboard/URLSession、AppState 新增业务逻辑限制、repository smoke、schema validation。
- 行为门禁：剪贴板 live capture、重启后持久化、pin/move/rename/delete、policy prune、paste/auto-paste、floating panel 选择和关闭后 filter 行为。
- UI 实物门禁：panel、hover、resize、权限辅助、自动粘贴相关改动必须有截图/录屏或可复现 UI harness 证据。

## 对五个问题的直接回答

1. 目标分层是否合理：合理。建议保留 `AppShell / Features / Core / Platform Adapters`，但 `Platform` 要明确是 adapter 实现层，不应被 Feature Store 直接绕过。
2. 迁移顺序是否合理：大方向合理。Clipboard 先行正确；Provider/Translation 第二批正确；但 Settings shell 和对应 settings pane 要随 feature 迁移，不能完全等到最后。
3. 是否漏掉关键架构风险：漏掉或低估了 route/runtime 不一致、repository failure 静默 fallback、默认 payload 预载、BlocksCore concrete repository 既成事实、helper/CLI 当前能力边界。
4. 哪些内容先修订：当前事实基线、Provider/Translation 契约、AppState 降级策略、Settings 迁移方式、Core import 边界、helper/CLI 非目标。Repository 内部拆文件、行数上限和具体目录搬迁可放 Step 2 实施计划。
5. 第一阶段开发应该做什么：围绕已有 `ClipboardRepository` 建 `ClipboardStore` 和用例层，通过 AppState facade 保持旧 UI 行为，逐步把 clipboard 状态和动作迁出 AppState，同时用现有 p9/P7/P8 门禁和 App build 防止功能丢失。
