# 架构升级方案 v0

状态：proposed
最后审阅：2026-07-05
来源级别：architecture proposal

本文是积木工具架构升级项目的 Step 1 方案。方案已由 App 架构师评审，结论为 `approve-with-changes`；本文已回写评审中有行动价值的意见。后续开发以 Step 2 实施计划为准。

## 1. 背景

项目已经经历多轮快速开发：正式 App scaffold、截图纵切、翻译浮层、provider gate、权限设置、剪贴板面板、剪贴板持久化和 reset fixture 清理都已进入主工程。功能增长速度快于架构收敛速度，导致部分代码已经出现“能跑但难演进”的迹象。

本轮架构升级的目标不是把所有代码重写一遍，而是重新确定合理的长期结构，让后续功能继续扩展时有清晰边界。

## 2. 当前事实

截至 2026-07-05 的本地代码盘点：

- `apps/Blocks/BlocksApp/Stores/AppState.swift` 约 2513 行，承载截图、翻译、provider、权限、快捷键、剪贴板、状态栏和部分持久化编排。
- `apps/Blocks/BlocksApp/Views/SettingsView.swift` 约 2260 行，承担多个设置域的页面、表单和交互。
- `docs/项目管理库/002_剪贴板持久化/数据存储架构规范-v0.md` 已标记 `implemented-v0`；代码中已有 `StorageEnvironment`、`SQLiteConnection`、`AppDatabase`、`BlobStore`、`ClipboardCapturePolicy`、`ClipboardRepository`。
- `apps/Blocks/BlocksCore/ClipboardRepository.swift` 约 790 行，已经接入生产级 SQLite repository；`AppState` 已在启动加载、live capture、pin、move、rename、delete、clear、policy prune 等路径接入 repository。
- `apps/Blocks/BlocksApp/Services/` 下既有 AppKit presenter、runtime service、权限辅助、Keychain、provider connection、shortcut controller，也有业务用例协调，`Service` 命名承载过宽。
- 现有目录大致是 `App / Models / Services / Stores / Support / Views / BlocksCore`，但不是按业务 feature 或依赖方向组织。
- `ProviderRouter.resolve()` 当前对 `.llmBacked` 返回 `unsupportedCapability`，但 `AppState.runTranslation()` 会对 `.llmBacked` 走 OpenAI-compatible 翻译 runtime；这是 route/runtime 契约不一致。
- 主 App 和 helper 当前没有 App Group entitlement；helper 仍是受控 debug / preflight / redacted watch 路径，CLI 当前主要是 action core 的受控入口，不能视为已打通生产共享数据路径。

## 3. 问题判断

### 3.1 AppState 过宽

`AppState` 现在是全局状态容器、业务用例入口、权限协调器、provider 路由入口、剪贴板 store facade、截图调度器和状态栏更新器的混合体。

风险：

- 任一 feature 改动都可能触碰同一个核心文件。
- 单元测试难以只测试某个业务域。
- 子 agent 并行开发容易冲突。
- 新功能容易继续塞进 `AppState`，形成更强耦合。

### 3.2 View 文件承担过多产品域

`SettingsView` 和部分 feature view 仍承载较多状态组合、表单逻辑和用户动作。SwiftUI View 应该偏渲染和局部交互，而不是承接跨域业务规则。

风险：

- 视觉调整和业务规则修改互相影响。
- UI 回归难定位。
- 组件复用困难。

### 3.3 Service / Support 命名不足以表达边界

当前 `Services` 同时包含：

- AppKit window / panel presenter。
- pasteboard / screenshot / permission 等系统 adapter。
- provider runtime。
- Keychain 访问。
- 业务用例协调。

风险：

- 后续开发者无法从目录判断依赖方向。
- 平台 API、业务 use case、存储和 UI 编排混在同层。

### 3.4 Core 层职责需要继续收敛

`BlocksCore` 已经放入 action core、storage、SQLite、clipboard foundation 和 repository。这是正确方向，但需要继续规定哪些类型可以进入 Core，哪些必须留在 App。

风险：

- 如果 Core 开始依赖 SwiftUI/AppKit/用户界面语义，就会破坏 CLI/helper 共享能力。
- 如果 App 直接绕过 Core 的 repository / action validation，会出现多事实源。

### 3.5 验证门禁偏静态

项目已有大量 Python verification 脚本，能守住不少结构和字符串门禁。但窗口、hover、resize、权限、外发确认和自动粘贴类问题，静态门禁不能替代真实交互验收。

风险：

- “脚本通过”不等于用户路径可用。
- AppKit/SwiftUI 层叠和焦点问题需要实物证据。

### 3.6 Provider route 与 runtime 契约不一致

`ProviderRouter` 对 `.llmBacked` 返回 unsupported，但翻译 runtime 已经把 `.llmBacked` 作为可执行入口。后续拆 `ProviderStore` 和 `TranslationStore` 前必须统一语义，否则会把不一致扩散到两个 feature。

### 3.7 Repository failure 不能静默降级成第二事实源

`AppState.makeClipboardRepository()` 失败时当前可返回 `nil`，相关路径存在内存 fallback。生产持久化落地后，静默 fallback 会让用户以为内容已保存，实际重启丢失。架构升级必须定义 fail-closed 或明确 UI 降级提示。

### 3.8 默认列表读取不应长期等同完整 payload 预载

当前为了保住 UI 行为，启动加载最近 records 后会读取 payload 并放入 `clipboardPayloads`。这对 v0 可接受，但长期不符合“默认查询返回 redacted read model，完整 payload 只由明确用例读取”的边界。

## 4. 目标架构

目标结构按依赖方向组织：

```text
AppShell
  - App lifecycle
  - global navigation / selected section
  - main window / menu bar / command routing
  - global status presentation

Features
  Clipboard
    - ClipboardStore
    - ClipboardUseCases
    - ClipboardViews
    - ClipboardPresenters
    - ClipboardPlatformAdapters
  Screenshot
  Translation
  Provider
  Permissions
  Shortcuts
  Settings

Core
  Domain models
  Action envelope / validation
  Storage infrastructure
  Repository interfaces and production repositories
  Redacted read models

Platform
  AppKit / SwiftUI bridge
  NSPasteboard
  ScreenCaptureKit
  Accessibility
  Keychain
  SMAppService / helper boundary
```

依赖方向：

```text
Views -> Feature Store / ViewModel -> UseCases -> Repository / Platform Adapter -> System or Storage
AppShell -> Feature Stores
CLI / Helper -> Core / explicitly allowed adapters
Core -> Foundation / SQLite3 only; no SwiftUI / AppKit
```

## 5. 分层规则

### 5.1 AppShell

职责：

- 管理 App 生命周期、菜单栏、主窗口入口、全局 section、全局状态展示。
- 组装 feature stores 和跨 feature 用例。
- 承接真正跨域的协调，例如“权限失败后打开设置页”。

不做：

- 不保存某个 feature 的业务列表。
- 不直接操作 SQLite、Keychain、pasteboard、provider network。
- 不承接某个 feature 内部的 pin、delete、rename、filter、search 等用例。
- 不在 repository 不可用时静默创建内存假生产事实源；必须 fail closed 或显示降级状态。

### 5.2 Feature Store

每个主要业务域建立自己的 `@MainActor ObservableObject` store。首轮保守沿用 `ObservableObject`，不强行切到新的 Observation 框架，避免把架构升级和 UI 状态框架迁移绑死。

职责：

- 持有该 feature 的 view state。
- 暴露用户动作方法。
- 调用 use case / repository / platform adapter。
- 生成 UI 需要的 read model。

不做：

- 不直接写日志中的敏感 payload。
- 不跨越其他 feature 的内部 store。
- 不把系统 API 调用散落到 SwiftUI View。

### 5.3 Use Case

Use case 负责业务动作编排，例如：

- `CaptureScreenshotUseCase`
- `PasteClipboardRecordUseCase`
- `RunTranslationUseCase`
- `SaveProviderSecretUseCase`
- `RefreshPermissionStateUseCase`

职责：

- 把用户动作转成可测试流程。
- 明确权限、确认、审计、存储和错误映射。
- 依赖 protocol，而不是直接依赖 AppKit / Keychain / network。

### 5.4 Repository

Repository 是业务数据事实源。当前剪贴板持久化已经证明这条路线可行。

规则：

- 首版接受 concrete repository 位于 `BlocksCore`，因为当前实现已在 Core 内落地；后续若迁到 Infrastructure，需要单独立项。
- `BlocksCore` 中的 repository 和 storage infrastructure 只能依赖 Foundation、SQLite3、CryptoKit 等非 UI 依赖。
- 业务历史、检索、审计、hook draft、截图历史等进入 repository。
- Repository 不返回 SQLite row；只返回 domain model 或 read model。
- Repository API 应按 read、write、policy、payload lifecycle 分组，避免继续膨胀成新的聚合点。
- 删除是生命周期操作，必须清 DB、索引、sidecar 和关联表。
- 默认查询返回 redacted read model；完整 payload 只能通过明确用例读取。

### 5.5 Platform Adapter

所有系统 API 进入 adapter：

- `PasteboardClient`
- `ScreenCaptureClient`
- `AccessibilityClient`
- `KeychainClient`
- `ShortcutRegistrar`
- `WorkspaceClient`
- `ProviderHTTPClient`

规则：

- Adapter 可依赖 AppKit、Security、ApplicationServices、ScreenCaptureKit。
- Feature Store 和 Use Case 依赖 adapter protocol。
- 测试使用 fake adapter。
- Helper、CLI、App Group 只能通过显式允许的 adapter / action core / storage environment 接入；当前不把 helper 生产写库、CLI 读取完整剪贴板、App Group 共享容器视为已具备能力。

### 5.6 View

SwiftUI View 职责：

- 渲染 store 提供的状态。
- 发送用户动作。
- 管理非常局部的 UI state，例如 hover、focus、临时展开。

不做：

- 不直接访问 repository。
- 不直接访问 Keychain、pasteboard、network。
- 不把业务规则放进大型 `body` 或多层私有方法。

## 7. 优先迁移顺序

### 7.1 先做架构基础，不先搬代码

Step 2 应先建立：

- 目录契约。
- feature store 命名规则。
- platform adapter protocol。
- AppState 瘦身目标。
- verification 脚本的结构门禁。

### 7.2 第一批迁移：Clipboard

理由：

- 剪贴板已经有生产 repository 和 policy 基础，第一阶段不再重建 SQLite / blob / migration 基础设施。
- 目前 `AppState` 中仍有较多剪贴板用例，适合验证 feature store 模式。
- 剪贴板涉及敏感数据，能同时检验 redacted read model、payload 读取、UI 交互和删除生命周期。

目标：

- 新增 `ClipboardStore`。
- 围绕既有 `ClipboardRepository` 建立 feature store 和薄用例层。
- 将 load、ingest live capture、filter/search、pin、move、rename、delete、clear unpinned、apply policy、copy plain text、paste/auto-paste 从 `AppState` 迁出或先通过 facade 转发。
- `AppState` 只保留打开面板、全局 status、权限失败后的跨域协调和兼容 facade。
- 先保住现有 UI 行为，不大规模搬 SwiftUI 文件。

行为保全清单：

- live capture 仍能写入生产 repository 并刷新面板。
- 重启后最近记录、pinboards 和 pinned metadata 仍能恢复。
- 筛选、搜索、固定、移动分组、重命名、删除、清空未固定、策略裁剪仍可用。
- copy plain text、paste / auto-paste、内部 pasteboard 写入抑制仍可用。
- bottom / side 面板、hover detail、filter clear、item font、card width、bottom height 不回归。
- debug recorder / preflight / import / reset debug store 路径不被误删或改成生产事实源。

### 7.3 第二批迁移：Provider / Translation

理由：

- provider、Keychain、外发确认、翻译 runtime 已经跨越 UI、网络、审计和安全边界。
- 这部分需要明确 use case、adapter 和 audit。

目标：

- `ProviderStore` 管 provider catalog、route、connection test、secret gate。
- `TranslationStore` 管输入、目标语言、engine route、runtime result。
- 外发确认和 audit 形成可测试 use case。
- 先统一 `.llmBacked` 的 route/runtime 语义：如果它落到 OpenAI-compatible runtime，route check 必须返回 ready / missingSecret / confirmationRequired，而不是 unsupported。
- 增加门禁，保证同一 engine/profile 在 route check 和 runtime gate 中的 readiness 不互相矛盾。

### 7.4 第三批迁移：Screenshot / Permissions / Shortcuts / Settings

目标：

- 截图能力拆成 capture use case、result presenter、AI action routing。
- 权限拆成 permission store 和 platform adapter。
- 快捷键拆成 shortcut store 和 registrar adapter。
- Settings shell 尽早建立；各 settings pane 随 feature 迁移，而不是完全排到最后。
- Clipboard 第一阶段至少明确 clipboard settings pane 的依赖边界，Provider / Translation 第二阶段同步拆 provider settings pane 和 translation settings pane。

## 8. 迁移策略

采用“分阶段替换事实源”，不是纯文件搬家。

1. 先为目标 feature 建立 store / adapter / use case。
2. 保留 `AppState` 的旧方法作为 facade，内部转发到新 store。
3. 更新 View 逐步依赖 feature store。
4. 补自动化门禁，禁止新代码继续把该 feature 逻辑写回 `AppState`。
5. 验证通过后删除 facade 中已无调用的方法。
6. 如果 repository 不可用，必须 fail closed 或显示降级状态，不允许静默写入内存、UserDefaults 或 JSON debug store 冒充生产事实源。
7. 默认列表 API 逐步转向 redacted read model；完整 payload 只允许 paste、hover detail、copy、translation preview 等明确用例读取。

这允许内部接口破坏和重组，但每个阶段必须证明用户可见行为不回归。

## 9. 架构门禁

后续开发前应新增或更新以下验证：

- `AppState` 行数和职责门禁：禁止新增剪贴板/翻译/provider/screenshot 大段业务逻辑。
- Feature 目录依赖门禁：`Features/*/Views` 不得直接引用 SQLite、Keychain、URLSession、NSPasteboard。
- Core 依赖门禁：`BlocksCore` 不得 import SwiftUI / AppKit / Security UI。
- Repository 门禁：业务历史不得进入 UserDefaults 或 JSON debug store。
- Repository fallback 门禁：生产 repository 失败不得静默进入内存事实源。
- Provider contract 门禁：同一 engine/profile 的 route check 和 runtime gate readiness 不得互相矛盾。
- Clipboard payload 门禁：新列表/read model API 不得默认批量读取完整 payload。
- Privacy 门禁：日志、helper stdout、provider audit、agent/CLI 默认输出不得包含完整 payload、图片 base64、secret、Authorization header 或完整文件路径。
- UI 实物门禁：涉及 panel、hover、resize、权限、自动粘贴的改动必须有截图、录屏或可复现 UI harness 证据。
- Build 门禁：App Debug build、CLI Debug build、现有 P4/P7/P8/P9 相关门禁按影响范围执行。

门禁分类：

- 结构门禁：Core import、feature view 禁止直接 SQLite/Keychain/NSPasteboard/URLSession、AppState 新增业务逻辑限制、repository smoke、schema validation。
- 行为门禁：剪贴板 live capture、重启持久化、pin/move/rename/delete、policy prune、paste/auto-paste、floating panel 选择和关闭后 filter 行为。
- UI 实物门禁：panel、hover、resize、权限辅助、自动粘贴相关改动必须有截图/录屏或可复现 UI harness 证据。

## 10. 不做事项

本项目 Step 1 不做：

- 不重写 App。
- 不替换 SwiftUI。
- 不改业务代码。
- 不引入新的数据库或大型架构框架。
- 不把已有验证脚本整体推倒重写。
- 不为了目录好看做无行为验收的批量搬文件。
- 不重建第二套剪贴板 SQLite / blob / migration 基础设施。

后续实施阶段也默认不做：

- 不默认启用 SQLCipher。
- 不默认做云同步或跨设备同步。
- 不把 helper 升级为可执行任意自动化或生产写库的后台进程。
- 不让 agent/CLI 绕过确认读取敏感 payload。
- 不把 App Group 共享容器写成当前已具备能力；必须等 signing/provisioning 复测后单独实施。

## 11. 子 agent 分工建议

进入评审阶段后建议：

- App 架构师：评审目标分层、依赖方向、AppState 迁移策略和 Core 边界。
- 测试/质量：评审门禁设计，补充哪些必须自动化、哪些必须实物验收。
- 安全合规顾问：评审敏感数据、Keychain、provider 外发、日志、agent/CLI 默认读取边界。
- 执行助理：整理依赖图、文件行数趋势、历史文档链接和验证命令。
- 开发：只在方案确认后按单 feature / 单阶段承接实现。

## 12. 待决策问题

1. Feature Store 是否统一保留 `ObservableObject`，还是在 macOS 14+ 范围内逐步采用 Observation。
2. Settings shell 的最小切入形态：先建空 shell，还是随 Clipboard settings pane 首次迁移。
3. Helper 是否在架构升级期保持 debug/预留状态，还是单独立项做长期 background recorder。
4. 迁移阶段是否设定硬性文件行数上限，例如核心 store 不超过 500 行、单个 View 不超过 400 行；该限制应作为提醒还是阻断门禁。
