## 总体判断

Step 4B PRD 的切片边界基本合理：只迁移 PermissionStore，不扩大到 ScreenshotStore、ShortcutStore、Settings shell、真实 provider、真实 OCR、helper/App Group/CLI 完整 payload，也没有要求触发真实 TCC 权限请求。PRD 已把 AppState facade、objectWillChange 桥接、Clipboard retry 边界、权限辅助入口和 forbidden token 作为明确验收点，方向符合 Step 3 后续拆分的质量要求。

结论为 `approve-with-changes`，原因不是方案方向错误，而是进入开发前应回写两类门禁细化，避免“看似执行了旧门禁、实际没有覆盖当前切片”的风险。

## P11B 方案评估

P11B 作为 Step 4B 的主自动化门禁是必要且合理的。PRD 中列出的检查项覆盖了测试/质量关心的核心边界：

- `PermissionStore.swift` 存在并进入 Blocks target。
- `PermissionStore` 为主线程可观察状态源。
- `AppState` 持有 `PermissionStore`，并桥接 `objectWillChange`。
- `AppState` 不再直接声明 `@Published var permissionSnapshot`，只保留 computed facade。
- `refreshPermissionState` facade 仍能触发 Clipboard pending paste retry，但 PermissionStore 自身不拥有 Clipboard retry 逻辑。
- 权限辅助、打开设置、Finder、Restart 等 facade API 对旧调用方保持可用。
- 新权限文件禁止出现外部调用、凭据、剪贴板、事件注入、provider/runtime 等越界 token。
- `SettingsView`、`ScreenshotHomeView` 不新增直接权限 API 调用。

需要回写的 P1 级门禁细化：

1. P11B 必须 fail closed：脚本文件缺失、target membership 无法解析、检查路径不存在、只匹配到旧脚本名或旧事实源时，均应失败，而不是跳过。
2. P11B 输出应包含检查到的关键文件路径和命中/未命中的规则摘要，便于验收记录证明它检查的是 Step 4B 当前事实源。
3. P11B 的脚本命名应在 Step 4B PRD、开发任务、验收记录中统一为 `tools/verification/p11b_permission_store_checks.py`。预初始化文档里旧的 P11B 泛化命名不能作为 Step 4B 的执行入口。

## 实物验收证据

PRD 要求的实物验收路径可操作，最低应覆盖：

- Settings 中权限诊断状态仍可见，Screen Recording / Accessibility 状态不被迁移误导。
- Refresh 权限状态不会伪造授权，也不会绕开 PermissionStateService。
- Request Screen Recording / Request Accessibility 入口只由用户显式点击触发。
- Show in Finder 只由用户显式点击触发。
- Restart 只由用户显式点击触发；如果环境不允许验证，必须记录为未覆盖。
- 截图权限缺失路径不回归，不能因为 PermissionStore 迁移导致错误提示、按钮或辅助引导消失。
- Clipboard pending paste retry 仍由 AppState facade 或闭包边界触发，不能迁入 PermissionStore。

TCC 环境限制必须显式记录为未覆盖或环境依赖：

- 当前机器已有 Screen Recording / Accessibility 授权时，无法证明首次授权弹窗链路。
- 未重置 TCC 数据库时，无法证明 denied、revoked、fresh install 的完整路径。
- 不应为了验收主动触发真实权限请求；只能记录用户显式操作路径或由已有环境状态验证展示逻辑。
- 如果签名、bundle id、Info.plist、sandbox entitlement 未触及，P7H 可不作为阻断门禁；如果触及，则必须升级为阻断门禁。

实物证据不得包含敏感内容、真实凭据、完整用户路径中可识别私密内容，截图应只保留必要 UI 区域。

## 阻断项、必改项、建议项、待验证项

P0 阻断项：未发现。

P1 必改项：

1. 统一 Step 4B P11B 执行入口为 `tools/verification/p11b_permission_store_checks.py`，并要求 fail closed。
2. 对阻断矩阵中的旧 P7/P10 脚本补充当前事实源要求：若仍依赖旧验收记录、旧路径或旧 AppState 直接字段字符串，必须更新后才能作为 Step 4B 阻断门禁；否则只能作为 baseline 辅助证据。

P2 建议项：

1. 在验收记录模板中单列“未触发真实 TCC 权限请求”与“已授权/未授权环境状态”，避免把环境状态误写成产品能力。
2. P11B 输出建议包含规则编号，方便后续 Step 4C/4D 复用相同检查框架。
3. 将 P10B 在矩阵中标注为 Step 3 regression，而非 PermissionStore acceptance。

待验证项：

1. 本轮按主会话要求停止扩展抽查，未逐行读取 P7/P10/P11 相关脚本实现。
2. 本轮未读取 `AppState.swift`、`SettingsView.swift`、`PermissionAssistPanelPresenter.swift` 当前代码，因此不判断现有实现是否已满足 PRD。
3. TCC 授权、撤销、首次请求、重启后状态刷新只能在实现后结合实际环境记录。

## 最终建议

可进入开发准备，但需先把上述 P1 必改项回写到开发任务或 PRD 验收段落。完成回写后，Step 4B 的测试/质量门禁强度足以支撑单切片开发；实现完成后仍需独立验收，不应由开发记录替代测试/质量验收结论。
