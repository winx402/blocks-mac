- 没有发现 P0；但存在 P1 级文档歧义和门禁职责不足，关闭前不宜派开发。

## 3. P0 / P1 / P2

### P0

无。

没有发现 PRD 方向必须整体拒绝的问题。

### P1

P1-1：Step 4C 接受范围与 Clipboard hardening 可拆 Step 4D 的口径冲突。

PRD 第 4 节允许 Clipboard hardening 在高风险时拆到 Step 4D，不阻断 Screenshot / Shortcut / Settings shell 收口；但第 9 节又要求 Step 4C 可接受必须四个子批次均完成。这会让开发、验收和最终接受无法判断：Clipboard hardening 被拆出时，Step 4C 是可关闭、部分关闭，还是必须继续阻塞。

必须回写为二选一：

- 方案 A：Step 4C 必须完成四个子批次，Clipboard hardening 不再作为可拆 Step 4D 的条件项。
- 方案 B：Step 4C core scope 是 ScreenshotStore、ShortcutStore、Settings shell；Clipboard hardening 是 conditional 4C-4，若触发拆分条件则进入 Step 4D，Step 4C 接受标准同步改为前三个子批次加明确的 Step 4D handoff record。

我建议采用方案 B，因为 Clipboard hardening 涉及完整 payload read model 和敏感数据边界，风险类型明显不同。

P1-2：P11A/C/D/E 只有统一 fail-closed 原则，缺少每个门禁的具体职责矩阵。

Step 4B 的 P11B 已经证明专项门禁需要明确到 target membership、facade、objectWillChange、forbidden token、旧事实源、用户触发路径等规则。Step 4C 当前只列脚本名和通用 fail-closed 要求，不足以让开发实现和测试/质量判断脚本是否覆盖边界。

必须在 PRD 中补每个脚本的最低检查清单：

- P11A ScreenshotStore：文件和 target membership；`AppState` 不再直接持有 screenshot facts；保留 computed facade；权限输入只通过 Permission facade / readable；无图片上传、OCR、provider call、base64 / image log；result presenter 走窄接口；Screenshot Result 行为入口不丢失。
- P11C ShortcutStore：文件和 target membership；`AppState` 不再直接持有 `shortcutRegistrationResults`；快捷键动作只通过 AppShell 注入闭包；不持有完整 `AppState`；无 shell / AppleScript / 未声明 CGEvent 自动化；录制状态一次只录一个命令。
- P11D Settings shell：Settings feature 文件和 target membership；`SettingsView` 退化为 wrapper / shell，不继续承载所有 pane 主体；所有 `SettingsViewMode` 映射明确；setting key 不改名；pane local state 不进入全局 store；pane 不新增敏感 API token。
- P11E Clipboard hardening：repository unavailable 有用户可见状态；默认列表 / 面板渲染不读取完整 payload；完整 payload 只在明确 copy / paste / hover detail / translation preview 等用例读取；验证输出和日志不包含剪贴板正文；CLI 默认不读取完整 payload。

P1-3：Settings shell 必增 pane 列表与 mode 列表不一致。

PRD 要求保留 `hooks`、`dataAudit` 等 `SettingsViewMode` 语义，但必须新增文件列表里没有 `HooksSettingsPane.swift` 和 `DataAuditSettingsPane.swift`，也没有说明这两个 mode 映射到哪个 pane。这个缺口会让实现阶段在“保留兼容 wrapper”和“拆 pane 主体”之间产生歧义。

必须回写其中一种：

- 新增 `HooksSettingsPane.swift` 和 `DataAuditSettingsPane.swift`；
- 或明确 `hooks` / `dataAudit` 由 `AgentCLISettingsPane`、`GeneralSettingsPane` 或其他具体 pane 承载，并要求 P11D 检查 mode mapping。

### P2

- PRD 应进一步说明 `ScreenshotStore` 与全局 `AppState.status` 的关系：建议 ScreenshotStore 产出 `AppStatus` / event，由 AppState 作为 window-level coordinator 发布，避免 screenshot store 变成全局 status owner。
- `ScreenshotStore` 的 AI route preview 应只依赖 route resolver protocol / closure，不直接持有 `ProviderStore`，避免 screenshot feature 与 provider feature 出现 store mesh。
- `PermissionSystemActions` 在 Step 4B 已作为 adapter，但 Step 4C 如果新增 Screenshot / Shortcut platform adapter，应保持同类命名和白名单策略，避免平台动作散落到 store / pane。
- Settings shell 拆分容易变成大规模机械搬文件；建议每个 pane 拆分都绑定至少一个可验证行为或 mode routing gate，不做无验收目标的纯重排。
- Clipboard hardening 如果留在 Step 4C，建议在 Settings shell 验收后设独立 go/no-go 检查点，再开始改 read model。

## 4. 四个切片是否可放入同一个 Step 4C

可以，但只能作为阶段收口 PRD，而不是单个开发任务。

可接受理由：

- 四个切片都服务于 Step 4 的同一目标：把 Step 3 / 4B 之后仍堆在 `AppState` 和 `SettingsView` 的 feature 事实源收口。
- PRD 已把每个切片列为独立子批次，并要求独立门禁、开发回调和验收记录。
- 如果 P1-1 的接受范围冲突被修正，统一 Step 4C 可以减少阶段文档分散，同时保留子批次检查点。

不可接受的执行方式：

- 一次性改完四个切片再统一验收。
- 在 Screenshot / Shortcut 未稳定前开始 Settings shell 大拆。
- 在 Settings shell 结构仍不稳定时同步改 Clipboard 完整 payload read model。
- 任一子批次出现 P0/P1 后继续扩大到后续子批次。

## 5. 子批次顺序复审

推荐顺序合理：`ScreenshotStore -> ShortcutStore -> Settings shell split -> Clipboard hardening`。

理由：

- ScreenshotStore 和 ShortcutStore 先迁出 `AppState` 中剩余的明确 feature facts，能为 Settings pane 拆分提供稳定 facade / store 入口。
- Shortcut settings 依赖快捷键 store 边界，先拆 ShortcutStore 后拆 Settings shell 更稳。
- Clipboard hardening 触碰 repository unavailable、默认 read model 和敏感 payload 读取，应等 Settings shell 基本稳定后再做，避免 UI 结构变更和隐私边界变更互相遮蔽。

建议保留一个例外：如果 Clipboard hardening 被安全合规或测试/质量判定为高风险，应拆为 Step 4D，不阻断 Screenshot / Shortcut / Settings shell 的 Step 4C closeout。

## 6. AppState / Store / Pane / Coordinator 边界

PRD 的目标方向正确：

- `AppState` 保留 app section、navigation、feature store 持有、`objectWillChange` 桥接、跨 feature facade 和 window-level coordination。
- Screenshot、Shortcut、Permission、Provider、Translation、Clipboard 等事实源逐步进入 feature store。
- Settings shell 负责 mode routing 和 pane 组合，pane 保留局部 UI 状态，不把 provider secret 输入、连接测试、shortcut recorder、permission assist 等状态混入全局 store。

需要回写或开发时守住：

- Store 不持有完整 `AppState`。
- Pane 不绕过 store / facade 直接触发 platform API 或敏感读取。
- Coordinator 只做跨 feature 编排，不重新成为业务事实源。
- 如果某项事实源暂留 `AppState`，必须在开发记录中写清原因、影响和后续入口。
