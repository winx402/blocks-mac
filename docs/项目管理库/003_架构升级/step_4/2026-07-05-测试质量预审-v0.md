# Step 4 Feature 模块迁移测试/质量预审 v0

状态：reviewed
日期：2026-07-05
来源级别：test and quality prereview
结论：approve-with-changes

## 1. 预审范围

本预审只评估 `PRD-Feature模块迁移预初始化-v0.md` 中 Step 4 的测试策略、自动化门禁、实物验收和回归范围。未修改代码，未运行完整验证，未创建分支，未接受任何残余风险。

当前 PRD 仍是 `pre-initialized`，不是开发派单。测试/质量结论只表示可以继续预规划；进入开发前必须根据 Step 3 实际验收结果更新事实基线、切片范围和门禁清单。

## 2. 总体判断

Step 4 候选切片方向合理：先做 Step 3 rebaseline，再按 Screenshot、Permission、Shortcut、Settings shell 分切片推进，Clipboard hardening 作为容量允许时的候选项。这个顺序符合低风险 facade 迁移，也能把 AppState 的剩余高耦合区域拆成可验收单元。

需要修改的核心点是：当前 PRD 只列出了一组候选脚本，但没有把每个切片的自动化门禁、实物证据、退役/替换旧门禁和验收出口绑定清楚。Step 4 涉及截图、权限、快捷键和 Settings shell，静态脚本通过不能替代真实 UI、真实权限身份和真实快捷键路径证据。

## 3. 切片验收策略

### Slice 4A: Step 3 Rebaseline

建议作为 Step 4 的强制入口，不进入功能开发。

自动化门禁：

- App Debug build。
- CLI Debug build。
- `DerivedData/Blocks/Build/Products/Debug/blocks --help`。
- `git diff --check`。
- Step 3 对应 P10A / P10B / P10C 或实际命名门禁必须通过，或由主 agent 明确降级接受。

最小证据：

- Step 3 后 `AppState.swift`、`SettingsView.swift`、新增 store、关键 service 的行数和职责清单。
- Provider / Translation 是否已接受进入事实基线。
- Step 4 是否继续处理 Provider / Translation settings pane。
- 哪些旧 P7/P8/P9 脚本仍以旧目录或归档验收记录为事实源，哪些需要迁移到当前项目视图。

### Slice 4B: ScreenshotStore

P11A 合理，应作为 ScreenshotStore 边界门禁。建议检查：

- `Features/Screenshot/ScreenshotStore.swift` 存在，且为主线程可观察 store。
- `AppState` 不再直接持有本切片迁出的截图事实源，只保留兼容 facade / AppShell 协调。
- `ScreenshotHomeView`、`ScreenshotResultView` 继续通过 facade 或明确 store 输入工作，不直接访问 ScreenCaptureKit、Keychain、URLSession、provider runtime。
- `ScreenshotStore` 可以调用 `ScreenshotCaptureService` / `ScreenshotResultPresenter`，但不能上传截图、不能读取 secret、不能执行 provider call。
- `routeSummaryForScreenshotAIAction` 的 screenshot 侧输入组织仍是 route preview，不把图片内容写入日志、audit、JSON 或测试输出。
- Xcode project 已加入新增文件。

必须保留的现有门禁：

- `p3c_screenshot_checks.py`
- `p3d_screenshot_ai_action_entry_checks.py`
- `p3e_screenshot_result_polish_checks.py`
- `p3f_screenshot_ai_route_ready_checks.py`
- 如果触碰 window/fullscreen/region capture 或 result presenter：`p7q_screenshot_window_fullscreen_checks.py`

最小实物证据：

- Region、Window、Fullscreen 至少各一条低敏实测记录；如果环境只覆盖单屏，必须记录多屏未覆盖。
- Window hover、Esc cancel、无候选窗口路径。
- Screen Recording 未授权或不可用时的错误提示路径。
- Screenshot AI action preview 显示 route，不上传图片。

### Slice 4C: PermissionStore

P11B 中 Permission 部分合理，但不应和 Shortcut 只做一个粗粒度成功/失败。建议 P11B 至少区分 PermissionStore 子报告。

建议检查：

- `Features/Permissions/PermissionStore.swift` 存在。
- 权限 snapshot、刷新、Screen Recording assist、Accessibility assist、打开设置和重启提示均由 store 或窄接口承接。
- `AppState` 仅保留 facade / 跨 feature 协调。
- 权限状态只能来自系统 snapshot 或明确辅助流程；不得用 UserDefaults 假造授权状态。
- 系统设置跳转和 Accessibility 请求必须由用户动作触发。
- Permission Assist state machine、窗口等待、拖拽隔离、关闭条件仍保留。

必须保留的现有门禁：

- `p7f_permission_state_refresh_checks.py`
- `p7f_permission_assist_position_drag_checks.py`
- `p7g_permission_settings_interaction_checks.py`
- `p7k_permission_identity_gate_checks.py`
- `p7r_permission_assist_ux_checks.py`
- 如果改 build / signing / TCC 识别：`p7h_stable_signing_permission_identity_checks.py`

最小实物证据：

- 当前稳定 app 身份下的 Screen Recording / Accessibility existing gate 结果。
- 已授权状态下 Permission Assist 不误导用户。
- 未授权或无法验证时，记录环境限制，不写成通过。
- 如果触碰 revoked-flow，必须有撤权后重新检查 / 重新引导证据；否则明确列为未覆盖。

### Slice 4D: ShortcutStore

P11B 中 Shortcut 部分合理。建议与 PermissionStore 共用脚本可以接受，但输出必须分开，避免 Permission 通过掩盖 Shortcut 回归。

建议检查：

- `Features/Shortcuts/ShortcutStore.swift` 存在。
- 注册结果、统计、启用/禁用、自定义绑定、恢复默认、全局 modifier preset、刷新注册均由 store 或窄接口承接。
- `ShortcutStore` 不持有完整 `AppState`；快捷键命令只接收 AppShell 注入的窄动作闭包。
- 仍使用现有 `ShortcutBindingStore`，不改变持久化策略。
- Settings 中快捷键配置和诊断仍显示正确。

必须保留的现有门禁：

- `p6a_shortcut_panel_interaction_checks.py`
- `p6b_shortcut_customization_panel_polish_checks.py`
- `p6c_shortcut_acceptance_gate_checks.py`
- `p7c_shortcut_global_modifier_checks.py`
- `p7d_panel_exclusivity_shortcut_focus_checks.py`
- 如果触碰 Clipboard/Translation panel focus 行为：对应 P7 clipboard / translation panel 门禁按影响范围运行。

最小实物证据：

- 默认三工具快捷键注册状态。
- 启用/禁用、修改、恢复默认、全局 modifier preset。
- 快捷键触发时 panel show/focus/exclusivity 不回归。
- 不能伪造全局系统按键触发结果；若只做静态或诊断验证，必须明确标记未覆盖真实按键路径。

### Slice 4E: Settings Shell Split

- `SettingsView.swift` 行数下降不是唯一目标；更重要的是职责变清楚、路由和设置项不丢失。
- 三语 String Catalog 覆盖新增或移动后的可见文案。

必须保留的现有门禁：

- `p8g_settings_shell_redesign_checks.py`

最小实物证据：

## 4. P11A / P11B / P11C 评估

结论：命名和方向合理，但当前 PRD 对检查内容描述不足。建议在最终 PRD 中把 P11 门禁写成可执行验收契约。

P11A 应聚焦 ScreenshotStore：

- Store 存在、target 引用、AppState facade、View 依赖方向。
- 截图状态和动作从 AppState 迁出。
- AI route preview 不变成 provider call。
- 截图图片不进入日志、audit、测试 JSON 或持久化。
- P3/P7Q 回归联动。

P11B 应拆出两个子域：

- Permission：PermissionStore、系统 snapshot、用户触发、assist state machine、TCC/stable identity。
- Shortcut：ShortcutStore、窄动作闭包、注册结果、绑定持久化、Settings 诊断、panel focus。

如果仍用一个脚本，输出 JSON 必须包含 `permission_checks` 和 `shortcut_checks` 两个独立分组。

P11C 应聚焦 Settings shell：

- Shell/pane 文件和 target 引用。
- 路由、设置 key、本地化、布局基线。
- Pane 禁止直接访问敏感系统/API 能力。
- 与 P8G/P8I/P8J/P8K 的旧结构假设冲突时，要更新旧门禁，不能简单跳过。

## 5. 现有门禁保留策略

必须作为 Step 4 总体验收基础保留：

- App Debug build。
- CLI Debug build。
- `blocks --help`。
- `git diff --check`。
- P11A/P11B/P11C 中与实际切片匹配的新增门禁。
- `p3c_screenshot_checks.py`，因为它覆盖 build、CLI screenshot dry-run、entitlements、helper embedding 和基础 action smoke。

按切片运行：

- Screenshot：P3C/P3D/P3E/P3F；触碰真实 window/fullscreen/region 或 result presenter 时加 P7Q。
- Permission：P7F permission state / assist、P7G permission settings interaction、P7K identity、P7R UX；触碰 signing/TCC 时加 P7H。
- Shortcut：P6A/P6B/P6C、P7C shortcut global modifier、P7D panel exclusivity/focus。
- Settings shell：P8G/P8I/P8J/P8K；如触碰历史 settings route/scroll/menu 问题，加 P7B/P7C/P7D/P7E/P7F/P7G 对应脚本。
- Clipboard hardening：P9A/P9B/P9C、P8M/P8N；触碰 panel/paste/hover 时加 P7L 或其替代版。

不建议无条件全跑：

- 与 Clipboard panel、Translation panel、alpha readiness closure 直接相关的 P7/P8 门禁，如果本次切片没有触碰对应区域，可以作为 nightly / release gate，不必作为每个小切片阻断项。
- 仍依赖归档验收记录或旧项目路径的脚本，需要先标注为 baseline gate；若作为 Step 4 阻断门禁，应迁移到当前 `docs/项目管理库/003_架构升级/step_4/` 证据。

## 6. 回归风险与最小证据

截图风险：

- Store 迁移后截图启动路径丢失、result presenter 不显示、AI preview 误变成外发、未授权路径崩溃。
- 最小证据：P3C/P3D/P3E/P3F 通过；至少一轮低敏 region/window/fullscreen 实测或明确环境限制；截图图片不落日志、不落仓库。

权限辅助风险：

- TCC identity、稳定签名路径、System Settings 定位、assist panel close condition、撤权状态判断容易回归。
- 最小证据：existing permission gate 或明确未授权环境；Permission Assist granted-state；若改 request/revoked flow，必须补 revoked-flow 实测。

快捷键风险：

- 注册回调持有完整 AppState、快捷键触发变成 close 而不是 focus、设置修改不持久、冲突/失败诊断丢失。
- 最小证据：P6A/B/C + P7C/P7D 通过；一条低敏人工记录说明默认快捷键、禁用、修改、恢复默认是否真实触发。

Settings shell 风险：

- 拆文件后 route 丢失、设置 key 改名、pane 直接访问敏感 API、窄宽/全屏/滚动布局回归。
- 最小证据：P8G/I/J/K 通过；主要 settings route 打开检查；关键设置关闭重开保持；新增文案三语覆盖。

## 7. 必改项

1. 最终 PRD 必须把 P11A/P11B/P11C 的检查内容写清楚，不能只列脚本名。
2. Step 4 进入开发前必须完成 Step 3 rebaseline，并明确 P10/P11/P3/P6/P7/P8/P9 的运行矩阵。
3. 对依赖旧归档验收记录或旧项目路径的门禁，必须说明是 baseline gate 还是当前 Step 4 阻断门禁；作为阻断门禁时应迁移事实源。
4. 每个切片必须定义实物验收最低证据，尤其 Screenshot、Permission、Shortcut。
5. Settings shell split 必须声明不改设置 key，并用门禁防止 pane 直接访问敏感 API。

## 8. 建议项

1. 把 Step 4 拆成 4A rebaseline、4B Screenshot、4C Permission、4D Shortcut、4E Settings，分别验收；不要默认一次性提交所有切片。
2. P11B 如果实现为单脚本，输出 JSON 中拆 `permission_checks` / `shortcut_checks`，便于定位失败。
3. 为 Step 4 新增一个聚合 runner，但聚合 runner 只组合脚本，不隐藏单项失败细节。
4. 对实物验收记录采用固定模板：环境、构建路径、权限状态、操作步骤、观察结果、未覆盖项、证据位置。
5. Clipboard hardening 建议单独作为后续小阶段，除非 Step 4 其他切片明显缩小。

## 9. 阻断项

当前无阻断继续预规划的问题。

进入开发前的阻断项：

- Step 3 未完成或未被主 agent 明确接受 / 降级接受。
- P10 门禁失败且未记录处理策略。
- 最终 PRD 继续把未验收的 Provider / Translation 结果当成事实。
- 没有为 Screenshot / Permission / Shortcut 的真实行为设置最小实物证据。
- P11 门禁仍只有脚本名，没有可执行检查范围。

## 10. 待验证项

- Step 3 后 `AppState`、`SettingsView` 和各 store/service 的真实行数与职责。
- Step 3 后 Provider / Translation settings pane 是否具备拆分前提。
- P7Q/P7R/P7K/P7S 等门禁当前是否仍能在项目视图下直接运行，还是需要迁移归档依赖。
- 当前机器是否具备稳定签名、Screen Recording、Accessibility existing gate 的真实验收条件。
- `p7l_clipboard_experience_gate_checks.py` 是否仍因 Step 2 ClipboardStore 迁移而需要更新为当前结构。

## 11. 最终结论

结论为 `approve-with-changes`。

Step 4 可以继续预规划，但在进入开发前必须补齐 P11 具体检查内容、切片化运行矩阵、旧门禁事实源处理方式和实物验收最低证据。当前 PRD 的方向可用；若不做这些修改，后续容易出现“静态脚本通过但真实截图、权限辅助、快捷键或 Settings 路由回归”的验收空洞。
