# 2026-07-05 App 架构师预审 v0

结论：approve-with-changes

状态：reviewed
来源级别：App architecture pre-review
复审范围：`PRD-Feature模块迁移预初始化-v0.md`、架构升级阶段总览、Step 3 PRD 当前状态，以及当前 `AppState` / Screenshot / Permission / Shortcut / Settings 相关入口的只读抽查。

## 1. 总体判断

Step 4 作为预初始化文档的方向成立：它没有把 Step 3 未验收结果写成事实，也没有直接进入开发派单；候选范围覆盖 Screenshot、Permission、Shortcut、Settings shell 和 Clipboard hardening，符合 Step 1 的 feature 化迁移方向。

但本文不能在当前形态直接升级为 `ready-for-development`。Step 4 涉及 ScreenCaptureKit、Accessibility、全局快捷键、设置入口和多个 store 之间的协调，如果一次性把 4B/4C/4D/4E/4F 都纳入一个开发阶段，会制造新的跨 store 耦合，并扩大 UI / 权限 / 回归风险。

建议保留本文作为预规划基础，但必须修改后再进入开发：先拆出 Step 4A rebaseline，再确定一个最小可开发 Step 4B。4B 不应同时包含 ScreenshotStore、PermissionStore、ShortcutStore、完整 Settings shell 和 Clipboard hardening。

## 2. 切片顺序评估

当前候选切片顺序大体合理，但需要调整开发粒度。

建议拆分为：

1. Step 4A：Rebaseline / final PRD，不写业务代码。
   - 等 Step 3 验收后重算 `AppState`、`SettingsView`、ProviderStore、TranslationStore、ClipboardStore 和相关 service 的事实基线。
   - 明确 Step 4B 只做一个可验收切片。
   - 决定 Provider / Translation settings pane 是否进入 Settings shell 拆分。

2. Step 4B：优先做 PermissionStore 或 PermissionStore + ScreenshotStore 的最小组合。
   - 如果先做 ScreenshotStore，必须通过 protocol / closure 读取权限状态，不直接持有完整 AppState。
   - 如果先做 PermissionStore，它可以为 ScreenshotStore 和 clipboard paste retry 提供稳定输入，但 paste retry 仍应留在 AppShell / Clipboard 协调层。

3. Step 4C：ShortcutStore。
   - ShortcutStore 依赖 AppShell 注入的窄动作闭包，不直接持有 AppState。

4. Step 4D：Settings shell / pane split。
   - 等相关 store 边界稳定后再拆 pane，避免 pane 继续通过 AppState 间接绑定未拆 feature。

5. Step 4E 或后续 Step：Clipboard hardening。
   - `repositoryUnavailable` 产品化和 redacted list + lazy payload 涉及敏感数据与 UI 行为，不建议混入 Screenshot / Permission / Shortcut 首批迁移。

## 3. 依赖方向评估

### ScreenshotStore

风险点：

- PRD 写到 `ScreenshotStore` 可以依赖 `ScreenshotResultPresenter`。这会让 feature store 直接承担 AppKit window / panel presentation，容易把 store 变成 UI coordinator。
- Screenshot AI action route preview 如果直接依赖 ProviderStore，会在 ScreenshotStore 和 ProviderStore 之间形成 store mesh。

建议：

- `ScreenshotStore` 可依赖 `ScreenshotCaptureService` 或 `ScreenshotCapturing` protocol。
- 结果展示优先留在 AppState / AppShell facade，或通过 `ScreenshotResultPresenting` protocol 注入；不要让 ScreenshotStore 直接扩大为窗口协调器。
- AI action route preview 通过闭包或 protocol 注入，例如 `resolveScreenshotAIActionRoute(action:)`，不要让 ScreenshotStore 直接持有 ProviderStore。
- Screen Recording 权限通过 `PermissionReadable` / closure 输入，不直接读取或请求权限。

### PermissionStore

风险点：

- Permission 同时影响 screenshot、auto-paste retry、Settings permission pane 和 permission assist panel。
- 如果 PermissionStore 直接触发 retry paste 或静默打开系统设置，会越过用户动作边界。

建议：

- `PermissionStore` 只持有 `permissionSnapshot`、刷新、用户触发的辅助请求和状态投射。
- 自动粘贴重试留给 AppShell / Clipboard 协调层。
- 系统设置跳转和权限请求必须由用户动作触发，并通过 presenter / service 的窄接口执行。

### ShortcutStore

风险点：

- 快捷键注册需要执行 screenshot、clipboard panel、translation panel 等跨 feature 动作；若 ShortcutStore 持有 AppState，会把 AppState 耦合搬进新的 store。

建议：

- `ShortcutStore` 接收 `[ShortcutCommand: () -> Void]` 或明确的 action protocol。
- 快捷键配置仍可沿用 `ShortcutBindingStore`；本阶段不改变持久化策略。
- ShortcutStore 只负责注册状态、绑定配置和诊断，不直接知道 feature 内部状态。

### Settings shell

风险点：

- 过早拆 Settings shell 会把未稳定的 Provider / Translation / Permission / Shortcut store 边界固化到 pane 层。
- Pane 若直接引入 `URLSession`、`SecItem`、`NSPasteboard.general`、`SCShareableContent.current` 等敏感 API，会破坏分层。

建议：

- Settings shell 先做 shell + section list + 少量稳定 pane；Provider / Translation pane 是否拆出必须等 Step 3 接受后决定。
- Pane 只调用 AppState facade 或明确 feature store facade，不直接调用系统敏感 API。
- 保持现有 `SettingsViewMode` 行为不回归。

## 4. AppState facade 策略

PRD 的 facade 策略与 Step 2 / Step 3 一致：先保留 View 调用入口，内部转发到 feature store，避免一次性重写 UI。

进入开发前应补充以下硬规则：

- AppState 可以保留 `selectedSection`、global `status`、window / panel presenter orchestration 和跨 feature 协调。
- AppState 不得新增本阶段迁出 feature 的 `@Published` 事实源。
- AppState 的 facade method 必须薄转发；如果需要状态投射，应记录返回结果如何映射到 `AppStatus`。
- 每个新增 store 的 `objectWillChange` 绑定方式要跟 Step 2 / Step 3 保持一致。
- P11 门禁应检查 AppState 中本阶段迁出的事实源不再是直接 `@Published`，并检查 facade 方法仍存在。

## 5. 必须等待 Step 3 验收后才能进入 ready-for-development 的内容

以下内容不得在 Step 3 验收前写成已定实现或直接派发开发：

- `ProviderStore` / `TranslationStore` 是否存在、是否进入 target、是否通过 P10A / P10B。
- `routeSummaryForScreenshotAIAction(_:)` 的最终归属：AppState facade、ProviderStore facade，还是新的 route resolver protocol。
- Step 3 后 `AppState` 剩余 `@Published` 事实源和实际行数。
- Provider / Translation settings pane 是否适合进入 Settings shell 拆分。
- P5/P10 结果是否稳定；如果 Step 3 降级接受或返工，Step 4 必须先重写范围。
- `index.md` / `step.md` 的阶段状态，避免多个线程同时写入冲突。

## 6. 必改项

1. 将 Step 4 明确拆成至少 Step 4A / Step 4B。
   - Step 4A 只做 rebaseline 和最终 PRD。
   - Step 4B 只选一个最小实现切片，不要一次性做 4B 到 4F。

2. 修改 ScreenshotStore 边界。
   - 不建议直接依赖完整 `ScreenshotResultPresenter` 或 ProviderStore。
   - 改为 protocol / closure 注入，或把 presenter 继续留在 AppShell。

3. 明确 PermissionStore 先后关系。
   - 如果 ScreenshotStore 先做，权限输入必须是窄接口。
   - 如果 PermissionStore 先做，不得包含 paste retry 编排。

4. 明确 ShortcutStore 动作注入方式。
   - 只能接收 AppShell 暴露的窄动作闭包或 protocol。
   - 禁止 ShortcutStore 持有 AppState。

5. Settings shell 不能在 Step 3 未验收前决定 Provider / Translation pane 细节。
   - PRD 应把这些 pane 标记为 Step 3-dependent。

6. P11 门禁需要从候选名细化为检查项。
   - 至少覆盖 store 文件存在并进 target、AppState forbidden `@Published`、View 禁止直接敏感 API、Settings pane 禁止直接系统 API、App / CLI build。

## 7. 建议项

- 在最终 PRD 中给每个 store 定义输入 / 输出协议，而不是只列文件名。
- 给 Step 4B 设置行数和职责观察指标，例如 AppState 行数变化、迁出 `@Published` 数量、SettingsView 行数变化。
- Screenshot / Permission / Shortcut 任一涉及真实 UI 流程的改动，除脚本门禁外应要求截图、录屏或可复现 UI harness 证据。
- 对 PermissionAssistPanelPresenter 先做窄接口封装，不急于搬文件。
- Clipboard hardening 单独立 Step 4E 或 Step 5 前置，不要混入第一批。

## 8. 阻断项

当前没有阻断继续预规划的 P0。

进入 `ready-for-development` 的阻断项：

- Step 3 未完成开发、测试/质量验收、App 架构师实现复审和主 agent 接受判断。
- Step 4 未拆成具体可开发切片。
- 依赖方向仍允许 store 直接持有 AppState，或多个 feature store 互相强持有。
- P11 门禁仍只有名称，没有明确检查内容。

## 9. 待验证项

- Step 3 后 AppState / SettingsView / stores / services 的实际行数。
- Step 3 是否改变 route preview、Provider / Translation settings pane、status projection 和 audit 归属。
- 当前 P3 / P6 / P7 / P8 / P9 门禁在 Step 3 后是否仍可运行，是否有旧路径或旧验收故事误报。
- PermissionAssistPanelPresenter 是否适合在 Step 4 中只做窄接口，还是需要单独拆分。
- Settings shell 拆分是否需要 UI/交互设计师先确认导航和 pane 层级。

## 10. 预审结论

结论为 `approve-with-changes`。

本文可以作为 Step 4 预规划基础继续使用，但不能直接升级为开发 PRD。主 agent 应在 Step 3 验收后先组织 Step 4A rebaseline，再选择单一 Step 4B 实施切片。若最终 PRD 采纳上述必改项，App 架构视角可以支持进入下一轮 `ready-for-development` 评审。
