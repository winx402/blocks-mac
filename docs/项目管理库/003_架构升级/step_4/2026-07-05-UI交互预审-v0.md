## 2. 总体判断

Step 4 以 facade 迁移和 Settings shell 结构拆分为主，不绑定视觉重设计，这个方向从体验风险看是正确的。当前最大风险不是界面不够新，而是迁移时丢失已有的导航模式、局部交互状态、权限提示语义和截图结果页的安全承诺。

因此本预审不建议 reject；但在进入 `ready-for-development` 前，最终 PRD 必须增加一份用户可见行为保持清单和体验验收门槛。没有这份清单时，SettingsView 拆分很容易变成“文件拆开了，但路由、返回、录制状态或安全提示出现轻微回归”的隐性风险。

## 3. Settings shell 拆分必须保持的体验状态

必改项：

1. 保持现有 `SettingsViewMode` 路由能力。
   当前模式包括 `all`、`general`、`clipboard`、`clipboardPrivacy`、`translation`、`shortcuts`、`providers`、`agentCLI`、`hooks`、`dataAudit`、`permissions`。拆分后每个 mode 仍应能作为独立入口渲染，不应只服务于 `all` 聚合页。

2. 保持 `clipboardPrivacy` 的返回路径。
   当前独立隐私页通过返回按钮回到 Clipboard 设置。拆分后必须保留“返回剪贴板”的语义和目标，不应把它降级为关闭窗口或回到全部设置。

3. 保持设置项的持久化 key。
   PRD 已写明不改变已有 setting key；从体验角度看，这也是必须项。拆分后用户已有语言、快捷键、剪贴板策略、Provider、Translation、Agent/CLI 配置不应因为 pane 迁移而重置。

4. 保持 pane 级临时状态的生命周期。
   特别是：
   - Shortcut 录制只允许一次录一个命令，`shortcutRecorderState` 不能变成每行独立状态。
   - Provider secret 输入、确认存储、OpenAI test connection 外发确认等状态应留在 Provider pane 范围，不应在子组件重绘时意外丢失。
   - Permission snapshot 的刷新、重启提示和 request assist 入口应留在同一信息上下文内。

5. 保持现有布局密度和行组件语义。
   当前 Settings 使用统一的 section、row、action row、固定 trailing column、可选择的诊断文本和辅助说明。Step 4 若只做结构拆分，应先复用这些行组件或等价组件；不要同时改成新的侧栏、卡片密度、视觉层级或信息架构。

建议项：

- 在最终 PRD 的 Slice 4E 下增加“Settings shell UX contract”表格，逐项列出 mode、标题、说明、主要 sections、返回行为、局部状态、敏感动作和验收路径。
- 将 `SettingsSectionList` 先定义为路由/section 选择容器，而不是新的视觉导航系统。视觉和信息架构调整应拆成后续 UX spec。

## 4. Permission Assist 交互风险

必改项：

1. 权限操作必须继续由用户动作触发。
   PRD 已写明 PermissionStore 不擅自触发系统设置跳转。UI 验收也应明确：Screen Recording、Accessibility、Show in Finder、Restart Blocks 都必须由显式按钮触发。

2. 保持权限诊断和动作入口同屏可理解。
   当前 Permissions 页面同时展示 Screen Recording 与 Accessibility 的授权状态、app path、签名、bundle ID、建议操作，以及刷新/重启/请求权限入口。拆分后不能只保留按钮，否则用户不知道为什么要点、点完后如何确认。

3. 保持“请求权限，并在系统设置更新后确认”的双阶段语义。
   当前文案区分 request、I finished、restart 和 drag app icon。迁移后如果只显示“已完成”或只显示“请求权限”，会让用户误以为 app 已自动完成授权。

4. 保持手动拖动 fallback。
   当前有“拖动积木工具到权限列表”和“在 Finder 中显示当前 App”的辅助路径。PermissionStore 抽出后，这些 fallback 不应被误删。

建议项：

- Permission Assist 的状态文案应在最终验收中覆盖 opening、waiting、guiding、checking、granted、failed、cancelled、timedOut 等状态。当前本次未读取 presenter 内部状态机，建议由测试/质量或 App 架构师补充实测证据。
- 如果权限行继续显示 app path，长路径应验证截断、复制和 VoiceOver 读取效果，避免用户无法区分当前运行路径与系统设置里的同名 App。

## 5. 截图结果与 AI action preview 风险

必改项：

1. 保持 Screenshot Home 的四类反馈。
   当前首页有 app 状态标题/详情、last capture summary、region/window/fullscreen 三个截图入口、Screen Recording Settings 入口、recent captures 空态和列表态。迁移 ScreenshotStore 后这些反馈不能只剩截图按钮。

2. 保持 Screenshot Result 的结果动作与 outcome banner。
   复制、另存为、重新截图、关闭，以及 copy/save/cancel/failure 的反馈 banner 都是用户理解截图是否完成的关键路径。迁移 presenter 或 store 时必须保留。

3. AI action preview 必须继续明确“不上传图片、不调用 provider”。
   当前结果页会显示 route ready/blocked、provider profile、confirmation level、dependency note，并显示 `provider_call_not_executed / image_not_uploaded` 与“不发送图片”的文案。迁移后如果这些字段缺失，用户会误以为点击 Translate/Summarize/OCR 会真实处理截图或外发图片。

4. 保持 blocked 状态可解释。
   对 Translation，当前文案说明需要先有 OCR 文本；对 Summary，说明只是 route preview。迁移 route summary 解析后，blocked 不能只显示错误码，应保留本地化的 status detail。

建议项：

- AI action 按钮目前通过显示预览卡体现选中状态。若 Step 4 不做视觉改动，至少在验收中确认选中后焦点、键盘导航和 VoiceOver 能读出当前预览对象。
- 截图图片本身应有可访问性标签或说明，尤其在结果页标题为“截图已完成”时，VoiceOver 用户需要知道当前预览图的模式、尺寸和来源。

## 6. 结构拆分 vs 视觉/信息架构调整

建议先做结构拆分，不建议在 Step 4 同时做视觉或信息架构调整。

理由：

- Step 4 的主要目标是低风险 facade 迁移和 feature 边界清晰化；视觉/IA 改动会扩大回归面。
- 当前 SettingsView 虽然巨大，但已经存在相对稳定的内容分组、统一 row shell、独立 mode、隐私子页返回和敏感动作 gate。
- 如果先改视觉层级，就很难判断回归来自 Store 拆分、View 拆分，还是新 IA 决策。

可接受顺序：

1. 先拆 `SettingsShellView`、section list 和各 pane，保持视觉、顺序、文案和 setting key。
2. 用 P11C 与人工验收确认所有 mode、返回路径、局部状态和敏感动作不回归。
3. 若主 agent 后续认为 Settings 信息架构需要调整，再单独写 UX spec，不混入 Step 4E。

## 7. 文案、状态反馈和可访问性风险

必改项：

1. 保留安全边界文案。
   必须保留或等价表达以下语义：截图 AI preview 不发送图片、不调用 provider；Translation route check 不读 key、不调用 provider；权限请求需要用户在系统设置完成后确认；Agent/CLI 只描述现有边界，不承诺完整 payload 默认读取。

2. 保留失败、取消和待确认反馈。
   截图保存取消、复制失败、保存失败、permission timed out、route blocked、shortcut conflict 等状态不能只落在日志或内部状态。

3. 为 labelsHidden 的控件补可访问性验收。
   Settings 中多处 Toggle / Picker 使用隐藏 label 并依赖左侧行标题解释。最终验收应确认 VoiceOver 能读出每个控件的具体设置名，而不是只读“switch”或空标签。

4. 验证固定 trailing column 下的长文案。
   权限路径、shortcut conflict、provider readiness、中文/英文/日文长句都可能在 280pt trailing column 或两行 detail 中被截断。Step 4 不一定要改视觉，但需要确认拆分后没有更差。

建议项：

- 将本地化文案 key 的保留列入 PRD 验收，特别是 `screenshot.ai.*`、`screenshot.result.*`、`settings.permission*`、`settings.shortcut*`、`settings.agentCLI.*`。
- Shortcut 录制按钮当前 help 文案偏向“无效快捷键规则”，不是录制说明。若后续做体验打磨，可以单独调整；不建议混入 Step 4 结构拆分。

## 8. 阻断项

当前没有需要 reject 预初始化方案的 UI/交互阻断项。

转入开发前的阻断条件：

- Step 3 未验收，导致 Provider / Translation pane 边界仍不可作为事实。
- 最终 PRD 未补 Settings shell UX contract，就直接派发 SettingsView 拆分。
- Screenshot AI action preview 不能明确保持“不上传图片、不调用 provider”的用户可见承诺。
- Permission Assist 的用户触发、刷新确认、重启提示或手动 fallback 被实现方案移除。

## 9. 待验证项

1. Settings 各 mode 能否从现有入口稳定打开，并保持正确标题、说明、section 内容和滚动位置预期。
2. Clipboard Privacy 独立页能否返回 Clipboard 设置，且不会造成 all 模式下重复或迷路。
3. Shortcut 录制时，切换行、切换 pane、关闭 Settings 后是否停止监听并恢复 idle。
4. Permission Assist 在 screen recording 与 accessibility 两条路径下的打开、等待、完成、失败、取消、超时反馈是否仍可见。
5. Screenshot region/window/fullscreen 后，结果页的 copy/save/retake/close、outcome banner、recent captures 更新是否不回归。
6. AI action preview 在 ready 与 blocked 状态下是否保留 provider profile、confirmation level、localized status detail 和 no-upload 文案。
7. VoiceOver、键盘导航、Reduced Transparency、长文本和三语言本地化是否在拆分后无明显退化。

## 10. 回写 PRD 建议

建议主 agent 在 Step 4 最终 PRD 中新增以下验收条目：

- Settings shell 拆分不得改变 `SettingsViewMode` 路由、setting key、clipboardPrivacy 返回路径、pane 局部状态和当前分组顺序，除非另有单独 UX 决策记录。
- Permission pane 必须保留授权状态、推荐操作、刷新确认、重启提示、request assist、Show in Finder 和 drag fallback。
- Screenshot result 必须保留 copy/save/retake/close、outcome banner、AI route preview、blocked detail 和 no-upload/provider-not-called 文案。
- P11C 除静态边界检查外，需要至少覆盖 Settings mode 渲染、clipboardPrivacy 返回、Shortcut 录制状态、Permission assist 入口和 Screenshot result preview 的人工或自动验收说明。

最终结论：approve-with-changes。预初始化方向可以继续进入预规划；进入开发前必须补齐上述必改项或把未处理部分明确列为残余风险。
