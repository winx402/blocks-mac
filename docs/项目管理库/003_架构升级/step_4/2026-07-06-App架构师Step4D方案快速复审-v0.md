## 3. P0 / P1 / P2

### P0

无。

### P1

1. **4D-1 与 P11E 检查范围存在切片边界冲突。**  
   PRD 5.1 说 4D-1 出口是 P11E 通过；但第 6 节要求 P11E 检查普通 list / card / row / Settings / DataAudit / CLI 默认输出不传入 `ClipboardRecorderPayload`、hover 不为所有 filtered records 预读 payload。与此同时 5.2 又把 Clipboard panel 默认 row/card/list/tray 改造放到 4D-2。  
   **建议回写：**二选一：
   - 方案 A：把普通 panel row/card/list/tray 去 payload 化前移到 4D-1，让 P11E 在 4D-1 真正绿灯。
   - 方案 B：把 P11E 拆成阶段化子检查，例如 `p11e_phase=read_model` / `p11e_phase=ui`, 4D-1 只要求 load/facade/read model 绿灯，4D-2 才要求 UI 默认渲染绿灯。若不拆，4D-1 声称 P11E 通过会与 P11E 最低职责矛盾。

2. **payload cache 生命周期仍偏原则，没有形成开发可执行策略。**  
   PRD 已要求 cache 只能由 explicit read 写入，也要求 hover 退出、panel 关闭、repository reload、record 删除时清理策略必须明确，但未选择策略。开发并行启动时，这会导致实现自行决定 cache 保留范围。  
   **建议回写最小策略：**
   - 4D-1 默认优先“不缓存完整 payload”；如为性能需要缓存，只允许 keyed by `(recordID, purpose)`。
   - `loadRepositoryState` / repository reload 必须清空完整 payload cache。
   - record 删除必须清掉对应 payload cache。
   - hover detail 读取若缓存，只能保留 active hover record，hover exit 或 panel close 清空。
   - cache 不应作为宽 `@Published var payloads` 暴露给默认列表；如保留旧属性作为迁移中间态，P11E 必须证明默认 list/Settings/DataAudit/CLI 不读它。

3. **PRD 流程条款与当前“按草案并行启动实现”的执行方式冲突。**  
   PRD 11.1/11.2 写明 P0/P1 未关闭前不得派开发，且 PRD 阶段文档提交前不得启动 4D-1；但当前主会为了加速允许开发按草案并行启动。  
   **建议回写：**增加“并行开发例外”条款：开发可先做 P11E-first / 4D-1 narrow implementation，但不得进入 4D-2、不得写最终接受、不得把实现合并为 accepted，直到四方复审 P0/P1 清零并由主会回写 PRD。

4. **BlocksCLI `main.swift` 被列为必须修改，容易制造不必要范围。**  
   Step 4D 非目标是不新增 CLI 默认完整 payload 输出，当前 CLI 也未暴露 clipboard 默认输出。把 `apps/Blocks/BlocksCLI/main.swift` 列入“必须修改”可能诱导开发无必要触碰 CLI。  
   **建议回写：**将 CLI 改为“必须由 P11E 检查；仅在新增 metadata/redacted dry-run 或修正 denylist 需要时修改”。默认要求应是 CLI 不新增 clipboard payload 输出，而不是强制修改 CLI 文件。

### P2

1. `summary` 规则建议更硬：默认 redacted builder 应明确完全不展示历史 `record.summary`，除非未来引入 `summarySensitivity` / `summaryKind` 等结构化标记。当前草案已经接近这个方向，但可把“除非证明低敏”改成“本阶段一律不用于默认可见正文区域”。
2. `ClipboardPayloadReadPurpose` 建议同时进入开发记录和 P11E JSON 输出，记录 purpose、record id hash / synthetic id、result code，不记录正文。
3. 如果 4D-1 引入 `ClipboardReadModel.swift` / `ClipboardPayloadAccess.swift` / `ClipboardRepositoryState.swift`，P11E 应检查这些文件进入 Blocks app target；若某文件只服务 CLI 或 Core，应显式说明 target 归属，避免项目文件漂移。
4. 搜索策略建议在 PRD 中选默认值：优先 metadata / redacted display item 搜索；repository FTS 只作为可选后续或显式说明“不展示正文片段”。这有助于降低 4D-1 实现分歧。

## 4. 是否允许 P11E-first 开发

允许，但范围必须收窄：

- 允许：新增 P11E，先证明当前基线红灯；新增 read model / explicit read purpose；让 default load 不再预读 payload；收窄 AppState 无 purpose payload facade；建立 redacted display builder；迁移 P9B 到新契约。
- 暂不允许：进入 4D-2 UI/UX 全面改造、引入 CLI clipboard payload 命令、开启 helper 生产写库、App Group、provider call、OCR、Keychain、网络外发或任何真实系统动作。
- 如果开发为了让 P11E 绿灯必须触碰普通 panel row/card/list/tray，则应按上文 P1-1 回写，把这部分明确归入 4D-1。

## 5. 主 agent 建议

建议主 agent 以 `approve-with-changes` 接受本轮快速复审：不阻塞 P11E-first 并行实现，但要求在 PRD 正式提交 / 4D-1 stop-go 前回写 P1。

最重要的回写顺序：

1. 先解决 4D-1 与 P11E 检查范围冲突。
2. 再固定 payload cache 生命周期。
3. 再补并行开发例外条款。
4. 最后把 CLI 从“必须修改”改成“必须检查，按需修改”。
