Step 4B 选择 PermissionStore 单切片是合理的：它把权限状态从 `AppState` 抽成稳定事实源，同时不混入 ScreenshotStore、ShortcutStore、Settings shell 或 Clipboard hardening，范围控制符合 Step 4 预初始化结论。

## 4. Settings Permissions 体验契约

判断：基本完整，但需要澄清“诊断字段可见”的具体层级。

已覆盖：

- PRD 要求 Screen Recording 与 Accessibility 两条诊断同时可见。
- PRD 要求保留授权状态、bundle ID、app path、签名类型、team ID、usage description、recommended action、matching running app path、identity issue。
- PRD 要求 Refresh / Completed、Restart Blocks、Request Screen Recording、Request Accessibility、Show in Finder 均由用户点击触发。
- PRD 明确未授权或无法验证时不得写成已授权。

需要回写澄清：

- 当前 Settings compact row 主要展示 app path、recommended action、授权状态、签名摘要和 bundle ID。PRD 里列出的 team ID、usage description、matching running app path、identity issue 是“必须在 Settings 直接可见”，还是“必须在诊断数据中保留并通过等价 UI 可见”，需要写清楚。
- 如果 Step 4B 不改 Settings shell，建议不要要求重做诊断信息架构；但至少应验收 compact row 没有丢失现有可见信息，且 store 迁移后诊断数据字段未缺失。

## 5. Permission Assist 状态路径

判断：PRD 方向正确；状态覆盖应写得更可验收。

已覆盖：

- PRD 要求请求权限与诊断、后续动作同屏可理解。
- PRD 要求 Screen Recording 和 Accessibility 辅助入口区分清楚。
- PRD 要求等待、拖拽隔离、关闭条件、刷新检查、失败 / 超时 / 取消语义不丢失。
- 抽查代码显示当前 presenter 已有 `openingSystemSettings`、`waitingForSettingsWindow`、`guiding`、`checkingPermission`、`granted`、`failed`、`cancelled`、`timedOut` 等状态及对应文案。

需要回写澄清：

- 开发验收应列出实际覆盖到哪些状态；未覆盖状态必须写成未覆盖，不能写成通过。
- `granted` 路径通常会很快关闭面板，实测时可能难以观察；PRD 应允许用低敏日志或测试钩子说明，而不是要求真实截图证据。
- `cancelled` 和 `timedOut` 受时间和系统窗口状态影响，若无法稳定触发，应列为受限验证。

## 6. Screenshot Permission Missing 路径

判断：PRD 已保住核心路径，但建议补充 UI 反馈细节。

已覆盖：

- PRD 要求 `startScreenshot(mode:)` 在截图前刷新权限并检查 Screen Recording。
- PRD 要求缺少 Screen Recording 时继续设置 `permissionMissing` 状态并展示辅助路径。
- PRD 要求 Screenshot Home 的 Screen Recording Settings 入口仍可用。

建议回写：

- 验收时应确认状态标题与详情仍是用户可理解的缺权提示，而不只是内部状态变为 `permissionMissing`。
- 如果实现保留 alert 或等价辅助入口，应在开发记录中说明；如果改成非 alert 形式，也必须证明用户仍能到达授权辅助路径。

## 7. Clipboard Pending Paste Retry 体验

判断：PRD 保住了架构边界，但用户可见反馈还应补一句。

已覆盖：

- PRD 要求 `refreshPermissionState()` facade 刷新 store 后仍调用 `retryPendingClipboardPasteIfPossible()`。
- PRD 要求 PermissionStore 不直接处理 Clipboard retry。
- PRD 要求 Accessibility 授权后刷新仍能触发既有 retry。

建议回写：

- 验收应确认 Accessibility 缺失时仍显示“条目已准备到剪贴板，但需要 Accessibility 才能回到原 App 并发送 Command+V”这类用户可理解反馈。
- 授权后刷新触发 retry 时，成功、失败、仍未授权三种结果至少要有状态反馈或明确记录；不能只在内部重试。

## 8. 建议回写项

建议主 agent 在 PRD 或开发派单中补充以下条目。它们不是 P0/P1，但能降低实现解释偏差。

1. Settings Permissions 验收增加窄宽度检查。
   至少覆盖固定 trailing column、较窄窗口、长 app path、长 bundle ID 和长 recommended action 不出现严重重叠或控件丢失。

2. 三语言长句验收。
   至少抽查中文、英文、日文下权限诊断行、Permission Assist 状态文案、Screen Recording 缺权提示、Clipboard paste permission 提示。

3. 可访问性 label 验收。
   Settings 中隐藏 label 或依赖左侧标题解释的控件，应确认 VoiceOver 能读出具体动作或设置名，尤其是 Refresh / Completed、Restart Blocks、Request Screen Recording、Request Accessibility、Show in Finder。

4. Permission Assist 状态证据模板。
   开发记录应列出 opening / waiting / guiding / checking / granted / failed / cancelled / timedOut 中实际覆盖项和未覆盖原因。

5. Settings 诊断字段层级。
   明确 team ID、usage description、matching running app path、identity issue 是必须直接显示、可展开显示，还是仅要求数据字段不丢失。

6. Clipboard retry 用户反馈。
   明确 pending paste retry 保持 AppState / Clipboard 协调层后，用户仍能看到准备完成、缺权、授权后重试成功或失败的结果反馈。

- 未运行 App、未触发权限请求、未打开系统设置，因此本复审不能证明真实 TCC 流程可用。
- 没有继续扩展抽查全部 presenter 状态和全部本地化条目；已读信息足以判断方案方向，但不能替代后续实物验收。
- 真实授权 / 未授权 / revoked / ad-hoc signing / stable signing 的矩阵受环境影响，后续验收必须诚实标记未覆盖项。
- 如果开发实现为了满足“诊断字段全部可见”而顺手重做 Settings UI，会扩大范围；建议保持 Step 4B 单切片，不做 Settings shell 或视觉信息架构调整。
