# Step 2 项目负责人 PRD 预审 v0

状态：approve-for-role-review
日期：2026-07-07
角色：项目负责人
对象：`产品经理-PRD-v0.md`

## 1. 结论

Step 2 PRD 可以进入角色复审。PRD 聚焦标签与收藏模型替换，覆盖了 R7、R8、C5、C6、C7 和 C16 中属于 Step 2 的部分，未把 Step 1、Step 3、Step 4、Step 5 的能力提前塞回本阶段。

本预审不代表 PRD 最终接受。进入开发前仍需 UI/交互、App 架构、开发、测试/质量复审，并由项目负责人收敛。

## 2. 覆盖判断

已覆盖：

- 多标签：一条记录可关联多个标签。
- 标签管理：颜色、排序、重命名、合并、删除普通标签。
- 右键菜单：添加已有标签、移除已有标签、新建标签并添加到当前条目。
- 标签筛选：按标签筛选记录；收藏作为标签组第一项参与筛选。
- 标签搜索增量：标签名称接入 Step 1 搜索底座。
- 收藏：内置标签、五角星、默认第一、不可删除；收藏按钮等同于添加 / 移除收藏标签。
- 旧逻辑：旧 pinboard / 固定逻辑直接移除，不迁移旧数据。

未发现未归属需求。Step 2 不负责明文展示、OCR、详情编辑、隐私页 App 管理和面板专项布局打磨。

## 3. 角色复审重点

### 3.1 UI/交互设计师

重点检查：

- 标签在条目、筛选组、设置页和右键菜单中的信息结构是否一致。
- 右键菜单中已添加 / 未添加标签状态是否清楚。
- 新建、重名失败、移除、删除、重命名、合并后的反馈是否稳定。
- “收藏”五角星、默认第一、不可删除的视觉表达是否清楚。
- 设置页标签管理不承诺全量视觉重设计，但不能显得粗糙或造成布局跳动。

### 3.2 App 架构师

重点检查：

- Tag 表 / record-tag 关联表或等价模型是否是独立事实源，不是 pinboard 改名。
- 标签唯一性归一化、排序、颜色、内置标签约束和删除 / 合并事务是否清楚。
- 旧 pinboard / pinned 逻辑移除的影响面和回归门禁。
- 标签字段接入 Step 1 搜索索引时的依赖和拆分方式。

### 3.3 开发

重点检查：

- Step 2 是否可以在 Step 1 修订期间先做数据模型和 UI 方案拆解，哪些点必须等待 Step 1 搜索底座稳定。
- 旧固定按钮、旧分组入口、旧 pinboard 状态与新收藏标签的替换影响面。
- 设置页、面板、右键菜单、搜索索引之间的状态同步复杂度。

### 3.4 测试/质量

重点检查：

- 多标签、重名、颜色、排序、重命名、合并、删除普通标签、收藏切换、标签筛选、标签搜索、旧逻辑移除的验收矩阵。
- 合并和删除的边界：重复关联去重、目标标签保留规则、收藏标签不可删除。
- 并发推进 Step 1 / Step 2 时，标签搜索依赖如何测试和分阶段验收。

## 4. 需要复审收敛的问题

以下问题不阻塞进入角色复审，但进入开发前必须由项目负责人收敛：

1. 多标签筛选先做单标签筛选是否足够，还是需要 OR / AND 多选。当前 PRD 默认单标签筛选，这符合保守范围，但需要 UI 和测试确认不会误导。
2. 是否允许普通标签合并到“收藏”。当前 PRD 默认建议允许，但这会产生批量收藏效果；若角色复审认为误操作风险高，项目负责人可改为 Step 2 禁止合并到内置标签。
3. 收藏标签是否允许改色。当前 PRD 建议不可改名，未最终决定改色；需要 UI 复审后收敛。
4. 删除普通标签虽不要求二次确认，但需要最小反馈或撤销策略是否进入 Step 2，需要 UI / 测试给出建议。
5. Step 2 标签搜索接入依赖 Step 1 搜索底座；若 Step 1 未完成，技术方案必须拆成“标签模型先落地，搜索字段后接入”的可验证路径。

将 Step 2 PRD 派发给 UI/交互设计师、App 架构师、开发、测试/质量做只读复审。复审产物写入 `step_2/` 目录，项目负责人收敛后决定是否要求产品经理产出 `产品经理-PRD-v1.md`。
