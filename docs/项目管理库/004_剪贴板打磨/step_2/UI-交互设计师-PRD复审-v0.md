## 2. 总体判断

Step 2 PRD 的方向成立，可以继续推进，但进入开发前建议先回写几处 UI / 交互契约。当前 PRD 已正确收敛到标签与收藏模型，没有把 Step 3 的面板专项布局或 Step 4 / Step 5 能力提前纳入。

PRD 已经做对的部分：

- 明确用独立多标签模型替代旧 pinboard / 固定概念，不把旧模型改名为标签。
- 一个条目可有多个标签，标签支持颜色、排序、重命名、合并和删除。
- “收藏”收敛为内置标签，五角星、默认第一、不可删除，点击收藏即添加 / 移除收藏标签。
- 右键菜单覆盖添加已有标签、移除已有标签、新建标签并添加到当前条目。
- 设置页承担标签实体管理，不要求全量视觉重设计。
- 旧 pinboard / 固定逻辑直接移除，不做旧数据迁移，边界清楚。

需要改的主要问题不在产品方向，而在体验验收还不够具体：标签在面板筛选组、条目、设置页和右键菜单之间的可见结构需要统一；删除、合并、重命名、新建失败后的反馈需要有稳定规则；收藏作为内置标签的编辑和合并边界需要一次性收敛。否则开发可以按模型实现通过，但用户会遇到“我改了标签但不知道影响了哪里”“右键菜单不知道是添加还是移除”“收藏看起来像普通标签但又不能操作”的体验不一致。

## 3. 必须改的问题

### 3.1 标签信息结构需要补齐四个位置的一致表达

PRD 已分别提到条目展示、标签筛选、设置页和右键菜单，但还缺一个统一的信息结构口径。进入开发前需要明确同一套标签在四处如何出现、排序和反馈，避免实现时各自解释。

必须补充：

- 面板筛选组：默认有“全部”或等价未筛选状态；“收藏”第一；普通标签按设置页排序；Step 2 默认只做单标签筛选。
- 条目展示：条目显示已关联标签，顺序与标签组一致；长标签需要截断或换行规则，不得挤压主要内容；收藏可用五角星表达，但仍是标签关系。
- 设置页：标签列表展示颜色、名称、排序、内置状态和可用操作；收藏始终第一且不可删除。
- 右键菜单：同一条记录上已添加 / 未添加标签要清楚区分，且新建标签成功后立即添加到当前条目。

建议直接回写口径：

> Step 2 标签在面板筛选组、条目、设置页和右键菜单中使用同一排序规则：收藏第一，普通标签按用户排序。面板筛选默认是“全部”，Step 2 只支持单标签筛选；选择某标签后列表只展示拥有该标签的记录，并提供清除 / 回到全部路径。条目上的标签展示与标签组排序一致，长标签允许截断但必须保留可识别名称。设置页是标签实体管理入口；右键菜单是当前条目的标签关系管理入口。

验收建议：

- 有 `Work`、`Draft`、`收藏` 三个标签时，筛选组、条目标签、设置页和右键菜单中的相对排序一致。
- 选中 `Work` 后有明确 active 状态，并能回到全部记录。
- 删除当前 active 的普通标签后，筛选状态回到全部或给出明确空 / 已移除反馈，不能停留在失效筛选。

### 3.2 右键菜单的已添加 / 未添加状态需要给出具体交互规则

PRD 已要求右键菜单区分已添加和未添加状态，但没有定义交互形态。这个点是高频操作，如果只写“区分”，实现可能出现同一标签既能添加又能移除、已添加状态不可见、创建失败后状态不清等问题。

必须补充：

- 已添加标签和未添加标签不能混在一个无状态列表里。
- 已添加标签应能一眼看出，并提供“从当前条目移除”的操作。
- 未添加标签应提供“添加到当前条目”的操作。
- 新建标签的失败状态需要停留在当前操作语境，不能静默关闭后不说明原因。

建议采用的交互规则：

- 右键菜单使用一个 `Tags` / `标签` 子菜单。
- 子菜单内已添加标签显示 checkmark 或放入“已添加 / 移除”分组；点击已添加标签表示从当前条目移除。
- 未添加标签显示为普通可选项；点击后添加到当前条目。
- `New Tag...` 固定在子菜单底部；成功后新标签立即关联当前条目；重名或空名失败时保留输入并显示错误。

建议直接回写口径：

> 右键标签菜单必须是当前条目的关系编辑入口。已添加标签显示选中状态，点击表示从当前条目移除；未添加标签显示未选中状态，点击表示添加到当前条目。新建标签入口固定在标签子菜单底部；新建成功后立即添加到当前条目；空名或重名失败时不创建标签、不改变条目关系，并在当前输入位置展示错误。

验收建议：

- 一条记录已有 `Work` 时，右键菜单中 `Work` 明确显示为已添加状态；点击后移除。
- 一条记录没有 `Draft` 时，右键菜单中 `Draft` 明确显示为可添加状态；点击后添加。
- 新建 ` work ` 命中已有 `Work` 时，显示重名错误，当前记录标签关系不变。

### 3.3 新建、删除、重命名、合并的反馈需要形成最小状态契约

PRD 对重名失败有规则，对合并有模型规则，但对用户可见反馈还不够稳定。尤其删除和合并会影响多条记录，即使本阶段不要求二次确认，也需要让用户理解影响范围。

必须补充：

- 新建失败：错误文案、输入保留、关系不变。
- 重命名失败：错误文案、旧名称继续有效、筛选 / 搜索不被半更新。
- 删除普通标签：操作前或操作位置要能看出“会从所有记录移除此标签”；成功后有轻量反馈。
- 合并普通标签：用户必须能看清源标签、目标标签和结果；完成后有反馈。
- 操作失败：不应造成条目标签、筛选组、设置页之间状态不一致。

建议采用的交互规则：

- 设置页里每个普通标签行显示名称、颜色、排序控制和操作菜单。
- 删除不需要二次确认弹窗，但删除动作文案应带影响说明，例如“删除标签并从所有记录移除”。
- 合并使用小型确认面或 popover，不建议直接用单击菜单项立即执行。
- 合并结果保留目标标签名称、颜色和排序，被合并标签消失。

建议直接回写口径：

> 标签管理操作必须有最小反馈。创建 / 重命名空名或重名时，在输入控件附近展示错误并保留用户输入；删除普通标签时，界面文案必须说明该标签会从所有记录移除，成功后显示轻量成功反馈；合并标签时，确认面必须展示源标签、目标标签和结果说明，成功后展示“已合并到 {目标标签}”类反馈。所有失败都不得改变已有标签关系。

验收建议：

- 重命名 `Draft` 为 `work` 被阻止，`Draft` 仍显示在条目、筛选组和设置页。
- 删除 active 标签后不出现已删除标签仍被选中的状态。
- 合并 `Draft` 到 `Work` 后，条目、筛选组、右键菜单和搜索字段同步更新。

### 3.4 收藏标签的可编辑边界需要收敛

PRD 已明确收藏不可删除、默认第一、五角星，但仍把改色、合并到收藏留给复审。UI 侧建议在 Step 2 先把收藏作为稳定内置标签，不开放改名、删除、排序，也不把普通标签合并到收藏作为默认能力。

必须由项目负责人收敛：

- 收藏是否允许改色。
- 普通标签是否允许合并到收藏。
- 收藏是否出现在右键标签菜单中，以及点击已添加收藏是否等同于取消收藏。

UI 推荐口径：

- 收藏不可改名、不可删除、不可排序。
- 收藏不作为被合并标签。
- Step 2 暂不允许普通标签合并到收藏，避免一次合并变成批量收藏这种高影响操作。
- 收藏可以在右键菜单中作为第一项标签出现；添加 / 移除收藏与点击五角星保持同一语义。
- 收藏颜色建议固定或跟随系统强调色，不进入普通色板，降低“为什么这个内置标签又能改一半”的认知成本。

建议直接回写口径：

> “收藏”是内置标签，不可改名、不可删除、不可排序，始终显示在标签组第一位并使用五角星图标。Step 2 中普通标签不合并到“收藏”；如后续需要批量收藏，应作为独立能力再评估。右键菜单中“收藏”可作为第一项标签关系出现，添加 / 移除语义与条目五角星按钮一致。

如果项目负责人决定允许合并到收藏，建议最低要求：

- 合并确认面必须写明“合并后这些记录将被收藏”。
- 合并结果反馈必须说明新增收藏关系数量。
- 测试必须覆盖已有收藏和未收藏记录的去重。

### 3.5 设置页标签管理需要补最小质感与可访问性验收

PRD 已写设置页支持查看和管理标签实体，但“基础质感”还需要可验收。Step 2 不应做设置页全量视觉重设计，但标签管理不能只是技术表单堆叠。

必须补充：

- 标签行的基础结构：颜色 swatch、标签名称、内置标识、排序控制、操作入口。
- 收藏行的禁用操作表达：删除、改名、排序等不可用操作需要禁用或隐藏，并有可理解原因。
- 空状态：没有普通标签时，设置页仍显示收藏，并提供新建普通标签入口。
- 长标签名、长错误文案、中文 / 英文 / 日文长句不挤压操作列。
- 可访问性：颜色不能是唯一信息；五角星、颜色 swatch、删除 / 合并 / 重命名操作需要可读 label。

建议直接回写口径：

> 设置页标签管理采用稳定行结构：颜色 swatch、标签名称、内置状态、排序控制和操作菜单。收藏行固定第一，普通标签从第二行开始排序。普通标签为空时，仍展示收藏行和新建标签入口。颜色只作为辅助识别，界面必须同时显示标签名称；VoiceOver 能读出标签名、是否收藏 / 内置、颜色、排序位置和可用操作。

验收建议：

- 标签名很长时，名称截断或换行不覆盖颜色、排序和操作列。
- 收藏行不可删除，禁用原因可通过文案、tooltip 或可访问性 label 读出。
- 色板选择后，设置页、条目标签和筛选组同步更新，且不只依赖颜色传达标签身份。

## 4. 可后续优化的问题

### 4.1 多标签 AND / OR 筛选可后续做

PRD 默认单标签筛选是合理的。Step 2 只要把单选状态、清除路径和 active 标签表达写清楚，不需要提前做 AND / OR。

后续可优化：

- 多选标签筛选。
- AND / OR 切换。
- 标签计数和筛选命中数量展示。

### 4.2 标签颜色色板数量可由 UI/技术方案细化

PRD 要求受控色板是正确方向。Step 2 不必在 PRD v0 写死全部色值，但需要明确不能只靠颜色传达含义。

后续可优化：

- 预设 8-12 个系统友好的色板。
- 深浅模式下的对比度验收。
- 色弱可辨识检查。

### 4.3 标签搜索命中解释可不进入 Step 2

PRD 要求标签名称进入搜索增量即可。搜索结果是否显示“命中标签”可以等 Step 1 搜索底座和 Step 3 面板布局稳定后再做。

后续可优化：

- 搜索结果中显示命中标签来源。
- 高亮命中的标签名。
- 标签搜索和正文搜索权重可视化解释。

### 4.4 删除撤销可以后续评估

本阶段不要求删除前二次确认。UI 侧不强制 Step 2 增加 undo，但建议最终验收至少确认删除后的成功反馈和状态同步。

后续可优化：

- 删除标签后的短时撤销。
- 最近删除标签恢复。
- 批量管理。

## 5. PRD v0 建议新增的验收门槛

### 5.1 标签信息结构

必须验收：

- 筛选组、条目标签、设置页、右键菜单使用同一排序规则。
- 收藏固定第一，普通标签按用户排序。
- Step 2 单标签筛选有 active 状态和清除 / 回到全部路径。
- 删除或重命名 active 标签后，筛选状态不悬空。

### 5.2 右键菜单

必须验收：

- 已添加标签和未添加标签状态可区分。
- 已添加标签点击后移除当前条目关系。
- 未添加标签点击后添加当前条目关系。
- 新建标签成功后立即添加到当前条目。
- 新建空名 / 重名失败时显示错误，且条目关系不变。

### 5.3 设置页标签管理

必须验收：

- 标签行包含颜色、名称、排序和操作入口。
- 收藏行固定第一，不可删除，禁用状态可理解。
- 普通标签可改色、排序、重命名、合并、删除。
- 长标签名、长错误文案和窄宽度下操作列不重叠。
- 颜色不是唯一识别方式。

### 5.4 收藏

必须验收：

- 收藏显示五角星，默认第一。
- 收藏不可删除、不可改名、不可排序。
- 点击未收藏条目的五角星后添加收藏标签；再次点击移除。
- 右键菜单中的收藏操作与五角星状态同步。
- 按收藏筛选只显示拥有收藏标签的记录。

### 5.5 操作反馈

必须验收：

- 创建、重命名、删除、合并都有成功或失败反馈。
- 删除标签后，该标签从所有关联条目、筛选组和右键菜单中移除。
- 合并标签后，目标标签保留名称、颜色和排序，被合并标签消失。
- 失败操作不产生半更新状态。

### 5.6 可访问性和文案

必须验收：

- VoiceOver 能读出标签名、收藏状态、已添加 / 未添加状态、删除 / 合并 / 重命名动作。
- 五角星不能只依赖图形，需有收藏 / 取消收藏 label。
- 错误文案使用用户语言，例如“标签名称已存在”“标签名称不能为空”，避免暴露内部字段名。
- 中文、英文、日文长标签名和长错误文案不挤压主要操作。

## 6. 非目标边界确认

PRD 当前正确排除了以下内容，UI 侧不建议改回 Step 2：

- 明文展示和 OCR 搜索底座。
- 面板筛选 hover 安全区、搜索框宽度、条目密度和选中反馈专项重做。
- 详情编辑、保存 / 取消和富文本编辑。
- 隐私页真实 App 清单。
- 全量面板视觉重设计。
- 旧 pinboard / 固定数据迁移。
- 批量删除标签、删除前二次确认、自动清理空标签。

需要注意：Step 2 新增标签筛选和右键菜单会接触面板主路径，但本阶段只要求控件语义和状态稳定，不要求解决 Step 3 的布局专项问题。长标签和窄宽度只需作为“不重叠、不误导”的保底验收。

## 7. 对项目负责人的建议

建议结论：`approve-with-changes`。

建议要求产品经理回写以下 5 个必须改问题后，再由项目负责人判断是否进入开发准备：

1. 补齐标签在筛选组、条目、设置页和右键菜单中的统一信息结构与排序规则。
2. 明确右键菜单中已添加 / 未添加标签的具体状态和点击语义。
3. 补齐创建、重名失败、删除、重命名、合并后的最小反馈与失败不半更新规则。
4. 收敛收藏标签的编辑边界，UI 推荐 Step 2 禁止普通标签合并到收藏，收藏不可改名 / 删除 / 排序。
5. 补齐设置页标签管理的最小行结构、禁用状态、长文本和可访问性验收。

这些修改不改变 Step 2 的阶段范围，也不要求提前做 Step 3 的视觉布局重设计。它们主要把现有模型要求翻译成可实现、可测试、可被用户理解的交互契约。
