# Step 2 开发技术方案复审 v0

状态：approve-with-changes
日期：2026-07-07
角色：开发
对象：`App架构师-技术方案-v0.md`

## 1. 结论

Step 2 技术方案主线可实现，且与 PRD v1 的收敛口径一致：用 Tag / RecordTag 独立事实源替代旧 pinboard / pinned，以 Favorite built-in tag 表达收藏，用原子标签事务和 fail-closed verifier 防止旧事实源继续参与当前行为。

开发结论为 `approve-with-changes`。方案可以进入 v1 修订，但开发前需要把以下工程契约写硬：`AppDatabase` V2/migration 策略、Normalizer 的确定算法、`ClipboardTagRepository` 形态、`ClipboardTagStore` 与 `ClipboardStore` / `AppModel` 的单事实源边界、delete/merge mutation result、`preservePinned` / `clearUnpinned` 的 Step 2 替换，以及 P13B 与旧 P8/P9/P11 的迁移断言。

## 2. 当前代码事实

抽样核对当前代码后，技术方案识别的影响面成立：

- `AppDatabase` 仍创建 `clipboard_items.pinned`、`clipboard_pinboards`、`clipboard_pinned_metadata` 和 pinned 相关索引。
- `ClipboardRepository` 仍有 `pin`、`unpin`、`move(recordID:toPinboard:)`、`renamePinnedRecord`、`clearUnpinned`、`preservePinned` 和 pinboard metadata API。
- `ClipboardStore` / `ClipboardController` / `ClipboardFilterState` 仍围绕 `pinboards`、`pinnedMetadata`、`pinboardID`、`pinnedCount` 和 pinboard search/filter 工作。
- `ClipboardReadModel`、面板、设置页和 P8/P9/P11 等 verifier 仍有旧 pinned / pinboard 语义。

因此 Step 2 不能只做 UI 改名。实现必须建立新 Tag / RecordTag 当前事实源，并让旧字段即使短期保留也不参与 UI、筛选、收藏按钮、标签搜索字段、设置策略或 ok evidence。

## 3. 必须改

### 3.1 AppDatabase V2 / migration 要写成硬契约

技术方案建议新增 V2 是正确方向，但开发前需要明确：

- `AppDatabase` 是否 bump `PRAGMA user_version`，以及 v1 -> v2 的迁移入口在哪里。
- `clipboard_tags`、`clipboard_record_tags` 的创建和 favorite seed 是否在同一个迁移流程中完成。
- 旧 `clipboard_items.pinned`、`clipboard_pinboards`、`clipboard_pinned_metadata` 是否仅保留为 legacy storage；如果保留，哪些 active API 禁止再读写。
- 开发期已有数据库打开时是否允许保留旧表但不迁移数据，还是测试 fixture 使用新库重建。
- foreign key / cascade 是否在当前 SQLite connection 中持续启用；否则 RecordTag cascade 只是 schema 文案，不是运行时事实。

推荐口径：

> Step 2 使用 `AppDatabase` V2。V2 创建 `clipboard_tags` / `clipboard_record_tags`，seed 唯一 favorite built-in tag，不迁移旧 pinned/pinboard 数据。旧 pinned/pinboard 表和字段如保留，仅作为 legacy storage，active repository/store/view/verifier 不得以其作为当前事实源。

P13B 应断言 V2 schema、favorite unique index、record-tag unique key、foreign key cascade 或等价删除逻辑均存在。

### 3.2 Normalizer 需要固定算法，而不是保留二选一

方案中 “NFC or NFKC” 不能留到实现时临场判断。开发建议 v1 固定为：

- NFKC normalization，覆盖常见全角/半角差异。
- trim 首尾空白和换行。
- 内部 Unicode whitespace run 折叠成单个 ASCII space。
- 空结果失败。
- normalization 后仍含 control character 失败。
- locale-independent case folding，使用稳定 locale，不跟随系统语言。
- reserved aliases 至少覆盖 `favorite`、`收藏` 及其 trim/case/width 变体。

如果 App 架构师不采用 NFKC，也应在方案 v1 明确替代算法，并要求 normalizer fixture 覆盖：`Work` / ` work ` / `WORK`、连续空白、全角英文、空名、控制字符、`favorite`、`收藏`。

### 3.3 Repository 建议独立为 `ClipboardTagRepository`

开发建议采用独立 `ClipboardTagRepository`，而不是把所有 tag API 做成 `ClipboardRepository` extension。

理由：

- 旧 `ClipboardRepository` 已同时承担 payload、FTS、pinboard、policy pruning 等职责，继续扩展会让 Step 2 事务和旧 pinned 退出边界更难验证。
- Tag / RecordTag 是独立事实源，但必须共享同一个 `AppDatabase` / SQLite transaction helper；独立 repository 可以更清晰地暴露标签事务结果。
- P13B 更容易 fail-closed 检查 View 不直接写 DB、Store 不直接拼旧 pinboard 事实。

可接受的折中：

- 使用 `ClipboardTagRepository` 独立文件和 public API。
- 共享 `AppDatabase` connection / transaction helper。
- 如需要与 record deletion / prune 集成，由 `ClipboardRepository` 调用 tag repository 的 cleanup 或共享低层 helper；不要让 View / Store 同时调用两套互相不知道的删除逻辑。

### 3.4 Mutation API 必须返回 affected recordIDs

当前方案写了 emit search invalidation，但 API 形状仍偏口头。开发建议每个会影响记录标签字段的 mutation 返回明确结果：

```text
ClipboardTagMutationResult
- tags: [ClipboardTag] or changedTagIDs
- affectedRecordIDs: [String]
- removedTagIDs: [String]
- selectedTagTransition: none / clearIfSelected(tagID) / switchIfSelected(source, target)
```

命名不强制，但需要满足：

- create-and-attach、add、remove 返回当前 recordID。
- rename 返回所有关联该 tag 的 recordIDs。
- delete 返回删除前关联的 affected recordIDs。
- merge 返回 source 和 target 去重后的 affected recordIDs。
- updateColor / reorder 不需要 search invalidation，但需要刷新 tag list。

search invalidation / reindex hook 应只消费 `affectedRecordIDs`，避免 Store 或 View 二次查询旧状态推断。

### 3.5 `ClipboardTagStore` 必须是 tag 事实源，AppModel 只做 facade

方案允许 `ClipboardStore` 持有 `ClipboardTagStore`，这个方向可以接受，但需要更明确：

- `ClipboardTagStore` 是 `tags`、`recordTags`、`selectedTagID`、tag operation state/error 的唯一事实源。
- `ClipboardStore` 继续负责 records、payload read、preview/search/list 状态；可以桥接 `ClipboardTagStore.objectWillChange`，但不重复保存 tag arrays 或 selected tag。
- `AppModel` 只提供 coordinator facade、status banner 和跨 store 调用，不保存 tag facts。
- View 只能通过 `ClipboardTagStore` / `ClipboardStore` / `AppModel` facade 操作，不直接访问 repository 或旧 pinned/pinboard 状态。
- `ClipboardController.filteredRecords` 需要从 `pinboardID` 迁移到 `selectedTagID + recordTags`，并且 active filter count 不再把 pinboard 当作一类 filter。

如果实现为了减少改动把 tag state 暂放 `ClipboardStore`，P13B 必须仍能证明它是单一 tag 事实源，且没有与 `ClipboardTagStore` 并存双写。

### 3.6 delete / merge 需要同时覆盖 UI selection 和 search invalidation

方案已写 transaction 步骤，v1 还应补充 store 层成功后状态切换：

- 删除当前筛选 tag：transaction 成功后 `selectedTagID = nil`，失败保持原筛选。
- 合并当前筛选 source tag：transaction 成功后 `selectedTagID = targetTagID`，失败保持 source。
- 删除 / 合并非当前筛选 tag：不改变 selected tag。
- 删除 / 合并应先在 transaction 内捕获 affected recordIDs，再删除 source rows；否则提交后无法可靠重建 invalidation 集合。
- search invalidation 可以在 DB transaction 内写 dirty marker，或 transaction 成功后调用 adapter；但必须定义失败策略，不能出现 DB 成功、Store 失败、索引无标记且开发记录宣称完成。

### 3.7 `preservePinned` / `clearUnpinned` 应在 Step 2 改为 Favorite 语义

这里不建议留作后续 residual。PRD v1 已要求用户可见旧 pinboard / pinned / 固定独立模型退出；当前设置页和 repository 里还有 `preservePinned`、`clearUnpinned`、`clipboard.policy.clearUnpinned` 等 active 语义。如果 Step 2 不处理，会产生两个问题：

- UI 和 verifier 仍能以旧 pinned 作为当前策略事实源。
- repository prune 会继续保护旧 `clipboard_items.pinned`，而不是 favorite RecordTag。

推荐口径：

> Step 2 将用户可见和 repository policy 语义替换为 `preserveFavorite` / `clearUnfavorited` 或等价命名；保留策略时只基于 favorite RecordTag 判断。旧 `preservePinned` / `clearUnpinned` 如因兼容暂存，只能是 deprecated adapter，不出现在 active UI、Store facade、P13B ok evidence 或开发记录通过项中。

如果项目负责人决定不在 Step 2 改 policy，技术方案必须明确隐藏旧 UI，并把 repository 旧行为列为 P1 residual；开发不建议这样进入实现。

### 3.8 P13B 与旧 P8/P9/P11 迁移要明确红绿顺序

P13B 可落地，但建议 v1 写成 P13B-first：

1. 先新增 P13B，确认当前基线因缺少 Tag / RecordTag、仍有 active pinboard/pinned 事实源而低敏 FAIL。
2. Step 2A 让 schema / repository / normalizer / favorite bootstrap 相关断言转绿。
3. Step 2B 让 Store / AppModel facade / selectedTagID / objectWillChange 相关断言转绿。
4. Step 2C 让 UI active token、right-click、filter、settings 相关断言转绿。
5. Step 2D 让 search invalidation contract 和旧 P8/P9/P11 当前事实源迁移转绿。

旧 verifier 迁移建议：

- `p9a_clipboard_repository_storage_smoke.py`：增加 tags/favorite repository smoke，旧 pinboard smoke 只能 baseline reference。
- `p9b_clipboard_appstate_repository_integration_checks.py`：改为 AppModel/ClipboardStore/ClipboardTagStore tag facade，不再找 `togglePin` / `renamePinnedRecord` 作为 ok。
- `p8_clipboard_product_polish_checks.py`、`p8i_settings_clipboard_system_checks.py`：改查 favorite row、tag filter、settings tag management、right-click tag menu。
- `p11e_clipboard_hardening_checks.py`：只保留低敏输出和 payload boundary 相关断言；旧 pinned displayName 不作为 Step 2 tag acceptance。
- 任何旧 story/archive/project docs 只能放 `baseline_reference`，不得进入 `ok` 判定。

## 4. 可优化

- `ClipboardTagStore` 可拆成 `Features/Clipboard/Tags/` 子目录，避免再次把 tag management 全塞进单个 `ClipboardStore.swift`。
- `ClipboardSettingsPane` 的 tag management 建议拆子 view：tag row、tag editor、merge selector、color swatch、sort controls；否则 Step 2 很容易形成大文件返工。
- `recordTags` 可按 visible recordIDs lazy load；不要在面板每次刷新时全量 join 所有历史记录的 tags。
- right-click menu 新建标签失败反馈可以复用 Store error state，不需要引入全局 alert。
- 标签颜色 token 应使用受控 enum/string allowlist，P13B 可静态检查 palette token，不需要测试真实颜色。
- Step 1 search document 未落地时，先落 no-op `ClipboardTagSearchInvalidating` adapter；但开发记录和验收状态必须标 `end-to-end tag search pending Step 1`。

## 5. 可吸收到方案 / 开发的建议拆分

### 5.1 Step 2A：Schema / Normalizer / Repository

建议交付：

- `ClipboardTag`、`ClipboardRecordTag`、`ClipboardTagBuiltInKind`。
- `ClipboardTagNameNormalizer` 和 fixture。
- `AppDatabase` V2 migration 与 favorite seed。
- `ClipboardTagRepository`，包含 create/rename/color/reorder/delete/merge/add/remove/toggleFavorite。
- `ClipboardTagMutationResult` 或等价 affected recordIDs 输出。
- P13B 红灯转 schema/repository 部分绿。

### 5.2 Step 2B：Store / AppModel / Filter State

建议交付：

- `ClipboardTagStore` 作为 tag facts source。
- `selectedTagID` 替代 `ClipboardFilterState.pinboardID`。
- `ClipboardStore` 桥接 tag store，但不复制 tag facts。
- `AppModel` thin facade 和 status/error mapping。
- delete/merge success 后 selected tag clear/switch。

### 5.3 Step 2C：Panel / Right-click / Settings

建议交付：

- `ClipboardFilterBarView` 使用 tags/favorite。
- record card/row favorite button 改为 favorite RecordTag。
- right-click menu 支持 checked tags、add/remove、新建并 attach。
- settings tag management 替换旧 pinboards section。
- 用户可见旧 pinboard / pinned / fixed 独立模型退出。

### 5.4 Step 2D：Policy / Search Contract / Verifier Migration

建议交付：

- `preserveFavorite` / `clearUnfavorited` 或等价策略替换。
- tag search projection / invalidation hook。
- 若 Step 1 search document 未实现，使用 no-op adapter + residual risk。
- P13B 全绿。
- P8/P9/P11 当前事实源迁移，旧证据降级 baseline。

## 6. 残余风险

- Step 1 搜索底座尚未最终进入实现时，Step 2 只能验收标签字段契约，不能宣称端到端标签搜索完成。
- 旧 pinned/pinboard 字段如果短期保留，静态扫描会持续发现旧 token；P13B 必须区分 legacy storage 与 active UI/store/repository path。
- Normalizer 一旦进入 DB unique key，后续改算法会有迁移成本；必须在 v1 方案和开发记录中固定。
- `preserveFavorite` 会触及清理策略和设置页文案，属于 Step 2 必要影响面，不应被误判为范围扩大。
- 标签菜单和设置页管理的真实 UI 交互复杂度高于旧 pinboard move；若自动化无法覆盖所有 macOS menu 场景，开发记录和验收记录需要列为受限，而不是写成已完全覆盖。
