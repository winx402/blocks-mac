# 测试/质量 PRD 复审：Step 2 标签与收藏模型替换

日期：2026-07-07
角色：测试/质量
复审对象：`产品经理-PRD-v0.md`、`项目负责人-PRD预审-v0.md`，并对照 `step.md` 与 `需求覆盖矩阵-v0.md`

## 结论

`approve-with-changes`

Step 2 PRD 的阶段边界基本正确：聚焦多标签、收藏、标签管理、标签筛选、标签搜索增量和旧 pinboard / 固定逻辑移除，没有把 Step 1 明文展示 / OCR、Step 3 面板布局、Step 4 详情编辑、Step 5 隐私 App 管理提前塞回本阶段。

当前主要缺口是验收契约仍不够硬：标签搜索依赖 Step 1 的分阶段验收、删除 / 合并的边界、收藏内置标签的可变更范围、标签持久化和旧逻辑移除的负向证据都需要在进入开发前补清。否则实现完成后测试会无法稳定判断通过或失败。

## 已覆盖且可作为验收基础的点

1. 多标签模型：
   - 一条剪贴板记录可以关联多个标签。
   - 同一记录不能重复关联同一标签。
   - 标签关系用于筛选、搜索、展示和右键菜单。

2. 重名规则：
   - 创建和重命名前 trim。
   - trim 后不能为空。
   - 默认大小写不敏感重名校验。
   - `收藏` 名称不能被普通标签占用。

3. 标签管理：
   - 普通标签支持颜色、排序、重命名、合并、删除。
   - 设置页可查看和管理标签实体。
   - 颜色来自受控色板或等价受控选项。
   - `收藏` 始终在标签组第一位。

4. 收藏模型：
   - 收藏是内置标签，不是旧固定状态或第二套模型。
   - 五角星图标、默认第一、不可删除。
   - 点击收藏按钮等同于添加 / 移除 `收藏` 标签。

5. 右键菜单：
   - 添加已有标签。
   - 移除当前记录已有标签。
   - 新建标签并添加到当前记录。
   - 新建失败不应改变当前记录标签关系。

6. 旧逻辑移除：
   - 旧 pinboard / 固定概念不再作为用户可见模型出现。
   - 不迁移旧 pinboard / 固定数据。
   - 不要求旧分组名、旧固定项兼容。

## 必须改

1. 补清标签搜索依赖 Step 1 的分阶段验收。
   Step 2 PRD 正确指出标签搜索依赖 Step 1 搜索底座，但当前还不能直接作为最终验收标准。建议写成两层 gate：
   - Step 1 搜索底座未最终接受时：Step 2 至少验收标签字段模型、索引输入契约、重命名 / 合并 / 删除后的索引更新事件或等价接口，不要求端到端搜索框命中。
   - Step 1 搜索底座已接受后：必须端到端验收搜索标签名可命中记录，重命名后旧标签名不再命中，合并后源标签名不再命中，删除后标签名不再命中。
   - 最终接受 Step 2 前，需要项目负责人明确是否允许“标签模型先接受、标签搜索端到端延后到 Step 6”。如果允许，必须把它写成未完成项，而不是默认为通过。

2. 决定标签筛选是单选还是多选。
   PRD 目前建议先采用单标签筛选，但仍保留 OR / AND 待技术方案确认。测试需要固定规则：
   - 若 Step 2 只做单标签筛选，则 UI 不应呈现多选语义，也不验收 OR / AND。
   - 若支持多选，则必须明确 OR 还是 AND，并补充多标签筛选组合样例。
   建议 Step 2 固定为单标签筛选，避免把 Step 3 交互复杂度提前引入。

3. 补清标签持久化验收。
   PRD 描述了标签实体和 record-tag 关系，但没有明确跨刷新 / 重启 / repository reload 后必须保持。标签和收藏属于核心数据模型，必须验收：
   - 新建标签、颜色、排序、重命名结果可持久化。
   - 记录与标签关系可持久化。
   - 收藏标签关系可持久化。
   - 合并和删除后的结果可持久化。
   - fixture / import / repository reload 不产生重复内置 `收藏` 标签。

4. 补清删除普通标签的边界。
   当前 PRD 写明不要求二次确认、批量删除、自动清理空标签，这可以接受。但删除行为本身需要可判定：
   - 删除普通标签后，该标签从设置页、筛选列表、右键菜单和条目展示中消失。
   - 该标签与所有记录的关联一并移除，但记录本身不被删除。
   - 该标签名称不再作为搜索字段命中。
   - 当前正在按该标签筛选时，删除后的 UI 状态应明确，例如清空筛选、回到全部或显示无结果。
   - 删除失败时不应出现“标签实体删除但关系残留”或“关系删除但标签仍可见”的半完成状态。
   - `收藏` 标签删除入口不可用，底层也应拒绝删除。

5. 补清合并标签的边界。
   PRD 已覆盖 Draft 合并到 Work 的基本样例，但还需要边界：
   - 源标签和目标标签不能相同。
   - 目标标签保留名称、颜色和排序。
   - 源标签关联全部转移到目标标签。
   - 同时拥有源标签和目标标签的记录合并后只保留一个目标标签关联。
   - 源标签从设置页、筛选列表、右键菜单、条目展示和搜索字段中消失。
   - 当前正在按源标签筛选时，合并后的筛选状态如何处理需要明确。
   - 合并失败必须保持原状态，不允许部分记录已转移、部分未转移。

6. 决定是否允许合并到 `收藏`。
   项目负责人预审已把该点列为进入开发前需收敛问题。测试侧判断：若允许普通标签合并到 `收藏`，这等同批量收藏，必须有明确文案和验收样例；若不允许，则 UI 与底层都应拒绝。当前 PRD 的“默认建议允许”不足以直接进入开发。

7. 决定 `收藏` 标签是否允许改色。
   PRD 已建议不可改名、不可删除，但改色未定。测试需要明确：
   - 若允许改色，改色后设置页、筛选项、条目展示和持久化均要验收。
   - 若不允许改色，则设置页应禁用或隐藏改色入口，底层拒绝变更。
   该点不要求用户层面澄清，但需要项目负责人 / UI 在开发前收敛。

8. 补旧 pinboard / 固定逻辑移除的负向清单。
   “用户可见界面不再出现旧 pinboard / 固定”方向正确，但自动化和验收需要更具体的 forbidden evidence：
   - UI 文案中不再出现旧 `pinboard`、`固定`、`Pinned` 作为独立模型。
   - 不再存在与收藏标签并列的旧固定筛选入口。
   - 收藏按钮不再写入旧 pinned 独立事实源。
   - 如果代码内部短期保留兼容字段，必须不参与当前 UI / 搜索 / 筛选事实源，并在开发记录中说明。

## 可直接吸收的建议口径

以下内容可作为产品经理修订 PRD 或后续测试方案的输入，不需要扩展 Step 2 范围。

1. 标签筛选推荐口径：
   - Step 2 只支持单标签筛选。
   - UI 不展示多选、AND 或 OR 语义。
   - 验收 pass：选择 `Work` 后只展示拥有 `Work` 的记录；切换到 `Draft` 后只展示拥有 `Draft` 的记录。
   - 验收 fail：同一时刻可选择多个标签但 PRD 未定义 AND / OR；或 UI 暗示多选但结果不可预测。

2. 标签搜索推荐口径：
   - Step 2 只新增“标签名称”作为搜索字段，不改变 Step 1 已定义的正文、OCR、URL、来源、文件名、类型等搜索字段。
   - Step 1 未接受前，Step 2 通过“标签字段索引契约”验收；Step 1 接受后，再做端到端搜索框验收。
   - 验收 fixture 的正文不得包含标签名，避免正文命中伪装成标签命中。
   - pass：记录 A 正文不含 `Work`，但关联 `Work` 标签；搜索 `Work` 命中 A。
   - fail：只有正文包含 `Work` 的记录能命中，而仅有 `Work` 标签的记录不能命中。

3. 持久化推荐口径：
   - 标签实体、颜色、排序、内置标记、record-tag 关系和收藏关系必须持久化。
   - repository reload / app relaunch 后不重复创建 `收藏` 标签。
   - pass：创建 `Work`、给记录 A 添加 `Work` 与 `收藏`、改色和排序后 reload，状态保持一致。
   - fail：reload 后标签丢失、关系丢失、颜色排序回退，或出现多个 `收藏`。

4. 删除普通标签推荐口径：
   - 删除普通标签会删除标签实体，并移除它与所有记录的关系，不删除记录本体。
   - 删除当前正在筛选的标签后，推荐回到“全部记录”筛选状态；至少不得停留在已不存在的标签筛选上。
   - pass：删除 `Draft` 后，`Draft` 从设置页、筛选项、右键菜单、条目展示和标签搜索字段消失，记录仍存在。
   - fail：`Draft` 标签消失但记录仍显示 `Draft`；或记录关系被清除但筛选项仍有 `Draft`；或删除标签误删记录。

5. 合并普通标签推荐口径：
   - Step 2 推荐只允许普通标签合并到普通标签。
   - 源标签与目标标签不能相同。
   - 目标标签保留名称、颜色和排序；源标签删除；源关系转移到目标；重复关系去重。
   - 若当前正在筛选源标签，合并完成后推荐切换到目标标签筛选，延续用户上下文。
   - pass：`Draft` 合并到 `Work` 后，所有原 `Draft` 记录拥有 `Work`，`Draft` 不再可见或可搜。
   - fail：源标签仍可见；目标标签颜色 / 排序被源标签覆盖；同一记录出现重复 `Work`；部分记录转移、部分未转移。

6. 合并到 `收藏` 推荐口径：
   - 测试/质量建议 Step 2 禁止普通标签合并到 `收藏`，原因是这等同批量收藏，误操作影响大，且 PRD 明确不做二次确认。
   - 如果项目负责人仍决定允许，应补充强提示文案和专门验收样例：这些记录将被收藏，源标签将删除。
   - pass（禁止口径）：合并目标列表不提供 `收藏`，底层也拒绝以 `收藏` 为目标的合并请求。
   - fail：UI 禁止但底层允许；或允许合并到 `收藏` 但无明确批量收藏提示。

7. `收藏` 可变更范围推荐口径：
   - Step 2 推荐 `收藏` 不可删除、不可重命名、不可改色、不可调整到非第一位。
   - 用户只能通过收藏按钮或标签操作给记录添加 / 移除 `收藏` 标签关系。
   - pass：设置页展示 `收藏`，但删除、改名、改色、排序控件禁用或隐藏；底层拒绝这些变更。
   - fail：`收藏` 被普通标签占名、被删除、被改名后收藏按钮失去语义，或排序后不在第一位。

8. 旧逻辑移除推荐口径：
   - Step 2 不迁移旧 pinned / pinboard 数据，也不展示迁移提示。
   - 用户可见模型只剩“标签”和内置 `收藏`。
   - pass：界面没有旧 pinboard / pinned / 固定独立入口；收藏按钮变更的是 `收藏` 标签关系。
   - fail：出现收藏和固定两个并列状态；旧 pinned 状态仍影响筛选、排序或搜索。

9. 失败原子性推荐口径：
   - 新建、重命名、删除、合并、改色、排序任一操作失败时，标签实体和 record-tag 关系都保持操作前状态。
   - pass：制造重名、空名或合并失败后，标签列表、记录关系、筛选结果和搜索字段均未变化。
   - fail：错误提示出现但数据部分变更。

## 建议的验收矩阵

1. 多标签与去重：
   - 记录 A 添加 `Work` 和 `Draft`，条目显示两个标签。
   - 按 `Work` 筛选命中 A；按 `Draft` 筛选也命中 A。
   - 对 A 再次添加 `Work` 不产生重复关联。
   - 移除 A 的 `Draft` 后，A 仍保留 `Work`，不再被 `Draft` 筛选命中。

2. 重名与输入归一化：
   - 已存在 `Work` 时，新建 `work`、` Work `、`WORK` 均失败。
   - 空白名称失败。
   - 失败不创建标签、不改变任何记录的标签关系。
   - 普通标签不能命名为 `收藏`，包括首尾空格和大小写等归一化场景。

3. 颜色、排序、重命名：
   - 修改普通标签颜色后，设置页、筛选项和条目展示一致更新。
   - 调整普通标签顺序后，`收藏` 仍第一，普通标签按用户顺序展示。
   - 重命名 `Draft` 为 `Review` 后，设置页、筛选项、右键菜单、条目展示和标签搜索字段同步更新。
   - 重命名失败不改变旧名称或记录关系。

4. 删除普通标签：
   - 删除 `Draft` 后，所有记录上的 `Draft` 关系移除，记录本身保留。
   - `Draft` 从设置页、筛选项、右键菜单和条目标签展示消失。
   - 搜索 `Draft` 不再因标签字段命中这些记录。
   - 删除空标签也只删除标签实体，不影响记录。
   - 删除 `收藏` 的入口不可用或被拒绝。

5. 合并：
   - `Draft` 合并到 `Work` 后，原 `Draft` 记录拥有 `Work`。
   - 同时有 `Draft` 和 `Work` 的记录合并后只保留一个 `Work`。
   - `Draft` 消失，`Work` 保留原名称、颜色、排序。
   - 搜索 `Draft` 不再因标签字段命中；搜索 `Work` 命中合并后的记录。
   - 合并失败不产生部分迁移。
   - 合并到 `收藏` 的允许 / 禁止路径按最终 PRD 决策验收。

6. 收藏：
   - 初始存在唯一 `收藏` 标签，五角星，第一位。
   - `收藏` 不可删除，不可被普通标签重名占用。
   - 未收藏记录点击收藏后拥有 `收藏` 标签。
   - 已收藏记录再次点击后移除 `收藏` 标签。
   - 按 `收藏` 筛选只显示拥有 `收藏` 标签的记录。
   - 收藏关系跨 reload / 重启保持。

7. 右键菜单：
   - 已添加标签和未添加标签状态可区分。
   - 添加已有标签后条目展示、筛选、搜索字段同步。
   - 移除已有标签后同步消失。
   - 新建标签并添加到当前记录成功后，设置页和条目同时可见。
   - 新建重名失败时，不改变标签列表和当前记录关系。

8. 标签搜索：
   - 在 Step 1 搜索底座可用后，搜索 `Work` 命中拥有 `Work` 的记录。
   - 搜索标签名不应依赖正文中偶然出现同名词作为唯一证据；fixture 需要区分正文命中和标签命中。
   - 重命名、合并、删除后搜索命中随之更新。
   - Step 2 不负责正文、OCR、来源 App、URL、时间、文件名、类型等非标签字段回归，但不应破坏 Step 1 已接受的搜索能力。

9. 旧逻辑移除：
   - UI 不再出现旧 pinboard / pinned / 固定独立模型。
   - 旧固定筛选和新收藏标签不并列。
   - 旧固定数据不迁移、不提示迁移。
   - 新收藏行为以标签关系为事实源。

## 并发推进 Step 1 / Step 2 的测试策略

1. Step 2 可以先验收标签模型、设置页管理、右键菜单、筛选和收藏切换，不必等待 Step 1 全量搜索/OCR 收敛。

2. 标签搜索需要拆成两类证据：
   - 模型层证据：标签字段进入可搜索字段或索引输入，且重命名 / 合并 / 删除会发出更新。
   - 端到端证据：搜索框输入标签名命中对应记录。

3. 如果 Step 1 搜索底座在 Step 2 验收时仍未接受，Step 2 不能把端到端标签搜索写成已通过，只能记录为依赖未闭合或阶段性未验证。

4. 若项目负责人决定允许 Step 2 在标签搜索端到端未闭合时先通过，验收结论应最多为带残余风险接受，并把最终端到端搜索放入 Step 6 或 Step 1/2 集成 gate。

## 旧逻辑回归风险

1. 把旧 pinned 字段简单改名为收藏，可能导致“收藏”不是标签事实源。需要门禁检查收藏只是一种内置标签关系。

2. 旧固定状态若仍参与筛选或排序，用户会看到收藏与固定并列或状态不一致。

3. 不迁移旧数据是已接受边界；测试不应要求迁移，但必须确认没有半迁移提示或兼容 UI 误导用户。

4. 标签搜索若接入旧搜索逻辑，可能只在正文偶然包含标签名时通过。fixture 必须让正文不含标签名，避免假阳性。

## 可后续优化

1. 删除普通标签前的二次确认、撤销或 toast 可以提升体验，但当前需求明确不要求二次确认，不应作为 Step 2 阻断项。

2. 自动清理空标签不属于 Step 2；空标签实体是否允许存在由用户主动创建 / 删除行为决定，不作为缺陷。

3. 批量删除标签不属于 Step 2。

4. 多标签 OR / AND 筛选可在后续交互打磨阶段再做；Step 2 固定单标签筛选更利于收敛。

5. 标签颜色的高级无障碍对比度审计可以后续加强；Step 2 至少应保证受控色板和可辨识状态。

6. 右键菜单的高级搜索、长标签折叠、拖拽排序动画和面板布局质感属于 Step 3 或后续 UI 打磨，不应阻塞 Step 2。

## 建议的质量门禁

1. 新增 Step 2 专用 fail-closed 脚本，检查：
   - 标签实体不是旧 pinboard / pinned 改名。
   - `收藏` 是内置标签关系事实源。
   - 普通标签唯一性、trim、大小写不敏感、空名拒绝。
   - 删除、合并、重命名、排序、颜色的模型边界。
   - 旧 pinboard / 固定 UI token 不作为当前事实源。

2. UI / 交互静态或轻量运行门禁覆盖：
   - 设置页标签管理入口。
   - 右键菜单添加 / 移除 / 新建标签。
   - 收藏切换。
   - 标签筛选。

3. 搜索门禁分阶段：
   - Step 1 未闭合时，只验收标签搜索字段契约。
   - Step 1 闭合后，验收端到端标签搜索。

4. 最终实现验收至少应串行运行：
   - Step 2 标签模型 / 边界检查脚本。
   - 标签 UI / 设置页 / 右键菜单检查脚本。
   - 标签搜索契约或端到端脚本，按 Step 1 状态选择。
   - 旧 pinboard / fixed 负向检查。
   - Blocks App build。
   - BlocksCLI build 与 `blocks --help`，若项目固定门禁要求。
   - `git diff --check`。

## 总体判断

Step 2 PRD 可以继续推进，但不建议原样进入开发。必须先把标签搜索分阶段验收、单选筛选规则、持久化、删除 / 合并边界、`收藏` 可变更范围和旧逻辑负向清单写清楚。补清后，本阶段验收可保持在标签与收藏模型范围内，不需要提前引入 Step 3 的复杂筛选交互或 Step 4/5 能力。
