# Step 2 App 架构师 PRD 复审 v0

复审日期：2026-07-07
复审角色：App 架构师
复审对象：`step_2/产品经理-PRD-v0.md`
复审范围：Step 2 标签与收藏模型替换
结论：`approve-with-changes`

## 1. 总体判断

Step 2 PRD 的阶段边界基本正确：它聚焦标签、收藏、多标签关系、标签管理、右键菜单、标签筛选和旧 pinboard / pinned 概念退出，没有把 Step 1 明文展示 / OCR、Step 3 面板专项交互、Step 4 详情编辑或 Step 5 隐私页 App 管理提前塞回 Step 2。

从 App 架构角度看，PRD 可以继续推进，但进入技术方案前需要补清几个 P1 架构契约。核心问题不是产品方向，而是数据事实源和事务边界还不够硬：Tag / record-tag 模型需要明确为独立事实源，标签唯一性需要稳定归一化键，收藏不能只靠显示名称表达内置语义，删除 / 合并需要原子事务，旧 pinboard / pinned 移除需要可验证的影响面，标签搜索接入 Step 1 索引需要拆分依赖。

## 2. 已符合架构方向的部分

- PRD 明确标签是独立实体，至少包含名称、颜色、排序位置和是否内置。
- PRD 明确一条剪贴板记录可以关联多个标签，同一记录不能重复关联同一标签。
- PRD 明确“收藏”不是旧固定状态，也不是第二套数据模型，而是内置标签。
- PRD 明确旧 pinboard / 固定逻辑直接移除，不做迁移和兼容。
- PRD 明确标签名称进入搜索增量，且 Step 1 搜索底座未稳定时，Step 2 至少先定义标签字段模型和索引更新要求。
- PRD 对颜色、排序、重命名、合并、删除普通标签和右键菜单行为已有完整用户可见行为描述。

这些方向可以保留。

## 3. 必须改 PRD 的点

### P1-1：Tag / record-tag 需要写成独立事实源契约

当前 PRD 说“标签是独立实体”，但还没有明确最低事实源结构。进入技术方案前，PRD 应补充：

- Tag 必须有稳定 `tagID` 或等价主键，不能用显示名称作为记录关联主键。
- Tag 至少应区分 `displayName`、`normalizedName`、`colorToken`、`sortOrder`、`builtInKind` 或等价字段。
- record-tag 关系应是独立关联事实源，至少由 `recordID + tagID` 唯一约束保证同一记录不重复关联同一标签。
- 旧 pinboard / pinned 不能作为新标签关系的事实源或兼容派生源。

原因：如果用显示名称或旧 pinboard id 作为事实源，后续重命名、合并、搜索索引、收藏语义和删除事务都会变脆。

### P1-2：唯一性归一化需要确定为稳定技术规则

PRD 已写去首尾空格、大小写不敏感校验，但还不足以支撑数据库唯一约束和跨 locale 稳定行为。进入技术方案前，PRD 应补充：

- 标签唯一性以 `normalizedName` 或等价归一化键判断，而不是 UI 临时比较。
- 归一化至少包括 trim、大小写折叠，并明确是否折叠连续空白、全半角、Unicode normalization。
- 归一化规则应稳定、locale-independent 或明确采用项目指定 locale，不应跟随系统语言产生不同唯一性结果。
- `displayName` 可保留用户输入的展示形式，但保存时必须绑定唯一的 normalized key。
- “收藏”应占用内置标签语义和归一化名称，普通标签不能通过大小写、空格或本地化绕过占用。

具体算法可留给技术方案，但 PRD 需要明确“稳定归一化键 + 唯一约束”这个边界。

### P1-3：收藏内置标签不能只靠名称表达

PRD 当前把“收藏”写成内置标签名称、默认第一、五角星、不可删除，这对 UI 足够，但对架构还不够。进入技术方案前，PRD 应补充：

- 收藏应由稳定 built-in identity 表达，例如 `builtInKind = favorite`，显示名称只是本地化或展示字段。
- 收藏标签不可删除、不可被合并删除、不可被普通重命名覆盖。
- 收藏排序第一是 invariant，不应依赖普通 sortOrder 恰好最小。
- 是否允许改色必须由项目负责人收敛；若允许，改色只能改变展示 token，不能改变内置语义。
- 是否允许普通标签合并到收藏必须明确。若允许，应写成“批量给关联记录添加收藏标签，然后删除源普通标签”的事务；若不允许，应在 PRD 中禁止。

项目负责人预审已指出“是否允许普通标签合并到收藏”需要收敛。这个点进入技术方案前必须定下来，否则 merge 事务和验收无法闭合。

### P1-4：删除 / 合并必须有原子事务和失败语义

PRD 已写删除、合并的用户结果，但缺少事务边界。进入技术方案前，PRD 应补充：

- 删除普通标签必须原子删除 tag entity 和所有 record-tag 关联；失败时不能留下半删除状态。
- 合并必须在一个事务内完成：转移关联、去重 `recordID + targetTagID`、删除源标签、更新排序/显示、触发搜索索引失效或重建。
- 合并多个标签时，任一源标签失败应整体失败或明确回滚，不能部分转移。
- 删除 / 合并完成后，面板列表、筛选状态、右键菜单、设置页和搜索标签字段要看到一致状态。
- 删除 / 合并不要求二次确认，但需要定义失败反馈和恢复后状态，不应静默吞掉冲突。

这不是要求做复杂撤销系统，而是要求仓储层和 UI 状态不要出现部分提交。

### P1-5：排序模型需要明确持久化与冲突处理

PRD 已写“收藏第一，普通标签按用户排序”，但进入技术方案前需要补清：

- 普通标签排序持久化字段或等价顺序源是什么。
- 收藏第一是否完全排除在普通排序之外。
- 新建标签默认插入位置：普通标签末尾、当前筛选附近，还是设置页最后。
- 删除 / 合并后 sortOrder 是否压缩、是否允许空洞，技术方案可定，但 PRD 要求显示顺序稳定。
- 重名失败、排序失败时不应改变原排序。

排序不是 UI 细节，因为筛选列表、设置页、右键菜单和搜索建议都可能依赖同一顺序。

### P1-6：旧 pinboard / pinned 移除需要列出门禁

PRD 已写旧逻辑不迁移、不兼容，这是正确方向。但进入技术方案前应把移除影响面写成可验证门禁：

- 用户可见文案、按钮、设置页、右键菜单、筛选入口不再出现 pinboard / pinned / 固定作为独立模型。
- 收藏按钮不得读写旧 pinned 状态；它只能增删“收藏”内置标签关系。
- 旧 pinboard / pinned 代码若暂时保留为内部兼容字段，不得参与当前 UI、筛选、搜索和验收事实源。
- verification 应检查旧 pinboard / pinned 不再作为当前 ok 证据，旧文档只能作为 baseline_reference。
- fixture/reset 路径要能构造 Tag 与 record-tag 事实，不再依赖旧 pinboard fixture 代表标签。

由于用户明确“不迁移旧数据”，这里的目标是切干净当前事实源，而不是做迁移兼容。

### P1-7：标签字段接入 Step 1 搜索索引需要拆阶段验收

PRD 已意识到 Step 1 搜索底座可能尚未最终接受，但仍写了“标签名称可以作为搜索字段进入搜索增量”。建议回写更明确的依赖拆分：

- Step 2 的核心可独立验收：Tag / record-tag 模型、设置页管理、右键菜单、标签筛选、收藏切换。
- 标签搜索字段接入依赖 Step 1 的搜索 index/read model；如果 Step 1 未接受，Step 2 只能交付标签搜索字段 adapter / invalidation contract，不能把全文搜索集成当作 Step 2 完成条件。
- 标签创建、重命名、合并、删除应触发“标签搜索字段需要更新”的事件或接口；具体索引重建由 Step 1 搜索服务承接。
- PRD 验收需要拆成“标签筛选可独立验收”和“标签搜索接入在 Step 1 搜索底座稳定后验收”两类。

这样可以并发推进 Step 1 / Step 2，又不会让 Step 2 被未完成的搜索底座阻塞。

## 4. 架构风险排序

### P0

无。当前 PRD 没有发现会直接导致 Step 2 方向不可接受的问题。

### P1

1. Tag / record-tag 独立事实源未写成最低契约，容易退化成旧 pinboard 改名。
2. 标签唯一性归一化规则不够稳定，可能导致数据库唯一约束、UI 校验和搜索命中不一致。
3. 收藏内置语义只靠名称和 UI 规则表达，缺少稳定 built-in identity。
4. 删除 / 合并事务缺少原子性、去重、失败回滚和索引失效要求。
5. 旧 pinboard / pinned 移除缺少可执行门禁，容易形成旧新事实源并存。
6. 标签搜索依赖 Step 1 搜索底座，验收拆分不够硬。

### P2

1. 标签颜色建议明确为 palette token，而不是任意颜色值；色板数量和可访问性可由 UI 复审继续细化。
2. 删除普通标签不要求二次确认是产品选择，但建议至少有轻量反馈文案或可见影响说明，避免误解为只从当前条目移除。
3. 右键菜单中标签列表过长时的分页、搜索或分组不必进入 Step 2 核心，但应作为后续可优化点。
4. 多标签筛选默认单标签是合理的保守范围；后续如果做 OR / AND，应基于同一 record-tag 关系扩展，不要改事实源。
5. 标签显示数量、长标签截断和卡片布局属于 Step 3 / UI 细化，不应阻塞 Step 2 数据模型。

## 5. 可后续优化但不阻塞的点

- 标签颜色色板、默认颜色分配、暗色模式对比度可由 UI/交互设计师细化。
- 设置页删除普通标签是否需要撤销，可后续根据测试/体验风险决定，不要求 Step 2 先做复杂 undo。
- 右键菜单的新建标签失败反馈形态可由 UI 方案确定，架构只要求失败不改变 tag / record-tag 事实。
- 标签搜索排序权重不需要 Step 2 定义；Step 2 只需提供标签字段和更新事件，排序权重应归 Step 1 搜索服务。
- 旧 pinboard / pinned 的代码清理可以按开发影响拆分，但当前事实源和验收门禁必须先转向 tag 模型。

## 6. 建议 PRD 回写清单

建议项目负责人要求产品经理在 `产品经理-PRD-v1.md` 中最少回写：

1. Tag 最低字段契约：稳定 `tagID`、`displayName`、`normalizedName`、`colorToken`、`sortOrder`、`builtInKind` 或等价模型。
2. record-tag 关系契约：`recordID + tagID` 唯一，不依赖旧 pinboard / pinned。
3. 标签唯一性归一化：稳定 normalized key，普通标签不能占用收藏。
4. 收藏内置 identity：收藏由 built-in kind 表达；不可删除、不可被合并删除；是否允许普通标签合并到收藏需要明确。
5. 删除 / 合并事务：原子转移、去重、删除、索引失效和失败反馈。
6. 排序规则：收藏第一 invariant，普通标签排序持久化，新建/删除/合并后的稳定显示顺序。
7. 旧逻辑移除门禁：UI、筛选、搜索、收藏按钮、fixture/verifier 不再以 pinboard / pinned 为当前事实源。
8. 搜索依赖拆分：标签模型/筛选先验收，标签搜索字段接入依赖 Step 1 搜索底座稳定后验收。

## 7. 可吸收建议与推荐口径

以下内容可以直接作为产品经理修订 PRD v1 的输入，或作为后续技术方案的边界文本。

### 7.1 推荐产品口径：标签模型不是 pinboard 改名

建议 PRD v1 增加类似表述：

> Step 2 的标签模型是新的独立事实源，不是旧 pinboard / pinned 的改名。标签实体与记录-标签关系应独立建模；旧 pinboard / pinned 不迁移、不兼容，也不作为当前 UI、筛选、收藏或搜索的事实来源。

这个口径可以帮助开发和验证脚本避免把旧字段继续当作新标签的底层实现。

### 7.2 推荐数据模型边界

建议 PRD v1 用产品可读方式写出最低模型，不需要指定具体数据库表名：

> 标签至少包含稳定标识、展示名称、归一化名称、颜色 token、普通标签排序值和内置类型。记录与标签通过独立关联关系连接，同一记录不能重复关联同一标签。

可作为技术方案输入的等价结构：

```text
Tag:
- tagID
- displayName
- normalizedName
- colorToken
- sortOrder
- builtInKind: none / favorite

RecordTag:
- recordID
- tagID
- unique(recordID, tagID)
```

这里的重点是事实源边界，不是要求 PRD 指定存储实现。

### 7.3 推荐唯一性归一化口径

建议 PRD v1 增加：

> 标签重名判断以稳定归一化名称为准。保存时先对用户输入做首尾空白清理和大小写折叠，并使用项目定义的稳定归一化规则生成唯一键。展示名称可以保留用户输入的可读形式，但唯一性、合并、重命名和搜索索引应以归一化键为准。

技术方案可再决定是否加入 Unicode normalization、连续空白折叠、全半角处理等细节。PRD 至少要明确“稳定归一化键”。

### 7.4 推荐收藏内置标签口径

建议项目负责人收敛后，PRD v1 采用其中一个明确口径。

保守口径：

> 收藏是内置标签，不能删除、不能重命名、不能被普通标签覆盖，也不能作为被合并标签删除。普通标签本阶段不允许合并到收藏，避免把合并操作变成批量收藏。

如果项目负责人希望允许合并到收藏，则建议写成：

> 普通标签允许合并到收藏。该操作等价于把源标签关联的记录批量添加收藏标签，并删除源普通标签。合并前需要明确文案提示“这些记录将被收藏”。收藏自身不能作为源标签被删除。

从 App 架构视角，推荐保守口径：Step 2 先禁止普通标签合并到收藏。理由是收藏具有强用户语义，批量收藏更像高影响操作；本阶段又明确不做复杂确认和撤销，保守处理更稳。

### 7.5 推荐删除 / 合并事务口径

建议 PRD v1 增加：

> 标签删除和合并必须以一致性为优先。删除普通标签时，应同时移除该标签与所有记录的关联；合并标签时，应把源标签的记录关联转移到目标标签，自动去重，然后删除源标签。删除或合并失败时，不应出现部分记录已变化、部分记录未变化的可见状态。

技术方案可进一步落成 repository transaction、UI refresh 和搜索索引 invalidation。

### 7.6 推荐排序口径

建议 PRD v1 增加：

> 收藏始终是标签组第一项，不参与普通标签排序。普通标签排序是持久化用户顺序；新建普通标签默认进入普通标签末尾。删除或合并后，普通标签显示顺序应保持稳定，不因内部排序字段变化造成跳动。

这能避免技术方案把收藏第一实现成普通 sortOrder 的偶然结果。

### 7.7 推荐旧逻辑退出门禁

建议 PRD v1 增加验收 / 门禁方向：

> Step 2 验收时，用户可见界面不再出现 pinboard / pinned / 固定作为独立模型；收藏按钮只读写收藏标签关系；标签筛选和右键标签状态只依赖 Tag / RecordTag 当前事实源。旧 pinboard / pinned 代码如因清理成本暂时存在，不得参与当前验收 ok 证据。

后续技术方案可据此新增 verifier，例如检查旧 pinned 状态不再驱动收藏、旧 pinboard 不再驱动标签筛选。

### 7.8 推荐搜索依赖拆分口径

建议 PRD v1 明确拆成两档验收：

> Step 2 必须独立完成标签实体、记录-标签关系、标签管理、右键菜单、标签筛选和收藏切换。标签名称进入搜索字段的完整验收依赖 Step 1 搜索底座；如果 Step 1 尚未最终接受，Step 2 只需提供标签字段变更事件或等价索引更新契约，待搜索底座稳定后再完成搜索接入验收。

这个口径可以允许 Step 2 与 Step 1 并发推进，同时避免把搜索底座未完成的风险算成 Step 2 数据模型失败。

### 7.9 推荐技术方案输入

后续技术方案可以直接接收以下任务边界：

1. 建立 Tag / RecordTag repository 或等价 store 边界，避免 View 直接拼接关系事实。
2. 设计 `normalizedName` 生成与唯一约束，并为重名失败返回可展示错误。
3. 实现内置 favorite tag bootstrap：缺失时创建，存在时校正 built-in identity，不迁移旧 pinned。
4. 删除 / 合并走 repository transaction，并在成功后触发 UI refresh 与搜索索引 invalidation。
5. 增加 Step 2 verifier：检查旧 pinboard / pinned 不作为当前事实源、favorite 不可删除、record-tag 唯一、merge 去重、search contract 存在。

这些是技术方案输入，不要求 PRD v1 写成具体代码任务。

## 8. 最终建议

结论为 `approve-with-changes`。

Step 2 PRD 的产品方向和范围可以接受，但上面的 P1 项需要在进入技术方案前回写。完成回写后，Step 2 可以与 Step 1 修订并行推进：先落 Tag / record-tag 事实源、设置页管理、右键菜单、标签筛选和收藏切换；标签搜索接入则通过明确 contract 等 Step 1 搜索底座稳定后收口。
