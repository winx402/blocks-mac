## P2 Findings

### P2-1：`canonical_identifier` 本地 DB 存完整路径可接受，但需写清 retention 与迁移约束

判断：可接受，不构成 P1。

理由：

- 技术方案没有持久化全量 App index；只在 `privacy_policy_rules` 中为显式 policy rule 持久化 `canonical_identifier`。
- 默认 CLI / audit / verification / 开发记录 / 验收记录不输出 `canonical_identifier`。
- capture bridge 使用 path hash / summary / source directory，不要求把完整 path 送入默认 read model 或输出。
- `Default` mutation 会删除 explicit rule，理论上可清除对应 full path。

建议补强：

```text
canonical_identifier 只允许为显式创建的 app_path / command_path / app_bundle policy rule 持久化；不得由 App scan cache 批量写入，也不得在 v5 migration 中从真实机器扫描结果回填。

Default mutation 删除 explicit rule 时必须同时删除 canonical_identifier、path_hash、path_summary 等该 rule 的 path-like 字段；P13E 增加 default-delete-purges-sensitive-identifier fixture。

旧 excludedBundleIDs migration 只能迁移 bundle_id restricted rule，不得尝试解析或回填真实路径。

PrivacyPolicySnapshot 默认只暴露 bundle id set 和 path hash set，不暴露 canonical_identifier。
```

### P2-2：`--include-sensitive-paths` 不建议进入首版 CLI

判断：技术方案已写“默认建议不实现，先只做 UI 显式 reveal”，这一路径安全上更稳。若项目负责人接受，首版 CLI 不应提供 `--include-sensitive-paths`。

若仍决定进入首版，当前 help warning 和 P13E 禁用证据规则方向正确，但建议再补：

```text
首版 CLI 默认不实现 --include-sensitive-paths；如必须实现，该参数必须：
- 默认关闭，并在 `blocks privacy --help` 中标注 sensitive local output。
- 不允许在 P13E、开发记录、验收记录、golden fixture、CI 命令或角色复审证据中使用。
- 每次使用都输出 warning，且 warning 本身不包含完整路径。
- 不影响 JSON 默认 schema；默认 schema 仍只给 subject_ref / path_summary / source_directory / path_hash / path_redacted=true。
```

### P2-3：login item / helper / launch label 白名单足够窄，但 fixture 白名单需要防止漂移成系统登记源读取

判断：当前边界足够进入开发准备。技术方案明确 login item / helper / launch label 首版只允许显式 typed input、已有 policy record 或白名单 fixture，不扫描 PATH、不执行命令、不读取系统登记源。

建议补强：

```text
Batch A 中把 fixture whitelist 定义为测试代码内的 synthetic subject source，不读取真实 Login Items、LaunchAgents、LaunchDaemons、launch services database 或 shell PATH。

P13E 增加 `privacy_cli_fixture_source_only_004`，断言 login_item / helper / launch_label fixture 来自 synthetic source；任何真实系统登记源读取 token 或 `launchctl` 调用均 fail。
```

### P2-4：P13E forbidden pattern 需要区分“输出泄漏”和“文档/源码中描述禁止项”

判断：P13E denylist 覆盖面足够，但实现时需要避免把 PRD / 技术方案中用于说明禁止项的文字误判为泄漏。

风险例子：PRD 和技术方案中会合法出现 `System Settings`、`Finder`、`launchctl`、`tccutil`、`provider` 等词，用来说明 hard-block 边界；如果 P13E 对所有 checked docs 做简单全文 forbidden token 扫描，会产生假失败或诱导开发弱化 denylist。

建议补强：

```text
P13E 将 forbidden pattern 分成两类：
- output_sanitizer：扫描 verifier stdout、CLI JSON、audit JSON、开发/验收证据样例，命中完整路径、TCC dump、secret、dangerous command、provider route 等必须 fail。
- call_graph / implementation denylist：扫描 Step 5 touched Swift / CLI implementation 中是否出现真实系统动作 API 或 command execution token。

PRD / 技术方案文档允许出现禁止项名称，但不得出现真实路径、真实命令参数、secret、TCC raw dump 或可复制危险命令。
```

### P2-5：dangerous action hard-block 输出已足够低敏，建议固定 blocked_capability 枚举

判断：当前 hard-block JSON 不泄露可复制危险命令；方案已禁止在 error message 中提供 `launchctl ...`、`tccutil ...`、`open x-apple.systempreferences:` 或 shell snippet。

建议补强：

```text
blocked_capability 使用固定枚举，例如 `tcc_reset`、`permission_request`、`system_settings_open`、`finder_open`、`app_launch`、`command_execution`、`shell_execution`、`launchctl_mutation`、`login_item_lifecycle`、`helper_lifecycle`、`cli_tool_lifecycle`。

error.message 可以省略或保持通用；详细解释只使用 low_sensitive_reason，不拼接用户输入、真实 command path、launch label 或系统配置字段。
```

## 重点问题判断

### 1. `canonical_identifier` 存完整路径

可接受，前提是它只作为本地 policy rule 的显式匹配字段，不默认输出、不进入 evidence、不批量持久化 App index，并且 `Default` 删除 rule 时清除。建议把上述 retention 规则写入开发派发或技术方案 v1 小修。

### 2. `--include-sensitive-paths`

不建议进入首版 CLI。技术方案已给出默认建议：先不实现 CLI sensitive path 参数，只做 UI 显式 reveal。若项目负责人仍要求首版提供，则现有 help warning / P13E 禁用证据方向可接受，但必须明确禁止在任何 verifier / 验收证据中使用。

### 3. login item / helper / launch label 白名单

足够窄。技术方案没有允许系统登记源扫描，也没有允许 `launchctl`、PATH scan、command execution 或 Login Items 生命周期操作。建议 P13E 明确 fixture whitelist 是 synthetic source。

### 4. dangerous action hard-block 输出

当前方案足够低敏：只输出 `dangerous_action_blocked`、`low_sensitive_reason`、`blocked_capability`、`required_future_review=true`、`mutation_performed=false`，并禁止可复制危险命令。建议固定 `blocked_capability` 枚举，避免开发拼接真实用户输入。

### 5. P13E sanitizer / denylist

覆盖充分：已包含 TCC raw rows、csreq、requirement data、auth_value、auth_reason、indirect object identifier、System Settings URL、Finder open token、launchctl / tccutil / shell snippets、provider route / upload token、Authorization / Bearer / secret、home path、真实 `/Applications` 等风险。需要在实现时区分 output sanitizer 与 docs/source 中的禁止项描述。

## 已确认安全边界

- P13E 使用 synthetic temp roots，不读取真实 `/Applications`。
- `.app` 是枚举叶子，不扫描 bundle 内部。
- 图标 provider 在 P13E 使用 fake provider；真实图标读取仅在 App target adapter，且不启动 App、不请求权限、不持久化 icon binary。
- App index 首版仅进程内缓存，不持久化全量本机 App 路径清单。
- UI policy mutation 只写 `PrivacyPolicyRepository`，不触发系统权限或系统状态变化。
- CLI subject 是本 App policy subject，不是系统对象生命周期控制器。
- `command_path` 不扫描 PATH、不执行、不读输出、不解析 shell / glob / alias。
- `login_item` / `helper` / `launch_label` 不读取系统登记源，除非后续技术方案另行白名单并复审；首版仅 explicit input、existing policy 或 fixture。
- Dangerous actions 即使带 `--confirm` / `--yes` 也 hard-block。
- P13E stdout 有 size bound 和 sample bound，不 dump full app list。

## 是否建议进入开发准备

建议进入开发准备。P0/P1 清零，P2 均为开发派发或技术方案 v1 可直接吸收的边界细化。开发派发时建议明确：

- 首版不实现 CLI `--include-sensitive-paths`，除非项目负责人显式接受。
- Batch A 必须先落 P13E baseline red / evidence schema / fail-closed。
- 禁止真实 App、真实剪贴板、provider、Keychain、TCC、System Settings、Finder、App launch、command execution 或真实系统状态变更。
- P13E 必须先于业务 PASS，且不能退化为 token presence gate。
