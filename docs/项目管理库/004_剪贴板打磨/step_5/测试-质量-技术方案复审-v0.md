# 004_剪贴板打磨 Step 5 测试/质量技术方案复审 v0

日期：2026-07-07

范围：Step 5 技术方案 v0 复审；不进入开发，不触发真实 App、真实剪贴板、provider、Keychain、TCC、System Settings、Finder、App launch、command execution 或真实系统状态变更。

## 1. 结论

结论：`approve-with-changes`。

技术方案 v0 主体成立：P13E-first、单一 `PrivacyPolicyRepository`、三层模型、三 root 受控递归、synthetic roots、fake icon provider、CLI typed subject、低敏输出合同和性能阈值都已具备可执行基础。性能阈值也已从 PRD 的“必须量化”推进为具体数值，足以进入实现前的门禁设计。

但当前还不建议直接进入开发派发。P13E required scenarios 和 Batch 验收里有两个测试/质量 P1 缺口，可能造成“P13E PASS 但 PRD 关键用户路径未被验证”的假 PASS：一是 UI 搜索/过滤/排序/可访问性/长文本/窄宽度没有成为显式 required scenario；二是 capture bridge 不是 P13E 的一等验收对象。建议产出技术方案 v1，或在开发派发前以等价补丁清单硬回写这些 P1。

## 2. P0 / P1 / P2

### P0

无。

### P1-1：P13E required scenarios 未显式覆盖 UI 搜索、过滤、排序、可访问性与布局边界

问题：

- PRD v1 将搜索、过滤、稳定排序、键盘、VoiceOver、窄宽度、长文本、多语言列为 Step 5 最低验收。
- 技术方案 v0 的 P13E `Required scenarios` 覆盖 scan、identity、icon、policy mutation、CLI，但没有显式列出 `privacy_app_row_a11y_004`、`privacy_app_narrow_width_004`、`privacy_app_long_text_i18n_004`，也没有搜索 / 过滤 / 排序 scenario id。
- 虽然 fail-closed 条件写了“search / filter / sort / large-list fixture 完整”，但没有 required block 和断言字段时，脚本容易只做 token presence 或只验证 large-list，遗漏用户路径。

建议回写为 P13E required scenarios：

```text
UI interaction / layout scenarios:
- privacy_app_search_fields_004: display name、bundle id、source directory、path summary、policy status、identity issue code 都能命中；path search 不匹配 raw home path。
- privacy_app_filter_combination_004: 同维度 OR，不同维度 AND，Clear filters / Clear search / Clear all 语义可区分。
- privacy_app_sort_stability_004: display name、bundle id、source directory priority、path summary、path hash tie-breaker；icon async 不改变排序；refresh 同 fixture 顺序稳定。
- privacy_app_row_a11y_004: row 暴露 App name、policy status、bundle id 可用性、source directory、主要异常；policy control 有 label / value / hint。
- privacy_app_narrow_width_004: 窄宽度下 policy status/control 仍可见，长文本不挤压 trailing control。
- privacy_app_long_text_i18n_004: 中文、英文、日文长 App 名、bundle id、path summary 使用低敏 fixture，截断与完整值入口可判定。
```

P13E evidence schema 建议新增：

```text
"ui_interaction": {
  "search_fields": {},
  "filter_combination": {},
  "sort_stability": {},
  "a11y": {},
  "layout": {}
}
```

### P1-2：capture bridge 不是 P13E 一等验收，存在 UI/CLI policy 已实现但 capture 不生效的假策略风险

问题：

- 技术方案 v0 正确识别 `app_path` override + capture bridge 是风险点，并设计了 `PrivacyPolicySnapshot`。
- 但 P13E required scenarios 没有 capture bridge scenario；Batch C 验收只笼统要求 `path override scenarios pass` 和 `ClipboardCapturePolicy` 接入。
- 如果实现只完成 UI/CLI 的 policy mutation，却没有让 live capture 按 `bundle_id` / `app_path` precedence skip/allow，P13E 仍可能通过。

建议回写为 P13E required scenarios：

```text
Capture bridge scenarios:
- privacy_capture_bundle_restricted_004: source bundle id 命中 restricted bundle_id rule -> skip with .excludedSource。
- privacy_capture_bundle_allowed_004: source bundle id 命中 allowed bundle_id rule -> allow。
- privacy_capture_app_path_precedence_004: app_path restricted 优先于 bundle_id allowed；app_path allowed 优先于 bundle_id restricted。
- privacy_capture_default_allow_004: 无 explicit rule -> default allow。
- privacy_capture_missing_path_fallback_004: 无 path hash 时只按 bundle id 规则判断，不伪造 app_path match。
- privacy_capture_snapshot_low_sensitive_004: evidence 只输出 bundle id fixture、path hash、summary、decision code，不输出真实路径、窗口标题、剪贴板 payload。
```

P13E fail-closed 条件建议补：

```text
- PrivacyPolicySnapshot 未包含 bundle_id allowed/restricted 与 app_path allowed/restricted set 时 fail。
- ClipboardCapturePolicy 未消费 PrivacyPolicySnapshot，或仍只消费旧 excludedBundleIdentifiers 时 fail。
- capture bridge scenario 缺 decision、matched_rule_type、mutation_performed=false、payload_read=false 时 fail。
```

### P2-1：旧 `excludedBundleIDs` 迁移建议加入 P13E scenario id

技术方案 v0 在 Batch C 验收中写了旧 `excludedBundleIDs` 迁移为 restricted bundle id policy，这是正确方向。建议补一个显式 scenario，避免只靠文字验收：

```text
- privacy_policy_legacy_excluded_bundle_migration_004:
  old UserDefaults fixture -> one-shot migration -> restricted bundle_id rules；
  migration marker present；
  AppModel / capture policy no longer reads old excluded string as active fact source。
```

该项不阻塞技术方案进入 v1 收敛，但开发验收中应进入 P13E 或 P9/P11E 相关回归。

### P2-2：P13E forbidden pattern 建议区分 hard token 与 allowlisted text

方案中 forbidden pattern 足够严格，但 `open `、`provider`、`System Settings`、`Finder` 这类词可能在文档说明、错误码标签或“denied_runtime_actions”里合法出现。建议 P13E sanitizer 使用 label-aware allowlist：

```text
- hard forbidden: raw home path、Authorization、Bearer、password、private key、JWT、webhook、base64、data:image、csreq、requirement_data。
- context forbidden: launchctl / tccutil / osascript / open / Finder / System Settings 只允许出现在 blocked_capability label 或 denied_runtime_actions summary，不允许出现在可复制命令、URL 或 raw output。
```

### P2-3：性能阈值清楚，但建议标注测量环境和失败输出

3000 synthetic apps、first page 300 ms、full index 2000 ms、search/filter 120 ms、CLI resolve 150 ms 可测。建议技术方案补：

```text
- performance result 输出 elapsed_ms、threshold_ms、fixture_count、sample_count。
- 超时输出只给 scenario id 和 summary，不 dump app list。
- 若本地机器波动导致性能失败，允许一次串行重跑；重跑仍失败才判 fail。
```

## 3. 复审重点判断

### P13E evidence schema / fail-closed

基本可执行。方案已经定义顶层 JSON、current fact sources、fixture data shape、required scenarios、fail-closed 条件、forbidden pattern 和 stdout bound。

当前主要缺口不是 schema 方向，而是 required scenarios 覆盖不完整。补齐 P1-1 / P1-2 后，P13E 可以作为 Step 5 hard gate。补齐前，P13E 可能成为“强静态 + 部分 fixture”门禁，不能独立支撑 Step 5 完成。

### 性能阈值

足够明确且可测。阈值具体到 fixture count、first page readiness、full index build、search/filter recompute、refresh no-blank、icon layout stability、stdout bound、CLI resolve response。

建议把测量环境、重跑规则和失败输出低敏格式留给 P13E 实现，不需要因此退回整体方案。

### Batch A-D 与回归矩阵

Batch A-D 顺序合理：

- Batch A 先建立 P13E baseline red、Core model、schema。
- Batch B 做 scanner、icon、PrivacyStore。
- Batch C 做 policy mutation、UI pane、capture bridge、旧 excluded migration。
- Batch D 做 CLI、sanitizer、full regression。

回归矩阵包含 P13A / P13B / P13C / P13D / P11E / P9A / P9B / P8 / P8I、Blocks App build、BlocksCLI build、`blocks --help`、`git diff --check`，边界基本足够。

需要修正的是：Batch C 的 capture bridge 和 UI interaction/layout evidence 必须变成 P13E required scenarios 或等价 fail-closed gate，而不是只出现在开发目标文字里。

### P13E 与既有门禁边界

边界基本清楚：

- P13E：Step 5 主门禁，负责 App inventory、policy subject、UI mutation、CLI typed subject、low-sensitive、performance。
- P8 / P8I：现有产品 polish / Settings clipboard 回归，不替代 P13E。
- P9A / P9B：repository / AppModel 集成回归，不替代 Step 5 subject、policy 和 CLI 验收。
- P11E：clipboard payload hardening，不替代真实 App identity / privacy policy 门禁。
- P13A-D：Step 1-4 回归，不作为 Step 5 主验收。

建议在开发派发里硬写“P13E FAIL 时不得用其他回归 PASS 声称 Step 5 完成”，方案 v0 已有该口径，可以保留。

## 4. 建议技术方案 v1 回写清单

建议技术方案 v1 最小回写以下内容后进入开发准备：

1. 把 UI search / filter / sort / a11y / narrow width / long text i18n 加入 P13E required scenarios 和 evidence schema。
2. 把 capture bridge 加入 P13E required scenarios，明确 `PrivacyPolicySnapshot` 到 `ClipboardCapturePolicy` 的 bundle_id / app_path precedence pass/fail。
3. 将旧 `excludedBundleIDs` migration 增加 scenario id，至少进入 Batch C 验收或 P13E 回归。
4. 给 P13E sanitizer 增加 context-aware forbidden pattern 规则，避免误判合法 blocked labels，同时继续禁止可复制危险命令和敏感原文。
5. 给性能 evidence 增加 elapsed / threshold / fixture_count / sample_count 字段和低敏失败输出规则。

## 5. 是否可进入开发准备

不建议以当前 v0 直接进入开发派发；建议先产出技术方案 v1 或由项目负责人在开发派发中硬回写 P1-1 / P1-2。

如果 P1-1 / P1-2 已回写为 hard gate，则测试/质量视角可进入开发准备；剩余 P2 可在 P13E 实现与开发验收阶段闭合。
