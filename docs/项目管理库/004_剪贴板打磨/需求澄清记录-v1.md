# 剪贴板打磨需求澄清记录 v1

状态：clarified-for-prd-v0
记录日期：2026-07-07
来源：用户对角色澄清回收后 3 个阻塞项的回答，以及项目负责人对 macOS OCR 能力的核验

说明：本文承接 [需求澄清记录 v0](需求澄清记录-v0.md) 和 [角色澄清回收 v0](角色澄清回收-v0.md)，用于进入 PRD v0 起草。本文仍不是 PRD，也不代表技术方案已完成。

## 1. OCR 范围

用户回答：

- 如果 macOS 系统提供 OCR 能力，则 OCR 可以进入 PRD v0。
- 如果 macOS 默认没有提供 OCR 能力，则先不支持。
- 如果 OCR 有性能问题，需要在体验和交互上处理好。

已核验事实：

- Apple Vision 框架提供 `VNRecognizeTextRequest`，用于检测图片中的文字区域并识别文字内容。
- 本机 macOS SDK 中 `VNRecognizeTextRequest` 标记为 `API_AVAILABLE(macos(10.15), ios(13.0), tvos(13.0))`。
- Vision 支持 `accurate` 和 `fast` 两种识别等级，存在准确率与性能的取舍。
- Apple 文档也说明 Vision 通过 `VNRecognizeTextRequest` 提供图片文字识别能力。

PRD v0 结论：

- OCR 进入 PRD v0，但限定为使用 macOS 系统 Vision 能力，不做自研 OCR。
- OCR 仅处理剪贴板中已有图片 payload，不引入外部 provider OCR。
- OCR 结果进入搜索索引，并参与图片条目的关键词搜索。
- PRD 必须定义 OCR 的性能体验：异步处理、索引中状态、失败状态、可重试状态、缓存策略、是否优先 fast 模式、是否延迟处理大图片。
- PRD 必须避免把 OCR 写成同步阻塞操作；面板打开、搜索输入和滚动不应被 OCR 卡住。

待技术方案确认：

- 支持语言列表、自动语言检测和中英文混排效果需要在实现阶段基于系统 API 和目标 macOS 版本验证。
- 大图、长截图、多图批量入库的处理队列、限流和失败恢复策略需要技术方案定义。

## 2. 明文边界与 payload 理解

用户回答：

- “明文”指这些链路有权限拿到真实内容。
- 交互上可以使用 payload、元数据优先等设计，这属于交互问题。
- 未来是否添加权限开关或过滤逻辑，等设计到相关链路时再考虑。
- 用户理解 payload 是数据索引或代指，不影响产品目标。
- 日志等链路应尽量从性能上考虑，不要过于复杂或性能差。

术语澄清：

- 在当前项目技术语境里，payload 通常指剪贴板记录的真实内容或内容载体，不只是索引。
- 用户本轮表达的产品意图是：相关链路具备读取真实内容的权限，不再以默认遮挡真实内容作为目标。
- “有权限读取真实内容”不等于所有界面、日志或 CLI 都必须默认展示完整正文；交互和输出可以为了可读性、性能和可操作性采用摘要、元数据优先、分页、延迟加载或显式展开。

PRD v0 结论：

- 项目核心原则改为“真实内容可访问，交互输出可控”。
- 面板和搜索以明文可用为目标，不再默认只展示字符数或 redacted summary。
- 日志、CLI、provider、自动化链路不再以内容保护为主要目标，但仍需避免低性能、低可读性和误操作。
- 暂不在 PRD v0 引入新的权限开关、过滤规则或复杂策略系统。
- 输出控制的理由应写成性能、可读性、可维护性和防误操作，而不是继续沿用“内容保护”作为产品叙事。

PRD v0 需要避免的误解：

- 不把“明文优先”写成“所有日志无限制落盘全文”。
- 不把“链路有权限拿真实内容”写成“provider / 自动化可以后台静默外发真实内容”。
- 不把 payload 术语强加给用户界面；用户文案应使用“内容”“正文”“原始内容”等更直观表达。

## 3. 详情编辑范围与保存模型

用户回答：

- 富文本可以编辑，并询问难度是否会影响富文本格式。
- URL 也可以编辑。
- 图片如果有 OCR，OCR 后的文字也可以编辑。
- 保存模型采用“显式保存 + 取消”。
- 保存和取消按钮不应突然出现/消失导致页面布局跳动，页面样式要处理好。

项目负责人判断：

- 富文本编辑进入 PRD v0，但必须把“保留格式”和“退化为纯文本编辑”的差异写清楚。
- 如果只编辑富文本的纯文本化内容，可能会丢失或重建格式；如果要求保留富文本格式，需要技术方案处理 attributed string、RTF/HTML 或现有 payload 格式的读写一致性。
- PRD v0 不应默认允许静默丢格式。若技术方案无法低风险保留格式，应回到项目负责人处做范围取舍。

PRD v0 结论：

- 可编辑类型包括 plain text、URL、富文本文本内容、图片 OCR 文本。
- 图片本体不编辑；只编辑 OCR 识别出的文字内容。
- URL 编辑应更新内部 payload、搜索索引、更新时间和可见摘要，但不更新系统剪贴板。
- 富文本编辑的验收目标应先写为“尽量保留原富文本格式”。如果技术评估确认无法可靠保留格式，需要在 PRD 或方案中明确降级为纯文本化编辑，并说明影响。
- OCR 文本编辑应更新 OCR 文本索引和详情展示，不应改写图片 payload 本体。
- 保存模型为显式保存 + 取消。
- 保存/取消控件需要有稳定布局位，不得因为 dirty state 出现或消失导致页面整体跳动。
- 保存失败需要展示失败反馈，并保持用户当前编辑内容可恢复。

待技术方案确认：

- 富文本 payload 当前保存格式、可逆编辑能力和格式保留范围。
- URL 记录是独立类型还是文本类型附带识别，编辑后是否可能改变记录类型。
- OCR 文本编辑属于 OCR overlay/annotation，还是记录派生字段，需要技术模型明确。

## 4. 设计与架构要求

用户补充：

- PRD 和技术实现不要只着眼于当前功能，应更全面思考未来扩展。
- 交互上必须考虑用户体验和页面质感。

PRD v0 影响：

- 搜索能力要按可扩展索引设计，而不是临时字符串过滤。
- 标签能力要按可扩展数据模型设计，而不是把 pinboard 改名为标签。
- OCR、富文本、URL、图片派生文本都应进入内容模型和索引模型的长期考虑。
- UI 设计不能只满足功能存在，需要定义稳定布局、反馈状态、空状态、失败态、长内容处理、性能状态和视觉密度。
- 保存/取消、OCR 状态、标签合并、筛选展开和选中反馈都应有明确交互质量要求。

## 5. 当前可进入 PRD v0 的状态

已解决的阻塞项：

- OCR：进入 PRD v0，限定使用 macOS Vision，需性能和状态设计。
- 明文边界：真实内容可访问，交互输出可控；暂不新增权限开关或复杂过滤系统。
- 详情编辑：plain text、URL、富文本文本内容、图片 OCR 文本进入范围；显式保存 + 取消；控件布局必须稳定。

仍需技术方案阶段重点评估：

- 富文本编辑是否能可靠保留格式。
- OCR 队列、缓存、失败重试和语言支持。
- 搜索索引字段和更新事务。
- CLI / 日志 / provider / 自动化的输出控制如何做到低复杂度和低性能损耗。
