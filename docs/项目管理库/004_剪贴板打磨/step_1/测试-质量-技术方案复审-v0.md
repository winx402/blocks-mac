# 测试/质量技术方案复审：Step 1 明文展示、搜索底座与系统 Vision OCR

日期：2026-07-07
角色：测试/质量
复审对象：`App架构师-技术方案-v0.md`、`项目负责人-技术方案预审-v0.md`、`产品经理-PRD-v1.md`

## 结论

`approve-with-changes`

技术方案主线“有界明文预览 + 可重建搜索文档 + 本地 Vision OCR 队列 + 低敏输出门禁”与 PRD v1 一致，且没有把标签/收藏、详情编辑、隐私页真实 App 清单或面板专项布局提前并入 Step 1。方案已经具备可测试基础：search document / preview snapshot 职责清楚，OCR recognizer protocol + mock hook 方向正确，P13A 新门禁和旧 P11E/P8/P8I/P9A/P9B 迁移方向也正确。

进入开发前仍建议补强 5 类可验收契约：fixture 明细、OCR mock 状态控制、搜索状态 pass/fail、性能门槛的数值或事件化判定、低敏输出 scan 与旧门禁迁移的 fail-closed 细则。否则实现完成后容易出现“方向正确但门禁不可稳定执行”的灰区。

## 必须改

1. 固化 synthetic fixture 清单和预期结果。
   技术方案列出了需要测试的 fixture 类型，但还需要写成可执行矩阵，避免开发和验收各自造样本。建议每个 fixture 至少有 `fixtureID`、record kind、关键字段、预期 preview、预期搜索、预期低敏输出规则。

2. OCR mock 需要明确可控制 pending / running / failed / retry。
   “MockVisionTextRecognizer 可返回 success、pending delay、running hold、failure”的方向正确，但验收需要更硬：
   - pending 应由 queue 中已入队但未开始的任务稳定表示。
   - running 应由 mock 持有异步 continuation / latch，测试主动释放，不依赖机器速度。
   - failed 应返回低敏 error code，不抛出真实 Vision 细节。
   - retry 应能先失败、再由用户触发或测试 hook 转回 pending/running，最终成功或再次失败。
   - mock 状态不得依赖真实 Vision、真实图片质量或系统性能。

3. 搜索状态需要写成 pass/fail 判定。
   技术方案定义了 `idle / results / empty / emptyIndexing / partialIndexing / failed`，但建议补充每个状态的触发 fixture 和失败条件：
   - `empty`：全部索引完成且无命中。
   - `emptyIndexing`：当前无命中，但 OCR 或 reindex 队列仍有 pending/running。
   - `partialIndexing`：已有非 OCR 命中，同时 OCR 或 reindex 仍 pending/running。
   - `failed`：只允许表达局部 OCR/index 失败，不应让整个搜索框不可用。
   - OCR 完成前搜索 `VISION-004` 应进入 `emptyIndexing` 或 `partialIndexing`；完成后进入 `results`。

4. 性能门槛需要“结构性 fail-closed + 最小数值 smoke”。
   PRD 和技术方案已有结构性要求：面板打开、搜索输入、滚动不等待 OCR，不同步读所有 payload，不在 MainActor 做大图 decode/Vision。测试侧认为这必须作为阻断门禁，同时建议增加最小数值 smoke：
   - 结构性门禁：P13A 检查 panel open / search input / scroll 主路径没有同步 OCR、批量 `readPayload`、全量 image decode。
   - 事件化门禁：mock OCR running hold 时，面板 preview 和搜索状态必须先返回，不能等 mock 释放。
   - 数值 smoke：开发记录固定本机样本规模、Debug/Release 构建、阈值和测量方式；例如 100 条 mixed fixture 下搜索状态返回时间、10 张 large image 入队时首屏可见时间。具体毫秒值可由开发记录确定，但最终验收前必须有数值或事件化证据，不能只写“不卡顿”。

5. low-sensitive output scan 需要明确 forbidden token / pattern。
   技术方案列了禁止输出类型，但 P13A 和迁移后的 P8/P9 需要可扫描模式。建议默认扫描验证输出、开发记录、验收记录和新增日志样例：
   - 本机路径：`/Users/`、真实 home 目录、`file:///Users/`。
   - 凭据：`Authorization`、`Bearer `、`sk-`、`api_key`、`secret`、`password`、`验证码`。
   - payload：完整 fixture 正文、完整 URL、完整 file path、图片 base64、完整 OCR text。
   - provider：provider raw request/response、外部 OCR endpoint、multipart image upload。
   输出可以包含 fixture id、record id suffix、length、hash、boolean、error code，不应包含 raw 内容。

6. 旧 P11E/P8/P8I/P9A/P9B 迁移必须 fail closed。
   轻量静态抽查显示当前旧 verifier 仍有 Step 4D hardening/redacted 断言，例如：
   - P11E 仍检查 repository load 不预取 payload、default UI 不读 payload。
   - P8 仍有 `redacted_card_preview`、`settings_hardening_section`、`no_default_payload_or_summary`。
   - P8I 仍要求 `settings.clipboardHardening.*` 和 redacted panel state。
   - P9B 仍要求 `record.redactedPreview`、metadata-first read model。
   这些断言不能直接作为 Step 1 阻断门禁。建议技术方案明确：
   - P13A 是 Step 1 当前事实源门禁。
   - P11E 退役为历史 baseline，或只保留 output boundary / no provider / no sensitive verifier output 检查。
   - P8/P8I/P9B 必须迁移为 bounded plaintext preview、settings hardening token 移除、search document/read model、purpose-classified content access。
   - 迁移后门禁应在旧 redacted/hardening 断言仍参与 `ok` 时失败，而不是静默通过。

7. Search document 双事实源需要明确 fail 条件。
   方案允许 `clipboard_items.search_text` 兼容存在，但当前事实源应为 search document / FTS。建议 P13A fail 条件写清：
   - 搜索主路径只基于 visible/redacted preview，fail。
   - 搜索主路径只基于旧 pinned displayName / metadata，fail。
   - 新 search document 存在但查询仍绕过它，fail。
   - 旧字段只作为迁移或兼容存在，且不参与当前查询事实源，可通过但需在输出中标记 `baseline_reference`。

## 可优化

1. `ClipboardPayloadReadPurpose` 是否改名可不阻塞 Step 1。
   从测试角度，当前更重要的是 purpose 语义被 verifier 重新解释为性能/审计分类，而不是隐私 allowlist。改名为 `ClipboardContentAccessPurpose` 可读性更好，但不是 P1。

2. Search ranking 首版不必过度精细。
   只要 direct content / URL / file / OCR 命中优先于 source/type/time，并且排序集中在 coordinator 或 repository 层，后续可调权重。

3. URL query 不作为 Step 1 必验是可接受取舍。
   本地 search document 可以有界保留 raw URL；日志/verifier 不输出完整 query。测试不应要求完整 query 搜索。

4. 多语言 OCR 准确率不应作为 Step 1 阻断。
   用 `VISION-004` 或等价低敏英文 token 做必验，其他语言准确率作为 P2 风险记录。

5. 真实 UI 手工验收可以后置到实现验收。
   技术方案阶段只需确认状态和证据可产生，不需要现在触发真实 App、真实剪贴板、TCC、provider 或系统设置。

## 可吸收建议

### 1. 推荐 fixture 矩阵

| fixtureID | 类型 | 输入摘要 | 必验 preview | 必验搜索 | 低敏输出要求 |
| --- | --- | --- | --- | --- | --- |
| `txt_alpha_004` | text | `Alpha roadmap item 004 search baseline` | 显示可读正文片段，不只显示长度 | `Alpha` 命中 | verifier 不输出完整正文，只输出 fixtureID / hit=true |
| `url_step1_004` | URL | `https://example.com/blocks/clipboard-step1` | 显示 host/path 摘要 | `example.com`、`clipboard-step1` 命中 | 不输出完整 URL query 或真实 URL |
| `rtf_plain_004` | rich text | RTF 中包含 `Rich Plain 004` | 显示 plain text | `Rich Plain 004` 命中 | 不输出 RTF 原文 |
| `file_url_report_004` | file URL | synthetic path，文件名 `Report-004.pdf` | 显示文件名或有界路径摘要 | `Report-004`、`pdf` 命中 | 不输出真实 `/Users/...` 路径 |
| `image_ocr_success_004` | image | mock OCR text `VISION-004` | 显示缩略图/图片状态 + OCR 状态 | OCR 完成后 `VISION-004` 命中 | 不输出图片 base64 或完整 OCR text |
| `image_ocr_failure_004` | image | mock failure `vision_unreadable` | 显示 failed / retry | 不让全局搜索失败 | 只输出 error_code |
| `image_ocr_retry_004` | image | first fail, retry success | failed -> retry -> pending/running -> succeeded | retry 成功后命中 | 只输出状态转换和 boolean |
| `long_text_004` | long text | 超过 preview/index 阈值 | preview 截断但可识别，`isTruncated=true` | 阈值内 token 命中 | 不输出完整长文本 |
| `large_image_004` | large image | 例如 4096x4096 synthetic image | 入队但不阻塞列表 | OCR 不阻塞搜索输入 | 输出尺寸/length，不输出图片内容 |

### 2. 推荐 P13A pass/fail 规则

P13A 建议至少包含以下 fail-closed checks：

- `bounded_preview_default`：panel preview 默认来自 bounded preview snapshot；若回到 `record.redactedPreview` 或只显示长度，fail。
- `view_no_bulk_payload_read`：panel row/card/tray 主路径出现批量 `readPayload`、全量 decode 或同步 OCR，fail。
- `search_uses_read_model`：搜索主路径没有使用 search document / FTS / read model，fail。
- `search_fields_complete`：content/rich/url/file/source/type/time/ocr/status 字段缺任一职责，fail。
- `search_state_contract`：empty/emptyIndexing/partialIndexing/failed 无可测状态，fail。
- `ocr_mock_deterministic`：pending/running/failed/retry 不能由 mock 稳定控制，fail。
- `ocr_no_provider_no_file_scan`：出现外部 OCR provider、图片上传、file URL 本体 OCR、目录扫描或新增权限请求，fail。
- `settings_negative_tokens_removed`：active UI 仍引用 `settings.clipboardHardening.*`、`redacted preview`、`payload 不可见`、`只显示字符数` 等，fail。
- `low_sensitive_output`：验证输出含完整正文、完整 URL、完整路径、完整 OCR text、base64、secret、Authorization、provider raw payload，fail。
- `current_evidence_only`：旧 003 / Step 4D 文档参与 `ok`，fail；只允许进入 `baseline_reference`。

### 3. 推荐搜索状态验收样例

1. 无查询时展示默认列表，状态为 `idle` 或等价默认状态。
2. 搜索 `Alpha` 命中文本 fixture，状态为 `results`。
3. 搜索 `no-such-fixture-token`，且所有索引完成，状态为 `empty`。
4. 搜索 `VISION-004`，OCR success fixture 仍 pending，状态为 `emptyIndexing`。
5. 搜索 `Alpha`，同时 OCR success fixture 仍 pending，状态为 `partialIndexing`。
6. OCR failure fixture 失败后，搜索其他字段仍可用；状态可显示局部失败，但不能让搜索整体 fail。
7. OCR retry 成功后，搜索 `VISION-004` 从 `emptyIndexing` 转为 `results`。

### 4. 推荐性能验收样例

1. Mock OCR 被 hold 在 running 状态时，打开面板仍返回 preview / image status，不等待 OCR 完成。
2. Mock OCR running 时输入搜索，搜索状态返回 `emptyIndexing` 或 `partialIndexing`，不等待 OCR 完成。
3. 100 条 mixed fixture、10 张 large image 入库后，OCR 进入队列，首屏 preview 不做同步 Vision。
4. 滚动列表时不触发全量 payload decode 或 OCR。
5. 开发记录固定一次本机测量：样本规模、构建配置、机器环境、首屏可见时间、搜索状态返回时间、OCR 队列开始时间。具体数值由开发记录给出，测试验收按记录复跑或静态/事件证据复核。

### 5. 推荐旧门禁迁移口径

| 脚本 | Step 1 推荐定位 | 必改方向 |
| --- | --- | --- |
| `p11e_clipboard_hardening_checks.py` | 退役为历史 baseline，或改为 output boundary check | 不再要求默认 UI 不读 payload / redacted read model；保留 no provider、no sensitive output、purpose-classified access |
| `p8_clipboard_product_polish_checks.py` | 当前 clipboard 产品展示门禁 | `redacted_card_preview` 改为 bounded plaintext preview；`no_default_payload_or_summary` 改为 no unbounded View payload read |
| `p8i_settings_clipboard_system_checks.py` | Settings clipboard system 门禁 | `clipboard_hardening_settings` 改为 hardening negative token removed + storage/performance retained |
| `p9a_clipboard_repository_storage_smoke.py` | Repository smoke | 补 search document / OCR state / FTS insert-update-delete smoke；保持低敏输出 |
| `p9b_clipboard_appstate_repository_integration_checks.py` | AppState/Repository integration | `record.redactedPreview` / metadata-first 断言迁移为 bounded preview + search document + content access purpose 分类 |

## 残余风险

1. Vision 识别稳定性依赖 macOS 版本和图片质量；mock 可保证状态测试，不能证明真实 OCR 准确率。
2. 性能阈值如果只在开发记录中后补，技术方案阶段无法提前判断最终体验是否达标。
3. 旧 verifier 迁移前，任何“全量门禁 PASS”都可能是假阳性或假阴性。
4. Search document 与旧 `search_text` 共存期间，必须持续防止双事实源。
