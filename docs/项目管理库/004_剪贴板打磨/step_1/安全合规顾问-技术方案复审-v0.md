## 结论

结论：`approve-with-changes`

技术方案主线成立：`有界明文预览 + 可重建搜索文档 + 本地 Vision OCR 队列 + 低敏输出门禁` 能把“链路可访问真实内容”限制在本地 App 内的明确读取、预览、搜索和 OCR 索引路径，而不是放大为 provider、日志、CLI、自动化的默认无限制外发。

当前没有 `reject` 级问题，也没有发现必须回到用户重新澄清的问题。进入开发前建议补强两类 must-change：一是 P13A / low-sensitive scan 的 forbidden token 覆盖面；二是把 OCR 输入边界、无新增权限、无 provider/自动化外发写成 verifier 可检查的 fail-closed 断言。

## 已确认的安全事实

1. 本地明文边界清楚。
   - 方案没有要求 View 层批量直接读取完整 payload。
   - 面板默认展示通过 `ClipboardContentPreviewSnapshot` 或等价 bounded preview。
   - 搜索通过 `ClipboardSearchDocument` / FTS 或等价 read model，不再依赖 redacted preview 字符串。
   - 完整 payload 可被 App 内明确路径读取，但高频面板打开、滚动和搜索输入不应同步读取所有完整 payload。

2. Vision OCR provider 边界清楚。
   - OCR 使用 macOS Vision。
   - OCR 只处理剪贴板历史中已有 image payload。
   - 明确不读 file URL 指向文件本体，不扫描本地目录，不调用 provider，不新增系统权限，不输出图片 base64 或 OCR full text。
   - `ClipboardVisionTextRecognizer` protocol + `AppleVisionTextRecognizer` implementation + mock recognizer 的分层利于测试和安全门禁。

3. CLI / 日志 / verification JSON 默认输出方向正确。
   - 日志默认记录状态、长度、类型、耗时、错误码、短 id / hash、队列状态、图片尺寸等低敏字段。
   - CLI 若被触及，默认输出结构化、有界；完整内容需要显式参数或独立 action。
   - Verification JSON 样例使用 boolean、count、fixture id、hash、length，不输出 fixture 正文、完整 URL、完整 OCR 文本、完整路径、图片 base64 或真实 home path。

4. 旧门禁迁移方向正确。
   - 旧 Step 4D 的“默认 payload 不可见”不再作为 Step 1 pass 条件。
   - 低敏输出、无 provider 外发、无真实敏感 fixture 的门禁精神被保留。
   - 新 P13A 作为 Step 1 当前事实源是合理方向。

## 必须改

### 1. P13A forbidden token / sensitive output scan 需要补全凭据类清单

当前方案已列出 `Authorization header`、`API key`、`secret`、`验证码`，但 Step 1 明文搜索和 OCR 会把真实剪贴板内容转成可搜索文档。真实剪贴板中经常包含更多凭据形态，若只靠泛化 `secret` 容易漏检。

技术方案应补充 P13A 或共享 sanitizer 的 forbidden token / pattern 清单，至少覆盖：

- `Authorization`、`Bearer`、`Basic`、`X-API-Key`、`api_key`、`access_token`、`refresh_token`、`id_token`。
- `sk-`、`sk_proj`、`sk-proj`、常见 provider key 前缀或 provider secret 文案。
- `password`、`passwd`、`pwd`、`otp`、`verification code`、`验证码`、`2fa`、`mfa`。
- `BEGIN PRIVATE KEY`、`BEGIN RSA PRIVATE KEY`、`BEGIN OPENSSH PRIVATE KEY`、SSH private key block。
- `cookie`、`session`、`set-cookie`、`jwt`、`webhook`、带 token query 的 URL。
- 图片/OCR 输出相关的 `base64`、`data:image`、`ocrText` full dump、`fullOCRText` 等字段名。

要求不是禁止 App 内搜索这些内容，而是禁止它们出现在日志、CLI 默认输出、verification JSON、开发记录、验收记录和失败详情中。P13A 应报告 pattern label、文件或字段名、计数即可，不输出命中的原文。

### 2. P13A 需要把 OCR 输入边界和权限边界变成 fail-closed 断言

技术方案正文已经写清 OCR 不读 file URL 本体、不扫描目录、不新增权限、不上传 provider，但 P13A 最低断言集合还主要集中在 preview/search/OCR async/provider 未接入。建议在 P13A 最低断言中显式加入：

- OCR 输入只来自 image payload / payload repository，不来自 file URL 指向文件本体。
- OCR queue / recognizer 相关文件不得引入目录扫描、任意文件读取或 file URL 自动读取路径。
- Step 1 新增 OCR/search/preview 文件不得引入 `ScreenCaptureKit`、Screen Recording、Accessibility、Automation、Full Disk Access、TCC reset、系统设置跳转、AppleScript、CGEvent 等权限或自动化 token。
- Step 1 OCR/search/preview 文件不得引入 provider upload、`URLSession` 外发、provider route 直连、多模态 provider call、Authorization header 或 image upload。
- 面板打开、搜索输入、OCR 入队、OCR 完成、OCR retry 不得触发 provider 或自动化外发。

这些断言应允许 existing unrelated provider / permission code 存在于项目其他模块，但 Step 1 新增或 touched 文件应 fail closed。

### 3. Verification JSON 和开发记录的低敏 schema 需要写成开发子批次验收条件

方案 9.3 已给出 JSON 样例，但建议在 Step 1A-1D 的验收中明确：每个子批次新增或更新的 verifier 都必须采用同一低敏 schema。

最低要求：

- 输出相对路径、suite、boolean、count、fixture id、record id short hash、length、duration、error category。
- 不输出完整 payload、完整 URL、完整 file path、完整 OCR text、图片 base64、真实 home path、真实 email、provider raw request / response、凭据类命中原文。
- 失败详情也必须走同一 sanitizer，不能只在 PASS 输出时低敏。

这项可以并入 Step 1D，但如果 Step 1A-1C 已经新增 verifier 或 smoke，也应同步遵守。

## 可优化

1. 统一复用 sanitizer。
   - 如果项目已有 `verification_sanitizer.py` 或等价工具，P13A、P9A/P9B 更新和 OCR smoke 应复用共享 sanitizer，而不是每个脚本自己写正则。
   - 这样能降低后续 URL、file path、email、token、base64 检测口径漂移。

2. 明确 URL query 的本地索引与输出差异。
   - 方案已建议完整 query 不作为必验搜索字段，日志 / verifier 不输出完整值。
   - 建议补一句：App 内本地 search document 可以按长度上限索引 query，但任何 verifier / log 只记录 host、path segment、length 或 hash。

3. `ClipboardPayloadReadPurpose` 重释义建议落文档。
   - 如果开发阶段先不改名，应在开发记录和 verifier 中说明 purpose 是成本 / 审计分类，不再是默认隐私 allowlist。
   - 避免后续复审误把 Step 1 明文目标判为违反 Step 4D hardening。

4. OCR mock fixture 建议拆成功、失败、延迟和大图四类。
   - 成功用于 `VISION-004` 命中。
   - 失败用于低敏错误和 retry。
   - 延迟用于 pending/running/partialIndexing。
   - 大图用于证明不阻塞 UI 和不输出 base64。

5. Search document 表中的 raw text 字段属于本地派生数据。
   - 这是可接受风险，但建议技术方案提醒 delete/prune/policy redaction 必须同步删除或失效派生表、FTS 和 OCR text，避免“record 已删但索引仍可搜”。
   - 方案已有事务路径，开发验收中应保留这个一致性检查。

## 可吸收建议

1. 子批次顺序可接受。
   - Step 1A 先做 search document / bounded preview，Step 1B 接搜索状态，Step 1C 接 Vision OCR，Step 1D 做设置页清理和 verifier 迁移，是合理顺序。
   - 安全合规建议在 Step 1A 就同步建立 P13A 的低敏输出骨架，不必等到 Step 1D 才开始，否则中间开发记录容易污染。

2. 不需要把 Step 5 的 CLI 广义对象管理拉回 Step 1。
   - Step 1 只要求若触及 CLI 搜索或调试输出，则默认结构化、有界，完整内容显式参数触发。
   - App / helper / CLI 广义对象管理仍应留在 Step 5。

3. 不需要新增复杂权限开关。
   - 用户已接受明文优先，本阶段不需要恢复内容保护开关。
   - 安全边界应通过本地数据流、输出控制、provider 禁止和 verification sanitizer 实现。

4. OCR 不需要外部准确率承诺。
   - 使用低敏短 token 和 mock hook 做验收即可。
   - 多语言准确率、Vision 版本差异和复杂图片质量问题可列为 P2 残余风险。

5. 旧 Step 4D 文档只能作为 baseline reference。
   - 技术方案已表达这一点。
   - 后续 verifier 输出应避免把旧 acceptance / archive 当作当前 pass 事实源。

## 可接受残余风险

1. 本地搜索文档和 OCR text 会保存真实剪贴板派生内容。
   - 这是 Step 1 明文搜索和 OCR 的必要结果。
   - 可接受前提是删除、裁剪、policy redaction、OCR retry 和 search document / FTS 生命周期保持一致。

2. 面板 bounded preview 会展示真实内容片段。
   - 这是用户确认的产品方向。
   - 安全合规不要求恢复 redacted preview，只要求有界预览、性能控制和输出边界。

3. CLI 可在显式参数下输出完整内容。
   - 这符合“链路可访问真实内容”的方向。
   - 默认输出、help、错误输出和批量输出必须仍然结构化、有界。

4. Vision OCR 结果受系统版本、语言和图片质量影响。
   - 使用 mock / fixture 验收 pending/running/succeeded/failed/retry 状态即可。
   - 多语言准确率不阻塞 Step 1。

## 建议给项目负责人的回写摘要

建议允许技术方案继续进入开发准备，但要求 App 架构师或开发任务在进入实现前补充：

- P13A / sanitizer 的凭据类 forbidden pattern 清单。
- P13A 对 OCR 输入边界、权限边界、无 provider/自动化外发的 fail-closed 断言。
- 每个子批次 verifier / smoke / 开发记录采用同一低敏输出 schema。

补齐这些后，安全合规视角不阻塞 Step 1 技术方案进入开发拆解。
