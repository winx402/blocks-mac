# Step 1 开发技术方案复审 v0

状态：approve-with-changes
日期：2026-07-07
角色：开发
对象：`App架构师-技术方案-v0.md`

## 1. 结论

Step 1 技术方案主线可落地：用有界明文 preview snapshot、可重建 search document、本地 Vision OCR 队列和低敏输出门禁替换当前 redacted-first 路径，方向与 PRD v1 一致，也没有把标签、详情编辑、隐私页和面板专项布局扩进来。

开发结论为 `approve-with-changes`。进入实现前需要把几个工程契约写硬：新 search document 与现有 `clipboard_items.search_text` / `clipboard_fts` 的事实源关系，repository 事务边界，OCR result 更新一致性，`ClipboardPayloadReadPurpose` 重释义或改名方案，以及 P13A verifier 的红绿门禁范围。

## 2. 当前代码事实

当前代码中已有以下事实，说明方案识别的问题真实存在：

- `AppDatabase` v1 已创建 `clipboard_items.search_text` 和 `clipboard_fts(record_id, search_text)`。
- `ClipboardRepository.insert(record:payload:)` 当前由私有 `searchText(for:payload:)` 拼接旧搜索文本，并通过 `replaceFTS(recordID:searchText:)` 写入 FTS。
- `ClipboardRepository.deleteRecords(_:)` 已删除 `clipboard_fts` 和 `clipboard_items`，但不存在 search document / OCR 派生表。
- `ClipboardRepository.applyPolicy(...)` 当前 redaction 会把 `clipboard_items.search_text = NULL` 并清 FTS；未来 search document / OCR state 必须同步失效。
- `ClipboardStore.preview(for:)` 当前调用 `record.redactedPreview(...)`。
- `ClipboardController.filteredRecords(...)` 当前对非空查询仍用 redacted preview / redacted searchable text / pinboard name 做内存过滤。
- `ClipboardPayloadReadPurpose` 目前只有 `paste`、`copyPlainText`、`hoverDetail`、`translationPreview`，语义仍残留 Step 4D allowlist。
- `ClipboardSettingsPane`、`DataAuditSettingsPane`、P8/P8I/P9B/P11E 等仍有 `settings.clipboardHardening.*`、`redacted`、metadata-first 相关断言。

## 3. 必须改

### 3.1 search document 事实源必须单一

技术方案需要明确：

- `ClipboardSearchDocument` 是当前搜索与 preview 派生内容的唯一事实源。
- `clipboard_fts` 只是由 search document 生成的查询投影。
- 现有 `clipboard_items.search_text` 只能二选一处理：删除 / 停止写入，或作为兼容投影由 search document 同步生成。不能继续由旧 `ClipboardRepository.searchText(for:payload:)` 独立生成。

推荐口径：

> Step 1 新增 `clipboard_search_documents` 后，`ClipboardSearchDocumentBuilder` 是唯一生成搜索文本和 bounded preview 的入口。`clipboard_fts` 从 search document 重建；`clipboard_items.search_text` 不再作为当前事实源，如保留只用于兼容，并由同一 builder 派生。

P13A 应断言旧 `searchText(for:payload:)` 不再是 active write path，或者断言它仅委托新 builder。

### 3.2 schema migration / 开发库策略要明确

方案建议新增派生表，但未明确数据库版本策略。开发前需要确认：

- 是否 bump `PRAGMA user_version`。
- 旧开发期数据库是否走迁移，还是允许重建。
- search document 缺失时如何 backfill。
- backfill 失败是否阻塞 App 启动。

推荐口径：

> Step 1 使用新的 schema version。打开旧 v1 数据库时创建 search document / OCR state 相关表，不删除原始 records/payloads；缺失 search document 的记录以 `pendingIndex` 状态进入后台重建，App 启动和面板打开不等待 backfill 完成。

### 3.3 repository 事务一致性要补成 API 契约

当前方案列了触发点，但开发还需要明确 repository 方法形状和事务约束。

必须写清：

- insert：record、payload、search document、FTS 在同一 transaction 成功或失败。
- duplicate insert：如果因 signature dedupe 返回旧记录，不应误建新 search document。
- delete/prune：record、payload cascade、search document、FTS、OCR state 同步删除；sidecar 文件仍可在 DB transaction 成功后删除。
- policy redaction：payload 派生字段、OCR text、FTS 必须失效，不能只清旧 `search_text`。
- OCR update：只允许更新仍存在、revision 匹配、未被 redacted/deleted 的 record；OCR text/status 与 FTS 更新同一 transaction。

推荐 API 输入：

- `upsertSearchDocument(recordID:payload:ocrState:reason:)`
- `deleteSearchDocuments(recordIDs:)`
- `markSearchDocumentRedacted(recordID:)`
- `updateOCRResult(recordID:revision:result:)`
- `rebuildSearchDocuments(limit:)`

命名不强制，但这些事务职责需要在方案中出现。

### 3.4 Step 1A-1D 拆分需要加前置红灯门禁

现有 1A-1D 可落地，但建议每批次前置验证更清晰：

- Step 1A-0：先新增 P13A 红灯 gate，确认当前代码因 redacted preview、visible filter、旧 hardening settings、旧 FTS fact source 等失败。
- Step 1A：schema / builder / bounded preview snapshot / insert-delete-prune 事务，不做 OCR 队列。
- Step 1B：Store search state 和 repository search 接入，非空查询不再走 `ClipboardController.filteredRecords` 的 redacted visible filter。
- Step 1C：Vision OCR queue、mock recognizer、OCR result transaction、retry 状态。
- Step 1D：Settings active token 清理、旧 P8/P8I/P9A/P9B/P11E 迁移、低敏输出回归。

这样可以避免先改 UI 明文展示，但底层 search/preview 事实源尚未稳定。

### 3.5 purpose 命名必须尽早收敛

方案提出可保留 `ClipboardPayloadReadPurpose` 并重释义，但开发视角不建议继续使用 “PayloadReadPurpose” 承载 preview/search/OCR，因为它会和 Step 4D 的隐私 allowlist 语义冲突。

推荐口径：

> Step 1 引入 `ClipboardContentAccessPurpose`，用于高成本内容访问分类，包含 `previewBuild`、`searchIndex`、`ocrInput`、`paste`、`copyPlainText`、`hoverDetail`、`translationPreview`。旧 `ClipboardPayloadReadPurpose` 在 Step 1 中退役或只作为 paste/copy/hover/translation 的兼容 alias，不再用于 verifier 断言。

如果为了降低改动保留旧名称，必须在方案和 P13A 中明确：它已不是隐私 allowlist，而是 performance / lifecycle 分类，并补齐 `previewBuild`、`searchIndex`、`ocrInput`。

### 3.6 P13A 最低断言需要更具体

方案中的 P13A 方向可实现，但建议补成 fail-closed 最低清单：

- 脚本自身存在且可执行。
- 新 Swift 文件 target membership 可解析。
- `ClipboardSearchDocument` / `ClipboardContentPreviewSnapshot` / OCR state 或等价类型存在。
- `ClipboardSearchDocumentBuilder` 或等价 builder 是唯一 search text / preview snapshot 构建入口。
- `ClipboardStore.preview(for:)` 不再默认调用 `redactedPreview`.
- 非空搜索主路径不再只调用 `ClipboardController.filteredRecords(query:)` 做 visible string filter。
- repository insert/delete/prune/policy redaction/OCR update 有 search document + FTS 一致性证据。
- OCR recognizer protocol + Apple Vision implementation + mock/test hook 存在，且 Vision import 不进入 BlocksCore。
- Settings active UI 不引用 `settings.clipboardHardening.*`。
- 旧 P11E/P8/P8I/P9B hardening 断言不参与 Step 1 `ok`。
- 输出 JSON 只包含 fixture id、长度、状态、相对路径、布尔值，不输出 fixture 正文、完整 URL、完整 path、完整 OCR text、base64。

P13A 开发记录应保留 baseline FAIL 和实现后 PASS 的低敏证据。

## 4. 可优化

- Preview snapshot 和 search document 可以共表，也可以分表；如果共表，建议明确 preview 字段与大字段索引字段的读取路径，避免列表加载时带出 256 KB search content。
- Search ranking 首版可先集中在 `ClipboardSearchCoordinator`，不要散在 repository SQL、Store filter 和 View 里。
- OCR claim 可以用持久状态字段实现，不一定要单独 job 表；但需要避免多次启动并发 claim 同一 record。
- RTF plain text 提取如果需要 AppKit，建议放在 BlocksApp builder adapter，再把低敏结果交给 Core repository；BlocksCore 不引入 AppKit。
- URL query 可以本地有界索引，但 verifier 和开发记录不要输出 query 原文。
- `ClipboardRepository.search(_:)` 可以保留 public API，但内部应改为 search document / FTS projection 查询，并返回 search state 所需的 counts 或 pending metadata。

## 5. 可吸收到方案 / 开发的建议拆分

### 5.1 建议文件边界

可作为后续开发方案输入：

- `BlocksCore/ClipboardSearchDocument.swift`：search document、preview snapshot、OCR state、search result state。
- `BlocksCore/ClipboardSearchDocumentBuilder.swift`：纯 Foundation 可完成的 token / bounded text 构建。
- `BlocksCore/ClipboardRepository+SearchDocuments.swift`：search document / FTS / OCR state repository API。
- `BlocksApp/Features/Clipboard/ClipboardContentAccessPurpose.swift`：高成本内容访问分类，如不放 Core。
- `BlocksApp/Features/Clipboard/ClipboardSearchCoordinator.swift`：Store-facing search state。
- `BlocksApp/Features/Clipboard/ClipboardVisionTextRecognizer.swift`：protocol、mock、Apple Vision implementation。
- `BlocksApp/Features/Clipboard/ClipboardVisionOCRQueue.swift`：队列、claim、retry、取消、恢复。

命名可以调整，但职责建议保持独立。

### 5.2 Step 1A 验收建议

Step 1A 不需要触碰完整 OCR。建议验收：

- text、URL、file URL、rich text fixture 入库时生成 search document 和 bounded preview snapshot。
- `clipboard_fts` 由 search document 投影写入。
- 删除 / prune / redaction 同步清理 search document 和 FTS。
- `ClipboardStore.preview(for:)` 使用 preview snapshot fallback，不再走 redacted preview。
- P13A 对当前事实源通过；旧 P11E 不再作为 hardening 阻断。

### 5.3 Step 1B 验收建议

Step 1B 只接搜索状态和主搜索路径：

- 非空查询走 repository search / FTS projection。
- `idle`、`results`、`empty`、`emptyIndexing`、`partialIndexing`、`failed` 有 Store 状态。
- source、URL host/path、file name、rich plain text、type synonyms、最小时间 token 可搜索。
- UI 不在 search input path 同步读全量 payload。

### 5.4 Step 1C 验收建议

Step 1C 专注 OCR：

- recognizer mock 能稳定制造 pending/running/succeeded/failed/retry。
- Apple Vision implementation 只在 BlocksApp，BlocksCore 无 Vision import。
- OCR 只读已有 image payload，不读 file URL 本体，不扫描目录，不请求权限，不触发 provider。
- OCR result 更新 search document + FTS 同一 transaction。
- App 启动时旧 running 状态可恢复为 pending 或 failed。

### 5.5 Step 1D 验收建议

Step 1D 处理清理和门禁：

- Settings active UI 不再引用 hardening/redacted 主叙事。
- P8/P8I/P9A/P9B/P11E 更新为当前事实源，旧 hardening 只作为 baseline reference。
- CLI/log/verifier output sanitizer 覆盖 fixture 正文、完整 URL、完整 path、完整 OCR text、base64、home path、secret pattern。
- `xcodebuild` 和 `blocks --help` 保持通过。

## 6. 残余风险

- Step 1 和 Step 2 都会触碰搜索字段扩展点。Step 1 必须先定义 tags hook，不实现标签事实源；Step 2 接入时不能再绕过 search document。
- Search document backfill 可能引入首次启动后台工作。需要在开发记录中写明不会阻塞面板打开。
- Vision OCR 在不同 macOS 版本上结果会波动。必须以 mock / fixture token 做验收，不能以真实图片准确率作为通过条件。
- 旧 hardening 文案在 String Catalog 中大量存在。Step 1D 应检查 active source，而不是要求历史未引用字符串一次性全删；否则容易扩大范围。
