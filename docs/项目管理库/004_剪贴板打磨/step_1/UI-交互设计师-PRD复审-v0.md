## 1. 复审范围

本轮只复审 Step 1：明文展示、搜索底座与系统 Vision OCR。

不把以下需求提前塞回 Step 1：

- Step 2：标签 / 收藏模型替换。
- Step 3：筛选 hover 安全区、搜索框宽度、单/双击显性控件、卡片密度、选中反馈专项打磨。
- Step 4：详情编辑、保存 / 取消、元数据重组。
- Step 5：隐私页真实 App 清单和 CLI 广义对象管理。
- Step 6：全量集成收口。

本轮是 PRD 文档复审，没有运行 App、没有验证真实 UI、没有触发剪贴板、OCR、provider 或系统权限。

## 2. 总体判断

Step 1 PRD 方向正确，可以进入后续方案准备，但建议先回写少量 UI / 交互验收细节后再开发。

PRD 已经做对的部分：

- 阶段目标清楚：先解决“看得见内容、搜得到内容”，不在 Step 1 做全量剪贴板重设计。
- 明确从默认 redacted / 只显示字符数转向面板明文可读预览。
- 搜索字段范围覆盖正文、来源 App、URL、时间、类型、富文本纯文本、文件名和 OCR 文本。
- Vision OCR 进入范围，并明确只使用 macOS Vision，不做外部 provider OCR。
- OCR 异步、不阻塞面板打开、搜索输入和滚动的体验目标明确。
- Step 2-6 的边界基本守住，没有把标签、详情编辑、隐私页 App 列表或面板专项布局提前写进 Step 1 交付。

需要改的主要原因不是范围方向，而是几类状态还不够可验收：无结果与索引中的关系、OCR 失败后的重试入口、时间字段搜索输入格式。若这些不补，开发和测试容易各自理解，最终体验可能出现“搜不到但不知道是否还在索引”“失败了但不知道能否重试”“时间搜索到底怎么搜”的问题。

## 3. 必须改的问题

### 3.1 搜索无结果与索引中状态需要明确区分

PRD 当前写了默认、有结果、无结果、索引中、失败，但还缺一个关键状态契约：当搜索词无结果且仍有 OCR / 内容索引在后台排队时，用户应看到什么。

必须补充：

- 搜索结果区应区分“确定无结果”和“当前无结果，但部分内容仍在索引 / OCR 中”。
- 当 OCR 或内容索引未完成时，搜索不能只显示普通无结果文案；需要给出轻量提示，例如“部分图片文字仍在识别，结果可能稍后出现”。
- 如果搜索已有部分结果但 OCR 仍在处理，应有非阻塞状态提示，避免用户误以为结果已经完整。
- 验收样例要覆盖：输入能命中 OCR 文本的关键词时，OCR 完成前和完成后的状态变化。

建议写入口径：

- `indexing` 是局部状态，不阻塞输入和滚动。
- `no results` 需要根据 indexing 是否存在拆成 `no results` 与 `no results yet / indexing`。

### 3.2 OCR 失败与可重试入口需要有 UI 位置和触发规则

PRD 已要求失败和可重试，但“具体入口由 UI/技术方案确定”过于松。可重试是用户可见状态，不只是技术恢复机制，至少要在 PRD 中定义入口类别。

必须补充：

- OCR 失败状态显示在图片条目上、搜索结果状态里，或两者之一；位置必须明确。
- 重试入口至少应有一个稳定位置，例如图片条目状态中的 `Retry OCR` 操作，或失败状态行中的重试按钮。
- 重试中要有反馈，不能点击后无变化。
- 重试失败后仍保持失败状态，并允许再次重试或说明不可恢复。
- OCR 不可用、图片过大、Vision 返回错误这类失败是否同文案处理，至少要有统一 fallback。

这不要求 Step 1 做复杂 OCR 管理面板，但需要让失败和重试不是抽象词。

### 3.3 时间字段搜索需要最小输入格式或降级边界

PRD 要求搜索覆盖时间，但又把具体输入格式交给技术方案确认。对用户体验和验收来说，这会导致不可测。

必须二选一：

- 明确 Step 1 支持的最小时间搜索格式，例如 `today`、`yesterday`、`今天`、`昨天`、`2026-07-07`、可见日期文本片段。
- 或者把时间字段从“搜索输入必须支持”降级为“时间字段进入索引 / 排序，具体时间搜索语法后续阶段确认”，并在覆盖矩阵或 PRD 中说明原因。

UI 侧不建议在 Step 1 暗含复杂时间查询。最小可验收格式比开放式“合理搜索”更稳。

## 4. 可后续优化的问题

### 4.1 明文预览的截断和多行策略可以留给实现，但验收要保底

PRD 允许摘要、截断、多行预览或延迟加载，这对 Step 1 是合理的，不能把 Step 3 的卡片密度和布局重做提前塞回来。

建议补一个保底验收：

- 文本 / URL / 富文本纯文本至少能看出内容主体，不再只显示长度。
- 长文本截断时，应保留开头或最能识别内容的片段，不能退回“N characters”。
- 图片应展示缩略图或清楚的图片状态；如果缩略图生成失败，需要 fallback，不应是空白卡片。

### 4.2 搜索命中解释和高亮可后续做

PRD 已定义字段和排序，Step 1 可以不要求完整高亮或命中解释。

建议后续优化：

- 搜索结果可显示命中来源，例如正文 / OCR / URL / 来源 App / 类型。
- 高亮命中词可作为 polish，不应阻断 Step 1。

### 4.3 OCR 语言和置信度可以由技术方案决定

PRD 不承诺完整语言覆盖是合理的。

建议后续优化：

- OCR 完成但置信度低时，是否显示“可能识别不完整”可留到实现或测试阶段。
- 多语言 OCR 的验收可以先覆盖中英文，日文等作为技术确认后的追加项。

### 4.4 输出边界文案不应出现在高频面板主路径

PRD 的“真实内容可访问，交互输出可控”文案方向清楚。UI 侧建议不要把长说明放在剪贴板面板主路径，避免占用高频空间。

建议：

- 面板内只保留必要状态。
- 边界说明放在设置页、帮助说明或验收文档中。

## 5. PRD v0 必须明确的 UI/交互验收口径

### 5.1 明文预览

必须验收：

- 文本记录显示真实正文片段，不再只显示字符数。
- URL 记录显示可识别 URL、host 或 URL 文本。
- 富文本记录显示可读纯文本化内容。
- 图片记录显示图片缩略图或清楚的图片状态，并显示 OCR 状态。
- 文件 / file URL 记录至少显示文件名或可读路径摘要。
- 长内容截断后仍可识别，不能退回 redacted 文案或纯长度文案。

需要低敏 fixture：

- 文本：`Alpha roadmap item 004 search baseline`
- URL：`https://example.com/blocks/clipboard-step1`
- 富文本：含可搜索纯文本。
- 图片：含 `VISION-004` 字样。
- 文件：含可搜索文件名。

### 5.2 搜索状态

必须验收：

- 默认状态：无查询时展示正常列表。
- 有结果：搜索正文、URL、文件名、富文本纯文本、来源 App 和类型同义词可命中。
- 无结果：保留搜索词，有明确空结果文案和清空路径。
- 索引中：OCR / 内容索引未完成时不阻塞输入、滚动和已有结果展示。
- 无结果但索引中：区别于确定无结果。
- 失败：单条 OCR / 索引失败不导致整个搜索不可用。

类型同义词必验：

- `pic`
- `picture`
- `image`
- `ima`
- `图片`
- `图`

排序验收：

- 正文 / URL / 文件名 / OCR 直接命中优先于来源 App。
- 来源 App 优先于类型同义词。
- 同级命中按最近记录时间或更新时间排序。

### 5.3 OCR 状态

必须验收：

- 待处理：图片记录可见，OCR 未开始不阻塞列表。
- 处理中：图片记录可见，面板可滚动，搜索可输入。
- 完成：OCR 文本进入搜索，`VISION-004` 可命中。
- 失败：失败状态局部显示，不影响其他记录搜索。
- 可重试：有明确重试入口，点击后有处理中反馈。
- 不可用 / fallback：Vision 不可用或图片不适合 OCR 时，有清楚文案。

必须明确：

- OCR 不上传 provider。
- OCR 不阻塞面板打开。
- OCR 不要求 Step 1 支持编辑 OCR 文本。

### 5.4 边界文案

必须验收：

- 设置页不再出现与明文目标冲突的内容保护 / 遮挡主路径文案。
- 如果保留容量、保留天数、清理策略等设置，文案不能暗示默认遮挡真实内容。
- 如果新增搜索 / OCR 状态说明，使用“内容”“正文”“图片文字识别”等用户语言，不把 `payload` 作为界面术语。
- Provider / 自动化边界必须避免误导用户以为面板打开或搜索会自动外发全文或图片。

### 5.5 质感与可访问性

必须验收：

- 空状态、无结果、索引中、OCR 失败、可重试状态都有稳定文案和图标 / 视觉层级。
- 文案在中文、英文、日文长句下不挤压核心内容。
- VoiceOver 能读出记录类型、OCR 状态、失败 / 重试按钮和搜索结果状态。
- 键盘用户可以输入搜索、清空搜索，并触达 OCR 重试入口。
- 大量图片 OCR 排队时，面板不出现全局 loading 遮挡。

## 6. 非目标边界确认

PRD 当前正确排除了以下内容，UI 侧不建议改回 Step 1：

- 标签 / 收藏控件、标签筛选和标签管理。
- 筛选 hover 安全区、搜索框宽度、单/双击控件、选中反馈、卡片密度。
- 详情编辑和元数据布局。
- 隐私页真实 App 清单。
- 复杂权限开关和过滤系统。

需要注意：Step 1 改为明文预览后，Step 3 的面板密度和布局验收会受到影响，但不应因此把 Step 3 的专项布局提前纳入 Step 1。Step 1 只需保证明文预览可读、不粗糙、不阻塞搜索和 OCR 状态。

## 7. 对项目负责人的建议

建议结论：`approve-with-changes`。

建议要求产品经理回写 3 个必须改问题后进入下一轮接受判断：

1. 补齐“无结果但索引中”的搜索状态和验收样例。
2. 明确 OCR 失败 / 可重试的 UI 位置和触发规则。
3. 明确时间搜索最小输入格式，或从 Step 1 必验搜索输入中降级。

这些修改不改变 Step 1 范围，也不会把 Step 2-6 需求提前塞回 Step 1。其余可后续优化项可进入实现说明、测试验收或后续阶段 polish。
