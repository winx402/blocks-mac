# 004_剪贴板打磨 Step 4 PRD 预审 v0

## 结论

结论：`approve-for-role-review`。

产品经理已产出 `step_4/产品经理-PRD-v0.md`。项目负责人预审认为：PRD v0 范围聚焦 Step 4 详情编辑与元数据组织，未提前拉入 Step 5 隐私页真实 App 清单 / CLI 广义对象管理，也未把 Step 6 集成验收前置；可以进入角色复审。

## 范围判断

已覆盖 Step 4 必要范围：

- plain text、URL、富文本文本内容、图片 OCR 文本的可编辑边界。
- 图片本体、文件本体、其他非文本类 payload 的不可编辑边界。
- 显式保存 + 取消。
- dirty、saving、save-failed、dirty-navigation 等状态。
- 保存后更新内部内容、派生字段、摘要、搜索索引和更新时间。
- 不更新系统剪贴板。
- 富文本格式保留作为产品目标，但要求技术评估，不静默降级。
- OCR 文本编辑只更新 OCR 文本 / 索引 / 详情展示，不改图片 payload。
- 编辑区默认 2 行、最多 4 行、超过内部滚动。
- 元数据短项两列、长项单行。
- 低敏 fixture 和验收矩阵。

未发现提前扩大范围：

- 未进入 Step 5 的真实 App 清单、图标和 CLI 广义对象管理。
- 未进入 Step 6 的最终集成回扫。
- 未要求实现完整富文本编辑器。
- 未要求保存历史记录时同步改写系统剪贴板。

## 进入复审前不要求产品经理立即返工

当前没有阻塞角色复审的 P0/P1 文档缺口。以下问题不在预审阶段拦截，应交由角色复审补充：

1. 富文本保留的真实可行性和降级取舍。
2. URL record kind 与非法 URL 校验的模型边界。
3. payload / 派生字段 / 摘要 / 搜索索引 / 更新时间是否能形成原子保存事务。
4. OCR retry 与用户编辑 OCR 文本的冲突策略。
5. dirty-navigation 的具体 UI 形态和保存失败反馈位置。
6. 元数据两列 / 长项布局在窄宽度和长内容下的实际验收口径。

## 角色复审要求

角色复审不只提出问题，也应给出可吸收建议和推荐口径。复审结论使用：

- `approve`
- `approve-with-changes`
- `rework-required`

如有 P0/P1，必须说明阻塞原因和建议改法；如只是实现方案阶段确认项，应明确标为非阻塞。

### UI / 交互设计师重点

- 编辑入口：直接编辑还是点击编辑。
- 保存 / 取消操作区稳定布局方案。
- dirty、saving、failed、read-only、OCR 状态的反馈。
- 编辑区 2 行默认 / 4 行上限和内部滚动的体验。
- 元数据两列 / 单行在窄宽度、长文本、多语言下的降级。

### App 架构师重点

- 富文本 payload 的格式保留能力与可接受降级。
- URL、plain text、rich text、OCR text 的保存事务边界。
- 搜索索引同步 / 异步更新与失败回滚。
- OCR 用户编辑文本与 OCR retry 的冲突模型。
- 更新时间字段和 repository / read model 边界。

### 开发重点

- PRD 是否能落到现有 SwiftUI / Store / Repository 结构。
- 保存 / 取消 / dirty-navigation 状态流是否存在实现阻塞。
- 富文本、URL、OCR 文本编辑的工作量和风险。
- 是否需要新增 P13D 或等价 verifier。
- 低敏 fixture 和失败回滚证据如何落地。

### 测试 / 质量重点

- 可编辑 / 不可编辑类型矩阵是否可测。
- 保存成功、保存失败、取消、dirty-navigation、索引更新、系统剪贴板不更新是否有可验证证据。
- 富文本格式保留和 OCR 冲突策略如何验收。
- 编辑区高度、元数据长内容、多语言、可访问性验收是否完整。
