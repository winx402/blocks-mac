## 结论

结论：`rework-required`

P0：0

P1：2

P2：7

总体判断：技术方案 v0 的主路线是对的，已经覆盖 PRD v1 的大部分关键边界：bounded detail read model、metadata snapshot、detail edit purpose、单一 Store / Repository save command、同步事务优先、rich text fidelity gate、OCR user-edited 防覆盖、pasteboard spy/static scan、P13D fail-closed gate 和分批开发。

但当前方案仍有两个开发前必须修正的 P1：

1. 详情编辑后的 mutable content revision 没有闭合，当前代码里的 `ClipboardSearchDocumentBuilder.revision(for:)` 基于原始 `changeCount:signatureSHA256_12`，编辑 payload / OCR text 后不会自然变化；方案中的 `expectedRevision` / `newRevision` 若复用该 revision，会破坏冲突检测、缓存失效和 OCR locked revision。
2. OCR source migration 建议使用 `DEFAULT 'vision'`，会把现有非 OCR、pending、failed、empty、notRequired 记录错误标记为 Vision 来源，削弱 user-edited guard 和 retry / late completion 判断。

这两个问题都可以通过技术方案 v1 小范围修订解决，不需要推翻整体架构。

## 当前代码事实核对

以下为只读抽样事实，开发前仍应以最新工作区复核：

- `AppDatabase` 当前迁移到 `PRAGMA user_version = 3`，并在 `currentVersion > 3` 时抛 unsupported；Step 4 若新增 OCR source / content revision 字段，需要明确 v4 migration。
- `ClipboardRepository.insert` 已在同一 transaction 中插入 record、payload、search document。
- `ClipboardRepository.storePayload` 当前是 `ClipboardRepository.swift` 内 `private` helper，使用 `INSERT OR REPLACE` 写 `clipboard_payloads`，并写入 `created_at`。
- `ClipboardRepository+SearchDocuments.upsertSearchDocument` 会更新 `clipboard_search_documents`、`clipboard_items.search_text` / `updated_at` 和 FTS，可复用为 Step 4 同事务保存路径。
- `ClipboardSearchDocumentBuilder.revision(for:)` 当前是 `"\(record.changeCount):\(record.signatureSHA256_12)"`，不是可编辑内容版本。
- `ClipboardSearchDocument` 当前没有 `ocrTextSource` / `ocrUserEditedAt` / `ocrLockedRevision`。
- `updateOCRResult` 当前只校验 search document revision 和 redacted state，无法表达 user-edited OCR text 不被覆盖。
- `ClipboardPayloadReadPurpose` 当前没有 `detailEditRead` / `detailFullValueRead` / `detailEditSave`。
- 真实 pasteboard 写入路径存在于 paste/copy/autopaste 相关服务和 AppModel 中；Step 4 save path 不应引用这些路径。

## P1 Findings

### P1-1：可编辑内容 revision 未定义，`expectedRevision` 不能复用当前 capture revision

位置：`App架构师-技术方案-v0.md` 第 8、9、10、11、14、19 节。

问题：

方案中 `ClipboardDetailEditCommand.expectedRevision`、`ClipboardDetailSaveResult.newRevision`、`ClipboardDetailSaveFailure.revisionConflict` 和 OCR `ocr_locked_revision` 都依赖 revision 语义。但当前代码中的 search document revision 来自原始 capture 的 `changeCount` 和 `signatureSHA256_12`。用户编辑 plain text、URL、rich text 或 OCR text 时，record 的原始 capture signature 不应变，`changeCount` 也不会自然变；因此当前 revision 不能代表 mutable content version。

风险：

- 保存后 `updatedPreview.revision` 可能不变，purpose-scoped cache / detail read model / preview snapshot 很难可靠失效。
- stale draft 用旧 expectedRevision 保存时可能无法触发 `revisionConflict`。
- OCR `ocr_locked_revision` 如果锁的是 capture revision，后续 detail edit、retry、late completion 的冲突判断会失真。
- P13D 即使验证了 payload / search document 更新，也可能漏掉“版本未前进”的实现缺陷。

建议技术方案 v1 补充：

> Step 4 不复用 capture-based `ClipboardSearchDocument.revision` 作为 detail edit optimistic concurrency token。新增或等价提供 `contentRevision` / `contentVersion`，由 repository 在每次 detail edit save、OCR user-edited save、必要的内容级更新时推进；`ClipboardDetailReadModel.revision` 和 `ClipboardDetailEditCommand.expectedRevision` 使用该 mutable content revision。保存成功返回 `newContentRevision`，并以此失效 detail edit cache / preview snapshot / current search result。capture signature 继续作为原始捕获身份，不承担可编辑内容版本职责。

可选落点：

- 在 `clipboard_items` 增加 `content_revision TEXT NOT NULL` 和 `content_updated_at REAL NOT NULL`，旧数据用现有 `updated_at` 或 deterministic value 回填。
- 或使用 `content_version INTEGER NOT NULL DEFAULT 0`，detail edit save 在同 transaction 中递增。
- 若决定扩展 `ClipboardSearchDocument.revision`，必须同时保留原始 capture identity，避免 tag-only rebuild 或 OCR queue 误判为捕获内容改变。

P13D 建议新增断言：

- `detail_revision_advances_004`：plain text / URL / OCR text 保存后 detail read model revision 前进。
- `detail_stale_revision_conflict_004`：使用保存前 expectedRevision 再次保存应返回 `revisionConflict`，不产生 mutation。
- `detail_cache_invalidation_004`：保存成功后旧 `detailEditRead` cache 不再作为唯一事实源。

### P1-2：OCR source migration 默认值错误，不能把旧数据全部标记为 `vision`

位置：`App架构师-技术方案-v0.md` 第 10.4、19.8 节。

问题：

方案建议：

```text
clipboard_search_documents.ocr_text_source TEXT NOT NULL DEFAULT 'vision'
```

这会把所有既有 search document 行默认标记为 Vision 来源，包括非图片记录、OCR notRequired、pending、running、failed、succeeded empty，以及没有 OCR text 的旧记录。这个默认值与方案中 `ClipboardOCRTextSource.none` 的枚举设计冲突。

风险：

- P13D 可能误以为旧 pending/failed/empty 记录已有 Vision text source。
- retry / late completion guard 可能错误处理没有 OCR 文本的记录。
- metadata / detail read model 展示 OCR source 时会出现误导状态。

建议技术方案 v1 补充：

> OCR source migration 默认值应为 `none` 或等价空来源。迁移后只对 `ocr_status = 'succeeded' AND ocr_text IS NOT NULL AND ocr_text != ''` 的旧行回填 `vision`。`userEdited` 只能由 Step 4 detail edit save 写入；`ignoredLateVision` 只由 late completion 被 user-edited guard 拒绝后写入或记录为低敏事件，不作为所有旧行默认值。

建议 migration 口径：

```text
ALTER TABLE clipboard_search_documents
  ADD COLUMN ocr_text_source TEXT NOT NULL DEFAULT 'none';
ALTER TABLE clipboard_search_documents
  ADD COLUMN ocr_user_edited_at REAL;
ALTER TABLE clipboard_search_documents
  ADD COLUMN ocr_locked_revision TEXT;

UPDATE clipboard_search_documents
SET ocr_text_source = 'vision'
WHERE ocr_status = 'succeeded'
  AND ocr_text IS NOT NULL
  AND TRIM(ocr_text) != '';
```

P13D / P13A 建议新增断言：

- existing image `pending` / `failed` / `succeeded empty` migration 后不是 `vision`。
- user-edited OCR save 后 source 为 `userEdited`，retry / late completion 不覆盖。
- old succeeded OCR with non-empty text 可回填为 `vision`。

## P2 Findings

### P2-1：Repository save command 复用方向正确，但 payload helper 需要明确改造方式

方案已指出 `storePayload` 是 private helper，避免复制写入逻辑是对的。建议进一步写清：

- 如果新增 `ClipboardRepository+DetailEdit.swift`，要么把 payload write helper 抽为 repository 内部可复用的 `replacePayload` / `upsertPayload`，要么把 `saveDetailEdit(command:)` 放到能访问 helper 的同一文件范围。
- 不建议复制 `storePayload` 的 base64 decode、sidecar、byte count 逻辑。
- 当前 `storePayload` 使用 `INSERT OR REPLACE` 并写 `created_at`。Step 4 应明确 payload row 的 `created_at` 是“payload row 写入时间”还是“原始捕获时间”；如果 metadata 会展示 capture time，应只用 `clipboard_items.created_at`，避免误把 payload replace 时间当 capture time。

推荐口径：

> Detail edit save 复用既有 payload decode / sidecar / byte count 逻辑，但通过新的 internal `replacePayload` 明确这是内容更新。capture `createdAt` 保持来自 `clipboard_items.created_at`；内容更新时间来自 `content_updated_at` / `updated_at`。

### P2-2：schema migration 需要独立小节，覆盖 v4、decode/binding 和旧库 smoke

方案目前在 OCR 段落提到 v4 或等价，但 schema 影响不止 OCR source，还包括 content revision。建议技术方案 v1 增加独立 `Schema Migration` 小节：

- `MigrationRunner` 支持 version 4，`currentVersion > 4` 才 unsupported。
- v4 使用 `addColumnIfMissing` 方式兼容已有库。
- 更新 `ClipboardSearchDocument` decode / bindings / initializer / Codable 兼容。
- P9A 或 P13D 提供从 v3 fixture DB 打开并迁移到 v4 的 smoke。
- migration 输出低敏，不打印临时 DB 完整路径。

### P2-3：Rich text fidelity service 需要收窄“文本替换保格式”的承诺

方案建议用 `NSAttributedString` RTF decode / encode 和代表格式检查，方向可行，但“draft plain string 替换后尽量保留 document attributes”仍偏宽。开发实现时需要明确：

- 用户编辑的是 rich text 的 plain string draft，不提供 rich text toolbar。
- 插入、删除、跨格式区段编辑时，新文本继承哪一侧属性，不能靠“尽量”。
- 链接 target、列表、段落、inline style 的保真检查失败必须返回 `richTextFidelityFailed`，不得写入部分成功 payload。
- BlocksCore 是否允许 import AppKit / NSAttributedString RTF APIs 需要在技术方案中明确；BlocksCLI build 也必须覆盖。

推荐口径：

> `ClipboardRichTextFidelityService` 是 conservative service：只要无法证明代表格式未静默丢失，就返回 failure；它不尝试提供完整富文本编辑器能力。

### P2-4：URL validation 建议抽成明确 validator 与 fixture 表

方案列出了 URL 规则，但 `URLComponents(string:)` 本身偏宽松。建议技术方案 v1 指定 `ClipboardDetailURLValidator` 或等价 helper，并列出 pass/fail fixture：

- pass：`https://example.test/path?q=fixture`、`http://localhost:8080/path`、`mailto:user@example.test`。
- fail：empty、relative path、missing scheme、`http:///path`、control character、space-only、`file:///...`、custom scheme unless accepted。
- validator 不发网络、不 open URL、不触发 App launch。
- P13D 输出不得包含 URL 全文，query/path 应 sanitizer 后写证据。

### P2-5：P13D 的 pasteboard 证据要区分 save path 和 copy full value

Step 4 元数据可能有 `copy full value` 显式动作；这类动作未来可能合理写入系统剪贴板，但 PRD 的 `pasteboard_write_attempts=0` 是针对保存动作。技术方案的 static scan 如果简单扫描整个 detail editor 文件里的 `NSPasteboard.general`，可能产生误杀；如果只扫 Step 4 save 文件，又可能漏掉间接调用。

建议口径：

> P13D pasteboard guard 以 save path call graph / adapter spy 为准：`saveDetailEdit(command:)`、`ClipboardDetailStore.save()` 和其依赖不得触达 pasteboard write API。`copy full value` 如在 Step 4 实现，必须走单独显式用户动作和低敏测试，不计入保存动作的 `pasteboard_write_attempts=0`。

### P2-6：保存失败 / reindex failed fixture 需要 fault injection 点

方案要求 `detail_save_atomic_failure_004` 和 `reindex-failed`，但未说明如何稳定制造失败。建议补充：

- repository fixture 支持 fault injection phase：`beforePayloadWrite`、`afterPayloadWriteBeforeSearchDocument`、`afterSearchDocumentBeforeFTS`。
- 默认同步事务路径下，fault 后应整体 rollback。
- 如果本阶段未启用异步 reindex，P13D 应输出 `async_reindex_enabled=false`，并检查没有静默 catch；不强迫实现不可达的 `saved-index-pending` UI。
- 只有实现异步分支时，才要求 `saved-index-pending` / `reindex-failed` 实物 fixture。

### P2-7：批次拆分合理，但建议把 UI skeleton 前移

Batch A-D 大体合理，保留了 P13D-first、repository、rich text/OCR、UI full regression 的审查边界。建议微调：

- Batch A 除 read model / purpose 外，加入 `ClipboardDetailStore` 空状态机 skeleton 和 stable editor 入口占位，避免到 Batch D 才发现状态流与 UI 承载面不匹配。
- Batch B 完成 plain text / URL 后即可跑最小 detail editor save/cancel/dirty path，不要等 rich text/OCR 全部完成才验证 UI 状态。
- Batch C 的 rich text 可 feature-gate；若 fidelity fixture 不过，应及时回项目负责人选择降级，不阻塞 plain text / URL / OCR text 已闭合路径。
- Batch D 聚焦 layout / a11y / full regression，而不是首次集成所有状态。

## 可落地性总结

可落地：

- bounded detail read model 和 metadata snapshot 可基于现有 `ClipboardContentPreviewSnapshot`、`ClipboardSearchDocument` 和 record/tag facts 扩展。
- purpose enum 增加 detail edit/read/save 目的可落地，且与 Step 4D/P11E 的 purpose-scoped cache 方向一致。
- 单一 repository save command 可复用现有 transaction、payload write 和 `upsertSearchDocument` 路径。
- URL 和 plain text 是最稳定的首批可编辑类型。
- OCR user-edited 能通过 search document schema 扩展落地，但必须修正 migration 默认值和 update guard。

需要技术方案 v1 收敛后再开发：

- mutable content revision / optimistic concurrency token。
- OCR source migration 默认值、backfill 和 late completion guard。
- rich text fidelity service 的保守失败规则。
- P13D baseline red 的 failure code、sanitizer 和 fixture fault injection。

## 推荐技术方案 v1 补充结构

建议 App 架构师在 v1 中增加或改写以下小节：

1. `Content Revision and Conflict Token`
   - 定义 `contentRevision` / `contentVersion`、生成方式、何时前进、如何参与 detail read model、save command、OCR locked revision 和 cache invalidation。

2. `Schema Migration v4`
   - 同时覆盖 content revision 和 OCR source；默认值、backfill、decode/bindings、v3 fixture migration smoke。

3. `OCR Source Backfill and Guard`
   - `none` 默认、`vision` 回填条件、`userEdited` 写入条件、late completion skipped 状态。

4. `RichTextFidelityService Contract`
   - 保守策略、不可保真失败、BlocksCore/AppKit 编译边界、最低 fixture。

5. `P13D Baseline Red Codes`
   - baseline red 至少包含 `missing_p13d`、`missing_detail_purpose`、`missing_detail_save_command`、`missing_content_revision`、`missing_ocr_text_source`、`missing_pasteboard_spy`；实现后这些 failure 必须消除。
