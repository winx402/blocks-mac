## 结论

`approve-with-changes`

技术方案 v0 的方向成立，范围保持在 Step 4 详情编辑与元数据组织内，没有提前进入 Step 5 / Step 6。方案已覆盖 bounded detail read model、metadata snapshot、detail edit purpose、单一 Store / Repository save command、默认同步事务、异步 reindex 例外、pasteboard 不写入证据、rich text fidelity gate、OCR user-edited 冲突处理和 P13D fail-closed gate。

测试/质量侧不建议退回重写方案，但进入开发派发或技术方案 v1 前，需要把 P13D evidence schema、fixture / fault injection 稳定性、pasteboard 间接写入证据、rich text fidelity 逐项结果和低敏输出扫描补得更硬。当前方案的断言方向足够，但部分输出字段仍偏汇总，容易让 verifier “知道要查什么”，却不能在缺少某个失败路径证据时明确失败。

## 复审范围

本轮只复审 Step 4 技术方案 v0。不进入开发，不修改 PRD，不启动 Step 5 / Step 6，不触发真实 App、真实剪贴板、provider、Keychain、TCC、系统设置、Finder 或 restart。

## P0 / P1 / P2 Findings

### P0

无。

### P1

1. P13D 输出 schema 需要拆出逐场景 coverage，不能只保留汇总字段。

   方案第 14 节已列出最低断言，但示例输出中 `save_command`、`rich_text`、`ocr`、`pasteboard` 等字段仍是汇总布尔值。为防假 PASS，P13D 应明确列出每个 PRD v1 P1 / failure path 的 fixture id、执行结果和失败原因。

   必须补充的 coverage 字段建议：

   - `save_success`: plain text / URL / rich text / OCR text 四类分别记录 payload 或派生字段、summary、search document、FTS、updatedAt、detail read model 一致。
   - `search_index`: new token hit、old token no longer hit、tag tokens preserved、FTS updated。
   - `save_failure`: transaction failure、search document failure、FTS failure、payload missing、record missing、revision conflict、external update。
   - `async_reindex`: 是否启用；未启用时记录 `not_applicable_reason`；启用时覆盖 `saved-index-pending` 与 `reindex-failed`。
   - `url_validation`: valid http / https / mailto，invalid empty / no scheme / file / custom scheme / control chars，且 invalid mutation count 为 0。
   - `pasteboard`: 四类保存分别 `write_attempts=0`，并记录 static forbidden calls 为 0。
   - `rich_text`: link、paragraph / newline、inline style、list representative item 分项结果。
   - `ocr`: user-edited save、retry blocked or confirmed、late completion ignored、image payload unchanged。
   - `dirty_navigation`: save and continue、discard、continue editing、cancel discard mutation count。

   推荐 pass/fail：缺任一必测 scenario、fixture id、mutation count 或 sensitive-output scan 结果，P13D fail。

2. Fixture 与 fault injection 合同需要写成确定性规则。

   技术方案列出了 fixture 名称和 Batch 验收，但没有明确 fixture runner 的隔离方式、随机性、fake clock、故障注入点和复位规则。保存事务、reindex failed、record missing、revision conflict 这类路径如果只靠静态 scan 或手写 JSON，后续验收不可复跑。

   建议补充：

   - P13D 使用 isolated temp database / fixture repository，不读真实用户数据库。
   - 所有 fixture 使用 deterministic record id、revision、updatedAt fake clock 和 synthetic content。
   - fault injection 至少支持：search document write fail、FTS write fail、transaction rollback、record deleted before save、payload missing、expectedRevision mismatch、late OCR completion。
   - 每个 fixture run 前后清理 temp state；输出只包含 `<TMP>`、fixture id、relative path 或 bounded category。
   - P13D baseline red 时必须证明“缺 implementation / 缺 evidence 会失败”，不是只检查脚本存在。

   推荐 pass/fail：无法重复运行同一 fixture 得到稳定结果，或失败路径需要人工改真实数据库才能复现，判 fail。

3. Pasteboard 不写入证据需要覆盖间接调用路径。

   方案已列 static scan、fake pasteboard / adapter spy 和 fixture JSON，这是正确方向。但 static scan 若只扫 Step 4 detail save 文件，可能漏掉 Store / AppModel / coordinator 间接写入系统 pasteboard 的路径。

   建议补充：

   - P13D 对 Step 4 新增 / 修改的 detail edit 调用链做 forbidden symbol scan：`NSPasteboard.general`、`clearContents`、`setString`、`setData`、`writeObjects`、`ClipboardAutoPasteCoordinator`、`pasteClipboardRecord`。
   - 保存 fixture 运行时注入 fake pasteboard / spy；如果没有 adapter 注入点，则必须证明 detail save command 不依赖任何 paste coordinator。
   - 四类保存分别输出 pasteboard writes 为 0，不能只给总数。
   - 禁止为了验证“不写入”而读真实系统剪贴板内容。

   推荐 pass/fail：出现任何保存路径可达的 pasteboard write symbol，或 spy 未覆盖四类保存，P13D fail。

4. Rich text fidelity 需要从单一 `fidelity_passed` 拆成代表格式逐项结果。

   方案正确要求 RTF round-trip 和代表 fixture，但 P13D schema 只有 `fidelity_passed`，不足以证明链接、段落 / 换行、inline style、列表代表项分别被检查。

   建议补充：

   - `detail_rtf_format_004` 输出 `link_preserved`、`paragraphs_preserved`、`inline_style_preserved`、`list_representation_preserved`、`kind_remains_rich_text`、`plain_text_derivation_updated`。
   - 如果某项不能保留，必须输出当前项目负责人接受记录路径；否则 P13D fail。
   - 保存后 rich payload 与派生纯文本 / summary / search document 同源。
   - 不允许仅比较 plain text 后声称 rich text fidelity 通过。

   推荐 pass/fail：缺逐项 fidelity 结果、rich kind 变为 text、或无接受记录的降级，判 fail。

### P2

1. `saved-index-pending` / `reindex-failed` 是例外路径，方案建议不默认启用是合理的。但 P13D 输出需要写明是否启用，否则测试记录会分不清“未覆盖”和“不适用”。

2. Keyboard / VoiceOver 低敏证据可以在实现验收阶段以 checklist + manifest 记录，不必在技术方案 v0 完全细化；但最终 gate 应检查 tester、date、build / commit、viewport、locale、fixture id、逐项 pass/fail 和 sanitizer。

3. `payload missing` 对 plain text / URL / rich text 默认失败，不自动创建 payload，这个保守策略可接受；后续如产品想允许恢复空 payload，必须重新走项目负责人接受。

4. 空 plain text 当前建议允许，但 PRD 未明确。若实现保留该策略，建议在开发派发中列为可接受口径，并用 summary 文案 fixture 覆盖。

## P13D 覆盖 PRD v1 P1 的判断

总体判断：方向覆盖，但 schema 需要补硬。

| PRD v1 P1 / 高风险点 | 技术方案覆盖 | 测试/质量判断 |
| --- | --- | --- |
| 保存事务与索引一致性 | 默认同一 SQLite transaction，异步 reindex 为例外。 | 可接受；需补 per-scenario evidence 和 fault injection。 |
| 系统剪贴板不更新 | static scan + fake pasteboard / spy + write attempts 0。 | 方向正确；需覆盖间接调用路径和四类保存分项。 |
| 富文本不静默丢格式 | RTF round-trip + fidelity service + 降级接受记录。 | 可接受；需逐项 fidelity 输出。 |
| OCR retry / late completion 不覆盖用户编辑 | 新增 OCR source schema，retry guard，late completion ignored。 | 可接受；需 fixture 证明 user-edited 后 retry / late completion 结果。 |

## Fixture 稳定性推荐口径

P13D fixture 建议按以下规则实现和验收：

| Fixture | 必须证明 | Fail 条件 |
| --- | --- | --- |
| `detail_text_alpha_004` | view -> edit -> dirty -> save；payload / summary / search / FTS / updatedAt / detail model 一致。 | 只更新 UI 或 summary，search 新 token 不命中。 |
| `detail_url_invalid_004` | invalid URL 不产生 mutation，draft 保留。 | invalid URL 改 kind、发网络请求、或写入 repository。 |
| `detail_save_atomic_failure_004` | search / FTS failure 不产生用户不可见部分提交，或进入已定义 pending / failed。 | payload 已写但无 pending / failed / recovery 状态。 |
| `detail_record_missing_during_save_004` | 进入 record-unavailable，draft 不写其他记录。 | 草稿写到新 record 或静默丢失。 |
| `detail_revision_conflict_004` | expectedRevision mismatch 返回 conflict，草稿保留。 | 自动 merge 或覆盖外部更新。 |
| `detail_rtf_format_004` | link、paragraph、inline style、list 代表项有逐项结果。 | 只比较 plain text。 |
| `detail_ocr_user_edited_retry_004` | user-edited 后 retry blocked / confirmed，late completion ignored，图片 payload unchanged。 | late completion 静默覆盖。 |
| `detail_pasteboard_spy_004` | 四类保存 write attempts 均为 0。 | 只给总数或读取真实 clipboard。 |

## 保存事务 / 异步 Reindex 推荐 pass/fail

Pass：

- 默认同步事务下，payload / derived field、summary、search document、FTS、updatedAt、detail read model 在同一 save result 中一致。
- fault injection 导致 transaction failure 时，已保存事实源保持最近一次一致状态。
- 如果启用异步 reindex，P13D 明确展示 `saved-index-pending` / `reindex-failed`，并有恢复 / retry 路径。
- 保存失败后草稿保留，用户可以 retry / cancel / continue editing。

Fail：

- 保存返回成功但 search document / FTS 仍旧且无 pending 状态。
- payload 已更新、summary 或 updatedAt 已变，但 P13D 没有记录索引失败 / pending。
- record missing、payload missing、revision conflict 被吞掉，UI 仍显示成功。
- P13D 只能靠静态文件存在检查证明事务正确。

## URL / Network / Launch 推荐 pass/fail

Pass：

- `http`、`https`、`mailto` absolute URL 可保存，record kind 保持 URL。
- no scheme、empty、control chars、`file:`、默认 custom scheme 被阻止，mutation count 为 0。
- 保存 URL 不触发 network、App launch、Finder、系统权限或 provider call。

Fail：

- 自动补 `https://` 但 PRD 未接受。
- invalid URL 保存后再由其他层修正。
- custom scheme 默认成功且无 allowlist / 接受记录。
- verifier 输出 URL 全文或真实路径。

## 低敏输出推荐口径

P13D 和关联 evidence 应扫描：

- stdout / stderr。
- JSON output。
- evidence manifest。
- 低敏截图 / snapshot 的文件路径和 metadata。
- fixture temp DB path。

禁止输出：

- 真实剪贴板正文。
- 真实 home path / 真实文件路径。
- URL 全文，除非是 synthetic bounded fixture 且不含真实域名。
- OCR 原文、图片/base64。
- 邮箱、secret、Authorization header、二维码、验证码。

建议允许输出：

- fixture id。
- synthetic record id。
- bounded category。
- `<TMP>` / relative path。
- token hash、长度、计数、布尔值。
- low-sensitive host category 或 synthetic host。

## 残余风险

1. Rich text RTF round-trip 仍是实现风险；P13D 能阻断静默降级，但不能保证复杂富文本体验完美。
2. 真实 UI / VoiceOver / 多语言 / 窄宽度证据当前仍应作为后续低敏 evidence 或 Step 6 residual，不应在技术方案阶段写成已实测。
3. Pasteboard 不写入如果只靠 static scan 会有漏检风险；需要 spy 或调用链证据配合。
4. OCR user-edited schema migration 如果实现成 View-local 状态，将无法通过测试/质量接受。
