# Step 4 安全合规顾问技术方案复审 v0

日期：2026-07-07
复审角色：安全合规顾问
复审对象：`App架构师-技术方案-v0.md`
参考输入：`AGENTS.md`、`agents/安全合规顾问.md`、`../step.md`、`产品经理-PRD-v1.md`、`项目负责人-技术方案预审-v0.md`
复审范围：004_剪贴板打磨 Step 4 详情编辑与元数据组织

## 结论

结论：`approve-with-changes`

技术方案 v0 的主线成立：`bounded detail read model + metadata snapshot + detail edit purpose + 单一 repository save command + P13D fail-closed gate` 能把详情编辑限制在本地 App 内的明确用户动作路径，且没有把 Step 5 / Step 6、隐私页真实 App 清单、CLI 广义对象管理、图片/文件本体编辑、系统剪贴板同步写回或 provider / 自动化能力提前引入 Step 4。

当前没有 `rework-required` 级问题。进入开发前建议补强 P13D 的几个硬边界：真实系统 pasteboard 读写都要纳入证据、metadata full value copy 与保存路径要分开验收、provider / 自动化 / 网络外发要有 touched-file denylist、低敏 sanitizer 的凭据类清单要补全。补齐这些后，安全合规不阻塞 Step 4 技术方案进入开发拆解。

## 已确认的安全边界

1. 真实剪贴板保存路径边界清楚。
   - PRD 和技术方案都明确 Step 4 保存不得更新系统剪贴板。
   - 技术方案提供 static scan、fake pasteboard / adapter spy、fixture smoke 三类证据，并要求四类保存输出 `pasteboard_write_attempts=0`。
   - 保存路径不得调用 `ClipboardAutoPasteCoordinator`、`AppModel.pasteClipboardRecord` 或 `NSPasteboard.general` 写入 API。

2. Purpose 隔离方向正确。
   - 新增 `detailEditRead`、`detailFullValueRead`、`detailEditSave` 或等价 purpose。
   - 明确禁止复用 hover、paste、copy、translation、ocrInput、searchIndex、provider 等 purpose 承载详情编辑读写。
   - purpose-scoped cache、保存成功 / 取消 / 切换 / reload 后失效、repository transaction 内重新读取当前事实源的口径正确。

3. 保存事实源边界正确。
   - View 不直接写 payload、summary、search document、FTS 或 OCR 状态。
   - Store 只协调 draft / 状态，Repository 是持久化事实源。
   - 默认保存走同一 SQLite transaction；异步 reindex 只作为例外路径，并有 `saved-index-pending` / `reindex-failed` 状态。

4. OCR 文本编辑边界正确。
   - 只编辑 OCR 派生文本，不改图片 payload。
   - 需要持久化 `userEdited` / override / locked source 语义。
   - retry / late completion 不得静默覆盖用户编辑文本。

5. URL / file URL / rich text 边界正确。
   - URL 编辑只做本地解析，不发网络请求，不打开 App / Finder，不改 kind。
   - `file:` URL 默认按文件本体不可编辑处理。
   - 富文本不得静默降级 plain text；保真失败需要项目负责人接受降级 / 暂缓 / 只读记录。

6. Step 范围控制正确。
   - 未启动 Step 5 / Step 6。
   - 未将真实 UI / VoiceOver / 真实剪贴板 P2 residual 写成已实测事实。
   - 未把 metadata 完整值默认塞进布局路径，而是放到显式动作路径。

## 必须改

### 1. P13D pasteboard 证据应覆盖“读”和“写”，不只覆盖写入

技术方案第 13 节已经要求保存不得调用 `NSPasteboard.general.clearContents`、`setString`、`setData`、`writeObjects`，并通过 spy 输出 `pasteboard_write_attempts=0`。但本次复审重点要求“真实剪贴板不读写”，因此 P13D 还需要覆盖真实 pasteboard 读取。

建议补充：

- P13D 输出同时包含 `pasteboard_read_attempts=0` 和 `pasteboard_write_attempts=0`，或等价字段。
- static scan denylist 除写入 API 外，还应覆盖 Step 4 save / detail edit / verifier touched files 中的真实读取 API，例如 `NSPasteboard.general.string`、`data(forType:)`、`pasteboardItems`、`readObjects`、`availableType` 等。
- 如果某个 metadata “copy full value” user action 需要写系统剪贴板，它必须作为显式复制动作单独验收，不能混入保存事务的 pasteboard no-write 证据；测试仍应使用 fake pasteboard / adapter spy，不写真实系统剪贴板。

推荐口径：Step 4 保存路径不得读写真实系统 pasteboard；metadata full value copy 若实现为复制到 pasteboard，必须是用户显式动作、独立 purpose、fake pasteboard 验收，不得在默认详情展示、布局、保存、取消、dirty-navigation 中触发。

### 2. Metadata full value 显式动作需要细分“读取完整值”和“复制完整值”

技术方案已有 `detailFullValueRead`，并列出 `copy full URL` / `copy full file path` / `expand full bounded text` / `edit content`。这里有一个安全歧义：`copy full value` 可能既需要读取完整值，也可能写入系统 pasteboard。

建议补充：

- `detailFullValueRead` 仅表示读取完整值用于展开或生成显式复制 payload，不等同于系统 pasteboard 写入。
- 如果存在写入系统 pasteboard 的动作，应有单独的 user action / adapter，例如 `detailCopyFullValue` 或等价命名，并用 fake pasteboard 验收。
- 默认 layout、VoiceOver label、tooltip、metadata snapshot 不得触发完整值读取；视觉截断可通过 bounded value + “可复制完整值”说明表达。
- P13D 应区分 `full_value_read_attempts`、`full_value_copy_attempts` 和 pasteboard read/write evidence，避免把保存路径无写入与复制动作混淆。

推荐口径：完整 URL、完整 file path、OCR 原文和 rich text body 只能通过明确用户动作读取；如果动作是复制，则复制行为本身也必须显式、可审计、使用 fake pasteboard 验收，且不把完整值写入 evidence。

### 3. P13D 低敏 sanitizer 需要补全凭据类 forbidden pattern

PRD 和技术方案已经禁止真实路径、OCR 原文、URL 全文、图片/base64、邮箱、secret、Authorization header、二维码、验证码。建议把“secret”拆成更可执行的 forbidden pattern，避免真实剪贴板内容或 OCR 文本中的凭据进入日志、JSON、开发记录或失败详情。

P13D / sanitizer 至少应覆盖：

- `Authorization`、`Bearer`、`Basic`、`X-API-Key`、`api_key`、`access_token`、`refresh_token`、`id_token`。
- `sk-`、`sk_proj`、`sk-proj`、常见 provider key 前缀或 provider secret 文案。
- `password`、`passwd`、`pwd`、`otp`、`verification code`、`验证码`、`2fa`、`mfa`。
- `BEGIN PRIVATE KEY`、`BEGIN RSA PRIVATE KEY`、`BEGIN OPENSSH PRIVATE KEY`、SSH private key block。
- `cookie`、`session`、`set-cookie`、`jwt`、`webhook`、带 token query 的 URL。
- 图片 / OCR 输出相关的 `base64`、`data:image`、`ocrText` full dump、`fullOCRText` 等字段名。

门禁输出只能报告 pattern label、相对文件、字段名、计数和 pass/fail，不输出命中的原文。

### 4. Provider / 自动化 / 网络外发应补 touched-file denylist

方案已经通过 purpose 隔离避免复用 provider purpose，也写明 URL 校验不发网络请求。但 Step 4 涉及 URL 编辑、metadata full value 和 rich text / OCR 处理，建议 P13D 对 Step 4 新增或 touched 文件加一个最小 denylist，防止实现阶段引入外发或自动化能力。

建议 P13D fail-closed 检查：

- Step 4 detail edit / metadata / URL validation / rich text / OCR text edit 文件不得引入 `URLSession`、provider route 直连、image upload、多模态 provider call、Authorization header、Bearer token。
- 不得引入 shell、`Process`、AppleScript、CGEvent、Accessibility、ScreenCaptureKit、Finder / System Settings 打开动作。
- URL validation 仅本地解析，不触发网络可达性检查、App launch、Finder 打开或系统权限请求。
- OCR text edit 不重新运行 OCR、不调用 Vision pipeline、不触发 provider 或自动化外发。

这些检查应允许项目既有 unrelated provider / automation 代码继续存在，但 Step 4 新增或 touched 文件应 fail closed。

### 5. P13D failure detail 也必须走低敏 schema

技术方案已经提供 bounded JSON schema，但建议明确：失败路径也必须低敏，而不是只有 PASS 输出低敏。

建议补充：

- `failures[]` 只包含 rule id、relative path、line / symbol、pattern label、count、low-sensitive reason。
- 不包含完整 URL、真实路径、OCR 原文、rich text body、图片 base64、真实剪贴板正文、secret 命中原文。
- 如果 fixture smoke 失败，stdout / stderr / exception message 需要先经过 sanitizer，再进入 JSON 或开发记录。

## 可优化

1. 复用既有 sanitizer。
   - 若项目已有 `verification_sanitizer.py` 或 P13A/P13B/P13C 的 sanitizer，P13D 应复用同一套 ROOT/HOME/path/email/token/base64 处理逻辑。
   - 避免 Step 4 单独维护一套正则导致口径漂移。

2. 明确 draft / cache 生命周期。
   - 技术方案已经写明 `detailEditRead` cache 在保存、取消、切换、record missing、reload 后失效。
   - 建议 P13D 加一条 cache lifecycle smoke：保存成功后旧 draft / old payload 不再作为 editable source；取消后 draft 不进入 repository。

3. URL full value 建议在 evidence 中只报 host / scheme / length / hash。
   - App 内可以本地保存和搜索完整 URL。
   - 验收 JSON、截图和失败详情不应输出 URL 全文，尤其是 query 中可能含 token。

4. Rich text fidelity evidence 建议输出结构性结果。
   - 例如 `links_preserved=true`、`inline_style_preserved=true`、`list_representative_preserved=true`。
   - 不输出 RTF 原文、HTML、长 body 或 base64。

5. `record-unavailable` 下“复制草稿文本如安全可行”需要保守。
   - 建议首版不把复制草稿作为默认验收路径；如实现，应作为显式复制动作，使用 fake pasteboard，且 evidence 不包含草稿正文。

6. `saved-index-pending` / `reindex-failed` 例外建议保留为非默认路径。
   - 技术方案已推荐默认同事务。
   - 安全合规同意：异步 reindex 会增加中间态、失败证据和输出面，除非技术上必要，不应主动引入。

## 可吸收建议

1. 推荐接受当前单一 Store / Repository command 口径。
   - 这是控制误写、部分提交和输出污染的关键边界。
   - 代码审查应重点检查 View / AppState / AppModel 没有变成 detail edit 事实源。

2. 推荐保留富文本 gate 为进入开发的硬门槛。
   - 若最低代表 fixture 不通过，应由项目负责人接受暂缓、只读或派生纯文本编辑。
   - 不应为了完成 Step 4 静默降级为 plain text payload。

3. 推荐把 metadata full value 放在显式动作，而不是默认布局。
   - 默认 metadata snapshot 只给 bounded value 和 availability。
   - 完整 URL、完整路径、OCR 原文、rich text body 都只在用户明确动作下读取。

4. 推荐将 OCR user-edited source 持久化。
   - View-local 标记不足以防 late completion 覆盖。
   - schema migration 或等价持久化字段是必要边界。

5. 推荐低敏证据使用 fixture ID + hash + length。
   - `detail_text_alpha_004`、`detail_image_ocr_done_004` 等 fixture 可作为行为证明。
   - 不需要也不应记录真实剪贴板正文、真实 OCR 原文或完整 URL/path。

6. 推荐不启动 Step 5/6。
   - 本复审不建议把真实 App 清单、CLI 广义对象管理、集成验收或真实系统环境回扫塞回 Step 4。
   - Step 4 只需保证自身不会新增这些能力。

## 可接受残余风险

1. Step 4 会读取并编辑真实本地剪贴板历史内容。
   - 这是用户已接受的产品方向。
   - 可接受前提是读取发生在显式 Edit / full value 动作下，并通过 purpose 隔离和 bounded default read model 控制。

2. Search document、summary、FTS、OCR text 会随保存更新。
   - 这是详情编辑一致性的必要结果。
   - 可接受前提是同事务或有清晰 pending / failed 状态，且删除 / 裁剪 / conflict 不留下可搜旧内容。

3. Metadata 完整值可被用户显式读取或复制。
   - 这是“长项完整语义路径”的可用性需求。
   - 可接受前提是默认布局不预读完整值，复制动作显式，证据低敏，真实 pasteboard 测试使用 fake / spy。

4. 富文本 round-trip 可能无法覆盖所有复杂格式。
   - 可接受前提是代表 fixture 是硬门禁；未通过时不开放普通富文本编辑，必须有项目负责人降级接受记录。

5. 真实 UI / VoiceOver / 真实系统剪贴板未在技术方案阶段验证。
   - 技术方案阶段只要求低敏 evidence 和 fake / spy。
   - 真实环境回扫可留给 Step 6 或专项验收，不应伪装成当前已验证事实。

## 推荐回写口径

建议项目负责人允许 Step 4 技术方案继续收敛，但要求技术方案 v1 或开发派发中明确补入：

- P13D 同时检查真实 pasteboard 读写为 0，并区分保存路径与 metadata full value copy 动作。
- P13D / sanitizer 补全凭据类 forbidden pattern，失败详情也必须低敏。
- P13D 对 Step 4 touched files 增加 provider / network / automation / permission denylist。
- 完整 URL、真实路径、OCR 原文、图片 base64、rich text body、secret 命中原文不得进入日志、verification JSON、开发记录或验收记录。

补齐这些后，安全合规视角建议接受 Step 4 技术方案进入开发准备。
