## P1 Findings

1. OCR user-edited schema migration 契约不足，且推荐默认值会把旧数据语义写偏。

   证据：

   - PRD 要求 AppState / Store 不成为 OCR / search document 事实源，并要求 user-edited OCR 不被 retry / late completion 静默覆盖：`docs/项目管理库/004_剪贴板打磨/step_4/产品经理-PRD-v1.md:286`、`docs/项目管理库/004_剪贴板打磨/step_4/产品经理-PRD-v1.md:290`、`docs/项目管理库/004_剪贴板打磨/step_4/产品经理-PRD-v1.md:193`。
   - 技术方案推荐新增 `ClipboardOCRTextSource`，但 v4 schema 示例把 `clipboard_search_documents.ocr_text_source` 设为 `TEXT NOT NULL DEFAULT 'vision'`：`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:464`、`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:474`。
   - 当前数据库迁移只到 v3，`MigrationRunner` 对 `currentVersion > 3` 直接报 unsupported：`apps/Blocks/BlocksCore/AppDatabase.swift:71`。现有 `clipboard_search_documents` 没有 OCR source 字段：`apps/Blocks/BlocksCore/AppDatabase.swift:170`。现有 `updateOCRResult` 只按 revision / redacted guard 更新 OCR 结果，尚无 user-edited guard：`apps/Blocks/BlocksCore/ClipboardRepository+SearchDocuments.swift:355`。

   风险：

   - 旧库中非图片、OCR pending / failed / empty、无 OCR 文本的 search document 会被默认标成 `vision`，与方案中 `none` 语义不一致。
   - 如果技术方案不明确 backfill、默认值、旧库 fixture 和 `updateOCRResult` guard，开发可能只做加列但没有稳定语义，导致 retry / late completion 防覆盖规则依赖运行时推断。
   - P13D 当前输出 schema 没有单独的 `schema_migration` / `ocr_source_backfill` 证据字段，难以 fail-closed 地证明旧数据可打开且 user-edited source 已持久化。

   可执行修正建议：

   - 技术方案 v1 明确 v4 migration：`addColumnIfMissing` / 等价幂等加列，`PRAGMA user_version = 4`，并把 `currentVersion > 4` 作为新 unsupported 边界。
   - `ocr_text_source` 默认建议为 `none`，再按旧数据 backfill：已有 OCR 文本且 `ocr_status == succeeded` 的记录标为 `vision`；其他记录保持 `none`；user-edited 只能由 Step 4 save command 写入。
   - 同步列出需要修改的 read / write 点：`loadSearchDocument`、`bindings(for:)`、`upsertSearchDocument`、`updateOCRResult`、`rebuildSearchDocuments`。
   - P13D 增加旧 v3 fixture DB 升级检查，至少覆盖无 OCR、Vision OCR succeeded、OCR failed、image OCR user-edited 保存后的 retry / late completion。

2. P13D 的 fail-closed 边界还没有把 AppState / AppModel 不扩权和完整 purpose 隔离写成可检查合同。

   证据：

   - PRD 要求 View 不分散写 payload / summary / search document / FTS / OCR，并要求 AppState / Store 只能 facade / 协调，不成为编辑后 payload / OCR / search document 事实源：`docs/项目管理库/004_剪贴板打磨/step_4/产品经理-PRD-v1.md:289`、`docs/项目管理库/004_剪贴板打磨/step_4/产品经理-PRD-v1.md:290`。
   - 技术方案正文也写明 `ClipboardDetailStore` 不是事实源，`AppModel` 不接收 detail payload / OCR 文本 / 保存事务事实，Repository 是唯一持久化事实源：`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:156`。
   - 但 P13D 最低断言和输出 schema 目前主要覆盖 `single_store_command`、`single_repository_command`、`view_direct_repository_writes` 和 `forbidden_purpose_reuse_count`：`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:647`、`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:687`。它没有显式要求扫描 AppState / AppModel / ClipboardController 是否新增 full detail payload、OCR text、search document 或 save fact state。
   - 技术方案第 7 节禁止复用 `.ocrInput` / `.searchIndex`，并定义 `detailFullValueRead`：`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:229`、`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:240`。但 P13D 最低断言只点名 `detailEditRead` / `detailEditSave`，未把 `detailFullValueRead` 作为正向存在检查，也未在输出 schema 中分开列出 `.ocrInput` / `.searchIndex` 禁复用。

   风险：

   - 开发可能把 detail draft、完整 payload、OCR 文本或 save result 暂存在 AppModel / AppState / ClipboardController，View 仍通过单一 Store command 保存，P13D 却可能因为没有直接 repository write 而通过。
   - metadata full value、编辑读取和保存读取三类 purpose 如果没有正向 / 反向矩阵，容易复用 `.hoverDetail`、`.copyPlainText`、`.searchIndex` 或 `.ocrInput`，破坏 Step 1 / Step 3 已建立的 purpose 边界。
   - P9B 作为通用 integration gate 不能替代 Step 4 专属的 negative scan；Step 4 新增状态和字段需要 P13D 自己 fail-closed。

   可执行修正建议：

   - P13D 增加 `state_ownership` 或等价输出字段：`appstate_detail_fact_source_clear`、`appmodel_detail_fact_source_clear`、`controller_detail_fact_source_clear`、`detail_store_draft_only`。
   - P13D 增加 purpose 矩阵：正向要求 `detailEditRead`、`detailFullValueRead`、`detailEditSave`；反向统计 `.hoverDetail`、`.paste`、`.copyPlainText`、`.translationPreview`、`.ocrInput`、`.searchIndex`、provider 相关 purpose 在 Step 4 detail edit / metadata full value / save 路径中的复用次数必须为 0。
   - P13D 对 save call graph 做正向约束：View -> `ClipboardDetailStore.save()` -> `ClipboardRepository.saveDetailEdit(command:)`；AppModel 只能承载非事实源 facade / status，不得保存 detail payload、OCR text 或 search document。

## P2 Findings

1. Pasteboard 不写入 static scan 的口径建议从“文件包含 forbidden token”升级为“保存路径 call graph 禁止间接写入”。

   技术方案已列出 `AppModel.pasteClipboardRecord`、`NSPasteboard.general.*` 等禁止保存调用：`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:605`。当前代码中 paste / copy 写系统 pasteboard 的路径集中在 `AppModel` 和 `ClipboardAutoPasteCoordinator`，例如 `apps/Blocks/BlocksApp/App/AppModel.swift:314`、`apps/Blocks/BlocksApp/App/AppModel.swift:944`、`apps/Blocks/BlocksApp/Services/ClipboardAutoPasteCoordinator.swift:103`。

   建议 P13D 不只扫 Step 4 detail save 文件是否包含 `NSPasteboard.general`，还要证明 `saveDetailEdit` 的可达调用链没有进入 `AppModel.pasteClipboardRecord`、`copyClipboardRecordAsPlainText`、`ClipboardAutoPasteCoordinator.paste` / `writePayload` 或其他 pasteboard adapter 写入方法。这样能避免通过 facade 间接写系统剪贴板。

2. 保存事务证据建议显式输出 atomic failure 断言。

   技术方案默认同一 repository transaction，方向正确：`docs/项目管理库/004_剪贴板打磨/step_4/App架构师-技术方案-v0.md:331`。PRD 也已有 `detail_save_atomic_failure_004` fixture：`docs/项目管理库/004_剪贴板打磨/step_4/产品经理-PRD-v1.md:389`。

   建议 P13D 输出 schema 增加 `transaction_atomicity`：模拟 payload / summary 写入后、search document / FTS 写入前失败时，断言 payload、summary、search document、FTS、updatedAt、detail read model 均回到保存前一致状态；若采用异步 reindex，则必须明确进入 `saved-index-pending` / `reindex-failed`。

## 可吸收建议与推荐口径

- 推荐口径：保留当前技术路线，但要求 App 架构师在 v1 中吸收上述 P1；不需要回到 PRD 重新定义范围。
- Batch A 的入口应是 P13D red baseline，而不是先做 UI。P13D 缺 evidence、缺 schema migration fixture、缺 boundary negative scan 时必须失败。
- 默认坚持同步 repository transaction。只有开发能证明现有 `ClipboardSearchDocumentBuilder` / `upsertSearchDocument` 不能放入同一 transaction 时，才启用异步 reindex，并要求项目负责人接受 pending / failed 用户态。
- Rich text 推荐继续 gate-first：最低 fixture 不过时，优先暂缓富文本编辑或只读 + 可复制纯文本；不要在实现中转成 plain text payload。
- Detail editor 可以由 View 持有短期 UI draft，但完整 payload / OCR / search document / save result 的持久事实只认 Repository；AppModel 不承载 detail edit fact。
