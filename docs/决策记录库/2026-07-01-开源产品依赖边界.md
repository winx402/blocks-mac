# 开源产品依赖边界

状态：active
决策日期：2026-07-01
来源级别：user-confirmed decision

## 背景

V1 方向包含截图、剪贴板和翻译三类 macOS 高频工具。GitHub 上已经存在多个相关开源产品或公开项目，例如截图/标注、剪贴板历史、翻译/OCR、图片压缩等工具。

这些项目可提供产品功能、交互深度、边界设计和验收场景参考，但多数不是本项目所需的原生一体化形态。本项目的核心差异仍是：Mac 原生体验、同一套 action core、UI / CLI / agent 共用能力、权限与隐私可解释。

## 选项

1. 直接依赖开源产品，把部分功能交给外部 App 完成。
2. Fork 或复制开源产品代码作为本项目实现基础。
3. 不依赖开源整包产品，只把它们作为产品功能、交互深度和边界设计参考。

## 结论

选择选项 3。

本项目 V1 不把现有开源整包产品作为核心运行依赖，也不默认要求用户安装它们来完成截图、剪贴板或翻译主路径。开源产品可以用于：

- 对比功能清单、核心 Jobs、入口组合、交互细节和失败场景。
- 提炼功能深度、体验底线和验收标准。
- 识别成熟工具的产品边界，避免低估基础体验要求。

开源产品不得作为：

- V1 核心功能的唯一实现。
- 正式分发包中的未评估二进制依赖。
- 用户使用主路径的默认前置条件。
- 绕过本项目 action schema、权限确认和审计记录的捷径。
- 技术实现路线、代码复用或架构选型的默认依据。

底层开源库、命令行工具或系统框架不属于本决策所说的“整包产品”。如需引入，应单独评估许可证、分发方式、可替换性、性能和隐私边界。

## 后果

- 截图、剪贴板和翻译的主链路仍应按本项目的 Mac 原生体验和 action core 设计推进。
- Pot、CopyQ、Maccy、Easydict、eSearch、Flameshot、ksnip、ImageOptim、Caesium 等项目可以作为产品功能和体验参考对象，但不能被写成默认依赖。
- 产品规格可以引用这些项目的功能深度、入口设计和失败场景；技术方案不得把它们的实现方式直接写成本项目默认路线。
- 若后续为了验证效率临时使用外部 App，必须标注为一次性验证手段，不进入正式产品承诺。

## 复审条件

出现以下情况时复审本决策：

- 找到足够原生、许可证清晰、可稳定调用、可审计且可嵌入本项目 action core 的开源产品。
- V1 范围调整为插件式工具集合，而不是原生一体化工具箱。
- 某一底层能力自研成本明显高于预期，且已有可替换开源组件能满足许可证、分发和隐私要求。
