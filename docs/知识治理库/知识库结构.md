# 知识库结构

状态：active
最后审阅：2026-06-29
来源级别：authoritative definition

## 核心原则

1. 先定归属，再写内容。每份长期文档必须有一个主要问题和一个主要知识库。
2. 不重复维护事实。跨领域内容通过链接引用主文档，不复制整段定义。
3. 区分事实、推断、建议、待验证项。未验证内容必须标注状态。
4. 不保存敏感凭据。密码、API key、完整订阅链接、验证码、私钥和完整支付信息不能写入仓库。
5. 可变信息必须有日期。涉及价格、版本、政策、接口能力、系统限制和账号状态时，执行前重新核验。

## 顶层知识库职责

| 知识库 | 拥有 | 不拥有 |
| --- | --- | --- |
| 项目管理库 | 目标、阶段状态、计划、验收、交接 | 产品方案正文、技术方案正文、调研证据全文 |
| 产品知识库 | 产品定位、用户、使用场景、功能范围、体验原则 | 任务进度、代码实现细节、竞品原始摘录 |
| 技术知识库 | 架构假设、接口设计、运行时边界、权限和分发约束 | 产品价值判断、项目排期、竞品营销描述 |
| 调研与验证库 | 来源资料、竞品调研、验证计划、实验记录、待验证问题 | 已接受的长期产品定义、最终技术决策 |
| 决策记录库 | 重要选择的背景、选项、结论、后果和复审条件 | 日常状态、临时讨论、未经决定的假设 |
| 知识治理库 | 文档结构、归属规则、命名规则、维护流程 | 项目业务内容 |

## 文档状态

- `idea`：早期构想，尚未进入正式计划。
- `proposed`：建议方案，等待验证或确认。
- `active`：当前有效的源文档或流程。
- `evidence-only`：只作为证据或历史输入保留。
- `deprecated`：不再推荐使用，但保留历史。
- `superseded`：已被其他文档取代，必须链接到新文档。

## 命名规则

- 长期主题使用清晰主题名，例如 `产品定位.md`。
- 调研记录使用 `YYYY-MM-DD-主题.md`，保留时点属性。
- 决策记录使用 `YYYY-MM-DD-决策主题.md`。
- 子目录应代表可复用分类，不为单篇一次性内容过度嵌套。

## 维护流程

1. 判断新信息是否已经有明确归属。
2. 如果没有明确归属，先放入调研与验证库并标注来源、日期、待验证点。
3. 如果形成长期定义，更新拥有该问题的知识库文档，并同步维护该知识库的 `index.md`。
4. 如果形成重要选择，补一条决策记录并链接到被影响的主文档。
5. 如果涉及执行计划，在项目管理库记录状态和交付物链接。
